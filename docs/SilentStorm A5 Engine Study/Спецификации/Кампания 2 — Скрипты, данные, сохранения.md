# Кампания 2 — Скрипты, данные, сохранения

Источник: `reconstruction\Script` (изменённая Lua 4), `reconstruction\Main` (A5Script.*, ScriptFunctions.cpp, script*.cpp, iScriptScene.*, GResource.*, ModManager.*, iSaveManager.*, iMain.cpp, iMission.cpp), `reconstruction\DBFormat`, `reconstruction\ADOImport`, `reconstruction\DataImport`, `reconstruction\FileIO` (BasicChunk1.*, FilesPackage.*, Cruncher.cpp), `reconstruction\Misc` (Basic2.*, BasicFactory.h, BasicShare.h), `reconstruction\MiscDll\Commands.*`; база `C:\run\ss-db\A5GAME.sqlite` (таблица `Scripts`); библиотеки `Complete\Scripts\*.l`; примеры модов `Versions\Current`.

## Суть

Вся «режиссура» Silent Storm — сцены, триггеры, диалоги, цели миссий, меню выбора кампании — написана на Lua 4, но на сильно переделанной виртуальной машине. Её главная особенность: **всё состояние Lua — это просто данные**. Объекты Lua (таблицы, функции, прототипы, userdata) лежат в пронумерованных массивах, ссылки между ними — номера, а вызов функции — запись в явном стеке кадров потока, а не рекурсия C. Поэтому машину можно в любой момент записать в файл целиком — со всеми «спящими» потоками, стоящими посреди цикла ожидания, — и потом продолжить с той же инструкции. Скрипт — набор кооперативных потоков: поток работает, пока сам не уснёт (`Sleep(n)` — пропустить n тактов мира по 50 мс) или пока не закончится функция; на каждом такте мира движок один раз прокручивает все потоки. Вызовы из игры в Lua (`OnOpenObject`, `OnTalk`…) не выполняются сразу, а заводят новый поток, который отработает в ближайший такт.

Данные игры — это реляционная база (≈290 таблиц SQL Server), которая для игры выгружается в один файл `game.db`: по каждой таблице — столбцы целых, дробных и строковых значений; при загрузке из них строятся типизированные записи с прямыми ссылками друг на друга (двухпроходный импорт). Мод — это ещё один `game.db` той же формы, в котором неизменённые ячейки помечены «пустышкой» `0xFDFDFDFD`, плюс папка с ресурсами, которые перекрывают исходные по номеру. Сохранение игры — это сериализация **всего стека интерфейсов** (меню, миссия, мир, ИИ, скрипт) одним универсальным механизмом «чанков» с номерами полей, с поддержкой указателей между объектами и сжатием LZ; рядом лежат файлы зон для повторного входа и снимок `restart.sav` для перезапуска миссии.

## 1. Изменённая виртуальная машина Lua 4

### Назначение
Исполнять скрипты миссий как набор долгоживущих кооперативных потоков, которые можно в любой момент сохранить в файл и восстановить. Для этого стандартная Lua 4.0 (2000 г.) переделана так, что в её состоянии нет ни одного «сырого» адреса памяти, кроме интернированных строк и объектов движка, а вызов Lua-функции не использует стек C.

Изменённые относительно стандартной Lua 4.0 файлы (`Script\`): `lstate.h/.cpp` (новое состояние и потоки), `lobject.h/.cpp` (значения-индексы, таблицы на хеш-контейнере, сериализация), `lvm.cpp` (пошаговый интерпретатор), `ldo.cpp` (начало/конец вызова, запуск файлов и буферов), `lapi.cpp` (API, потоки, `Sleep`, `StartThread`, `lua_executeThreads`), `lgc.cpp` (сборщик по массивам), `lfunc.cpp`, `ltable.cpp`, `lstring.cpp` (строки и userdata), `ltm.h/.cpp`, `ldebug.cpp`, `lmem.cpp`, `lsaver.h/.cpp` (новый: имена C-функций), `lua.h` (новые теги и функции), `Script.h/.cpp` (обёртка и разбор аргументов). `lparser.cpp`/`lcode.cpp`/`llex.cpp` — стандартные, только прототипы создаются по номеру. `lundump.cpp` целиком закомментирован: **предкомпилированные (двоичные) чанки не поддерживаются**, только исходный текст. Стандартная библиотека Lua (`lbaselib`, `lstrlib`, `lmathlib`, `liolib`) **не подключена вовсе**: в скриптах нет `tostring`, `getn`, `strlen`, `format`, `floor`, `call`, `dofile`, `next`, `foreach`, `tinsert`, `settagmethod` и т. п. — доступны только функции движка (раздел 7) и общие библиотеки (раздел 9).

### Данные

**Значение (TObject)**: тип + 8-байтное поле. Число — `double`; строка — указатель на интернированную строку; таблица, функция (замыкание), userdata, служебная метка вызова — **целый индекс** в соответствующем массиве состояния.

| Тип Lua | Код | Поле значения |
|---|---|---|
| userdata | 0 | индекс в `userdatas` |
| nil | 1 | — |
| number | 2 | double |
| string | 3 | интернированная строка |
| table | 4 | индекс в `tables` |
| function | 5 | индекс в `closures` |
| (метка активного вызова) | 6 | индекс в `callInfos` |

Пользовательские теги: 6 — слабый указатель на объект движка (`tagLuaCPtr`), 7 — владеющий (`tagLuaCObj`), 8 — окно интерфейса (`tagLuaWindow`). Они создаются при инициализации скрипта тремя вызовами «новый тег» именно в этом порядке и проверяются по номерам.

**Состояние (lua_State)**:

| Поле | Смысл |
|---|---|
| `pContext` | Владеющий объект движка (скрипт `CScript`). |
| `pCT` | Текущий поток. |
| `threads` | Список потоков в порядке создания. |
| `nGT` | Индекс таблицы глобальных переменных. |
| `TMtable` | Методы тегов: на каждый тег 15 событий (`gettable`, `settable`, `index`, `getglobal`, `setglobal`, `add`, `sub`, `mul`, `div`, `pow`, `unm`, `lt`, `concat`, `gc`, `function`) — индекс замыкания или −1; плюс список собранных userdata. |
| `refArray`, `refFree` | Таблица ссылок (`lua_ref`): объект + состояние (LOCK −4, HOLD −2, COLLECTED −3, иначе номер следующей свободной). Ссылка 0 — «реестр». |
| `nGCticks` | Счётчик проверок сборщика. |
| `nGCAvoid` | >0 — сборка запрещена. |
| `nNoWait` | Глубина синхронных вызовов; при >0 `Sleep` игнорируется. |
| `strings` | Множество интернированных строк (никогда не очищается). |
| `protos`, `closures`, `tables`, `userdatas`, `callInfos` | Пять «векторов со свободным списком»: массив ячеек, пустая ячейка хранит номер следующей пустой; новый объект занимает последнюю освобождённую ячейку (LIFO), иначе дописывается в конец. |
| `callhook`, `linehook` | Отладочные крючки (сохраняются по имени). |

**Прототип** (скомпилированная функция): константы-числа, номера вложенных прототипов, байт-код, число параметров, признак `...`, размер стека, таблица строк, номера строк исходника, имена локальных переменных, строка определения.
**Замыкание**: признак «C-функция», либо адрес C-функции, либо номер прототипа; массив upvalue.
**Таблица**: хеш-контейнер «значение → значение» (без отдельной части-массива, в отличие от стандарта) + тег.
**Userdata**: тег, отметка сборщика, слабый указатель `CPtr`, владеющий указатель `CObj` (заполнен один из двух, по тегу).
**Сведения о вызове**: номер замыкания, номер прототипа, последний PC, строка, индекс в таблице строк.

**Поток (CLuaThread)**: `top` (первая свободная ячейка), `Cbase` (база текущей C-функции), `stack` (массив значений, исходно 1024 ячейки, удваивается при нехватке), `executedCalls` (стек кадров: номер прототипа, номер замыкания, база, текущая инструкция `currPC`, ожидаемое число результатов), `thisThreadIsSleeping` (счётчик сна), `bErrorInThread`, `name` (отладочное имя).

### Алгоритм: вызов функции (инструкция CALL или вызов из C)
1. Если вызываемое значение не функция — ищется метод тега `function`; если его нет — ошибка «attempt to call a nil value» (раздел 1, ошибки).
2. Создаётся запись «сведения о вызове», ячейка стека с функцией заменяется меткой (тип 6) с её номером.
3. **C-функция** выполняется сразу: база C-функции = ячейка после функции; upvalue дописываются как дополнительные аргументы; функция возвращает число результатов n; результаты (последние n ячеек) копируются на место функции, недостающие заполняются `nil`, лишние отбрасываются (если ожидалось фиксированное число). Сведения о вызове удаляются.
4. **Lua-функция** не выполняется: число аргументов подгоняется под число параметров (лишние отбрасываются, недостающие — `nil`; при `...` лишние упаковываются в таблицу с полем `n`), и на стек кадров потока **кладётся новый кадр** с `currPC = 0`. Дальше её будет выполнять общий цикл.

### Алгоритм: шаг интерпретатора (`luaV_stepExecute`)
Пока (у потока нет ошибки) И (идёт синхронный вызов `nNoWait > 0` ИЛИ счётчик сна ≤ 0) И (стек кадров не пуст):
1. Взять верхний кадр, прочитать инструкцию по `currPC`, увеличить `currPC`.
2. Выполнить её (семантика как в Lua 4.0, но все обращения к объектам — через индексы).
3. `RETURN`: снять кадр, переложить результаты на место функции, **продолжить** цикл (выполнение продолжится в кадре вызвавшей функции).
4. `END` (неявный конец функции): снять кадр, переложить результаты (их ноль) — и **выйти из цикла**. То есть любая Lua-функция, закончившаяся без явного `return`, отдаёт управление до следующего тика: поток продолжит вызывающую функцию только на следующем `ExecuteThreads` (подтверждено комментарием о поведении релиза v1.1/v1.2).
5. `CALL` с Lua-функцией кладёт кадр и цикл сразу продолжает выполнять уже её.

### Алгоритм: синхронный вызов из C (`luaD_call`)
`nNoWait += 1`; начать вызов; если это Lua-функция — прокрутить `luaV_stepExecute` (из-за `nNoWait > 0` сон не останавливает цикл); `nNoWait −= 1`. Используется только для методов тегов, сборщика мусора и доставки сообщения об ошибке. **Вызовы из игры в Lua этим путём не идут** (раздел 8.1).

### Таблицы, строки, userdata
- Таблица — хеш-контейнер. Ключи сравниваются по содержимому для строк, по значению для чисел, по индексу для остальных типов. Хеш: число → `(long)число`; строка — стандартный строковый хеш; таблица/функция/userdata → `индекс >> 3`.
- Присваивание `t[k] = nil` **не удаляет** ключ: в хеш-контейнере остаётся пара с `nil`. Такие пары удаляет только фаза разметки сборщика. Поэтому `for k, v in t` и `next` до сборки мусора **возвращают ключи с v = nil** (библиотека триггеров явно проверяет `handler ~= nil`).
- Порядок обхода таблиц — порядок хеш-контейнера, не порядок ключей; для «массивов» 1..n он не обязан быть возрастающим.
- Длина (`lua_getn`, функция `TableGetSize`): значение поля `n`, если оно число, иначе наибольший целый ключ с не-nil значением.
- Строки интернируются в множество состояния и **никогда не собираются**.
- Userdata для объекта движка **переиспользуется**: при упаковке указателя сначала линейно ищется существующая userdata с тем же тегом и тем же объектом; найденная возвращается (поэтому два `GetUnit("x")` дают равные значения `==`). Слабая (тег 6) и владеющая (тег 7) обёртки одного объекта — разные значения и `==` для них ложно; сравнивать нужно функцией `IsEqual`.
- При чтении глобальной проверяется метод тега `getglobal` для тега её значения (в игре таких методов нет); если значение `nil`, в консоль пишется красное «[Script warning!] Value was NIL when getting global with name …», **кроме имени `FALSE`** (имя `false` предупреждение даёт).

### Ошибки
1. Синтаксическая ошибка при разборе буфера: печатается сообщение, новый поток помечается ошибочным и без кадров — удаляется на ближайшем тике.
2. Ошибка времени выполнения (`lua_error`): сначала сообщение доставляется глобальной функции `_ERRORMESSAGE` (в игре — печать «Script error: …» в консоль) на отдельном потоке «Message thread» синхронным вызовом; затем стек вызовов сохраняется в «последнюю ошибку» (консольная команда `scripterror`); затем, поскольку во время тика нет защищённого режима, **текущий поток помечается ошибочным**, исключение не бросается. Текущая инструкция дорабатывает (C-функция возвращает 0 результатов), цикл видит флаг и выходит, поток удаляется в конце обхода. Остальные потоки продолжают работать.
3. Неверный тип или нехватка аргументов функции движка — это тоже `lua_error` (раздел 7.0): поток, вызвавший функцию с неправильными аргументами, умирает.

### Сборка мусора
1. Проверка `luaC_checkGC` вызывается при каждом завершении вызова функции, создании таблицы или замыкания, конкатенации. Сборка выполняется, когда счётчик проверок превысил **1000** (`++nGCticks > 1000`), после чего счётчик обнуляется. Объём памяти не учитывается.
2. Разметка: таблица глобальных, методы тегов, **стеки всех потоков** до `top`, ссылки LOCK; далее рекурсивно upvalue замыканий, ключи и значения таблиц. Пары с `nil`-значением при разметке удаляются из таблиц.
3. Сбор: неотмеченные таблицы, прототипы, замыкания освобождаются; неотмеченные userdata — после вызова метода `gc` тега (если есть) — освобождаются, вместе с ними снимается и владеющая ссылка на объект движка (так умирают группы, позиции, команды звука, созданные скриптом и нигде не запомненные).
4. Причуда реконструкции: при обходе userdata после отмеченной ячейки индекс увеличивается дважды, так что следующая за живой userdata ячейка в этот проход не проверяется (её отметка не снимается, сбор откладывается). Оригинал — не подтверждено.

### Формулы
- Номер свободной ячейки: `push`: если есть свободная — берётся голова свободного списка; иначе индекс = размер массива.
- Стек потока: если `размер − 1 − top ≤ n` при запросе n ячеек — размер удваивается.

### Особые случаи и прихваты
- **`return f(...)` опасен.** Компилятор Lua 4 превращает `return f(...)` в инструкцию «хвостовой вызов». Интерпретатор выполняет её как «начать вызов f, затем вернуться из верхнего кадра». Для C-функции f это работает. Для Lua-функции f «верхний кадр» после начала вызова — уже кадр самой f, поэтому f фактически не исполняется, а вызывающая функция возвращает `nil`. Все функции общих библиотек и почти все скрипты пишут `local a = f(...) return a` — по-видимому, именно из-за этого. В реализации на новом движке либо исправить, либо сохранить ограничение и правило для авторов (оригинал — не подтверждено, вывод из кода реконструкции и стиля всех скриптов).
- Неявный конец функции = пауза в один тик (п. 4 шага интерпретатора). Функция-«условие» триггера без явного `return` подвешивает менеджер триггеров на тик.
- Синхронный вызов Lua-функции, которая заканчивается `RETURN`, продолжил бы выполнять кадры вызывающего потока внутри C-вызова; на практике недостижимо, потому что Lua-методов тегов скрипты поставить не могут (нет `settagmethod`).
- Целые параметры функций движка проходят через `float` (см. 7.0): целые больше 2^24 = 16 777 216 теряют точность.
- Свободные ячейки массивов переиспользуются в порядке LIFO; индекс освобождённого объекта может достаться новому (опасно только при хранении индексов вне Lua — так делает обработчик окна, раздел 8.3).

### Что нужно от движка-носителя
Либо собственная реализация Lua 4 с теми же свойствами (сохраняемые потоки, явный стек кадров, сон в тиках), либо современная Lua 5.x с корутинами и полной сериализацией состояния (например, Eris/Pluto), где `Sleep` = `coroutine.yield` с счётчиком тиков, а C-функции регистрируются в таблице «имя → функция» для восстановления. Оригинальный Lua 4 синтаксически отличается от 5.x (`for k,v in t`, `%upvalue`, `~=`), поэтому для запуска оригинальных скриптов нужен либо порт Lua 4, либо транслятор.

## 2. Потоки скриптов, Sleep и такт выполнения

### Назначение
Дать дизайнеру писать сценарии «прямолинейно» (`идти → ждать → сказать → ждать`) без колбэков: каждый сценарий — поток, который сам решает, когда отдать управление.

### Данные
Список потоков состояния (порядок создания), текущий поток, у каждого потока счётчик сна и флаг ошибки (раздел 1). Отладочные имена потоков (сохраняются, видны в `script_show all`): «First thread» (создаётся вместе с состоянием), имя файла (запуск файла), «Buffer thread» (запуск строки/буфера), «Message thread» (доставка ошибки), «thread made by StartThread», «Thread to have at least one», имя вызываемой глобальной функции (вызов из игры).

### Алгоритм: такт (`lua_executeThreads`)
Для каждого потока в порядке списка (новые потоки, добавленные во время обхода, попадают в конец и **выполняются в этом же обходе**):
1. Если поток недействителен — удалить из списка, перейти к следующему.
2. Если у потока нет ошибки и счётчик сна > 0: уменьшить счётчик на 1; если он всё ещё > 0 — пропустить поток.
3. Сделать поток текущим и выполнить шаг интерпретатора (раздел 1): поток работает, пока не уснёт, не закончит неявным концом какой-либо функции, не опустеет стек кадров или не случится ошибка.
4. Если у потока ошибка или стек кадров пуст — удалить его из списка.
После обхода: если список пуст — создать пустой поток «Thread to have at least one»; текущим сделать первый поток списка.

### Алгоритм: `Sleep(n)`
1. Если идёт синхронный вызов (`nNoWait > 0`) — ничего не делать.
2. Иначе, если у текущего потока нет ошибки: без аргумента счётчик сна = 1; с аргументом = `(int)n` (дробная часть отбрасывается к нулю).
3. Функция возвращает управление интерпретатору; цикл шага видит счётчик > 0 и выходит.

Итог: `Sleep(n)` при n ≥ 1 — поток пропускает n−1 тиков и продолжает на n-м следующем вызове `ExecuteThreads`; `Sleep(0)`, `Sleep(0.5)` и отрицательные значения не дают паузы вовсе (кроме паузы от неявного конца функции).

### Алгоритм: `StartThread(f, a1, …)`
1. Первый аргумент обязан быть функцией, иначе ошибка («StartThread first parameter must be a function» / «Must be at least one parameter for StartThread»).
2. Создаётся новый поток «thread made by StartThread», в него копируются функция и аргументы, в нём **начинается** вызов (кладётся кадр, ничего не исполняется), исходный поток получает обратно свой стек без этих значений.
3. Новый поток в конце списка, поэтому при вызове из потока мира он стартует в этом же такте, после всех потоков, стоящих в списке раньше.
4. Возвращаемое значение — ничего (нет «дескриптора потока»: остановить или дождаться чужой поток нельзя, только через глобальные флаги).

### Алгоритм: запуск исходного текста (`DoString`, `DoBuffer`, `DoFile`)
1. Создать новый поток (имя — «Buffer thread» или имя файла), сделать его текущим.
2. Разобрать текст в прототип и замыкание; при синтаксической ошибке — сообщение, поток помечен ошибочным.
3. Если разбор удался — **начать** вызов главного чанка (только кадр).
4. Вернуть текущим прежний поток. Код верхнего уровня выполнится на ближайшем тике, в общем порядке потоков.

### Где и когда вызывается такт

| Скрипт | Когда тикает | Источник |
|---|---|---|
| Скрипт мира миссии / меню-сцены / глобальной карты / карты главы | Один раз в конце каждого `CWorld::Segment`: после командных очередей, юнитов, объектов, обломков, синхронизации карты ИИ, акков, взрывов и отложенного пересчёта видимости; перед проверкой хода реального времени, однократным `OnEnterZone`, погодой и сторожем проигрыша. Перед тактом глобальная «текущая» ссылка на скрипт ставится на скрипт этого мира. | `wMain.cpp` |
| Тот же скрипт, когда мир не сегментирует, но интерфейсу нужен скрипт (меню) | `ExecuteOwnScript` из интерфейса каждый кадр (сначала тоже выставляется глобальная ссылка). | `wMain.cpp` |
| Скрипт окна интерфейса (контейнер с ScriptID) | В `CWindow::Update`, пока окно требует обновления. | `UIWindow.cpp` |
| Обработчик события окна | Сразу после постановки вызова — немедленный внеочередной такт этого скрипта. | `UIWindow.cpp` |

Следствия: `Sleep(1)` в миссии ≈ 50 мс игрового (не реального) времени; когда игра на паузе или идёт загрузка — время скрипта стоит; при «перемотке» невидимых действий и при пропуске сцены (раздел 6) сегменты идут быстрее реального времени, и скриптовые паузы сжимаются. Счёт ходов в пошаговом режиме идёт отдельно (`SleepForTurn`, раздел 9).

### Особые случаи и прихваты
- **Синхронные вызовы игнорируют сон**: если Lua-функция вызвана синхронно из C (метод тега, сборщик), `Sleep` внутри неё ничего не делает.
- Поток, вызвавший функцию с неверными аргументами или неопределённую глобальную функцию, умирает молча (кроме сообщения в консоль). Типичный случай в данных: 10 вызовов `WaitForInterface()` — функции, которой в релизных библиотеках нет.
- Порядок выполнения потоков = порядок их создания; для одинакового поведения при сохранении/загрузке список потоков сохраняется вместе с порядком.
- Поток верхнего уровня скрипта, вызвавший бесконечный цикл с `Sleep` (так устроен менеджер триггеров), живёт до конца мира и сохраняется в каждом сейве.

### Что нужно от движка-носителя
Тикер, вызываемый ровно один раз за игровой сегмент в фиксированной точке порядка обновления мира; список корутин с порядком создания; счётчик сна в тиках, а не в секундах.

## 3. Сохранение состояния Lua и восстановление C-функций

### Назначение
Сохранить скрипт миссии «на ходу»: все глобальные переменные, все потоки с их стеками и точками остановки, все скомпилированные функции, все ссылки на объекты игры — и после загрузки продолжить ровно с той инструкции, где поток спал.

### Данные: что входит в сохранение
Скрипт мира (`CScript`, класс 0x70652130) — поле мира с тегом 32; мир — поле миссии; миссия — элемент стека интерфейсов (раздел 15). Скрипт окна интерфейса — поле окна с тегом 17, таблица обработчиков окна — тег 16.

| Объект | Тег | Содержимое |
|---|---|---|
| `CScript` | 1 | базовая часть: тег 2 «состояние наше» (bool), тег 3 — само состояние Lua |
| | 2 | мир (ссылка) |
| | 3 | список номеров ожидаемых команд интерфейса (раздел 6) |
| | 4 | слабый список «прочих объектов» (команды звука/эффекта, раздел 7.3) |
| | 5 | интерфейс окна, к которому привязан мост окон (слабая ссылка) |
| Состояние Lua | 2 | текущий поток |
| | 3 | рабочий буфер |
| | 4 | список потоков (владеющие ссылки на объекты-потоки, класс 0x70813170) |
| | 5 | индекс таблицы глобальных |
| | 6 | таблица методов тегов (на тег: 15 индексов замыканий + список собранных userdata) |
| | 7, 8 | таблица ссылок и голова её свободного списка |

| | 19, 20 | крючки вызова и строки — **по имени** |
| | 21 | владелец (скрипт) |
| Поток | 2..8 | `top`, `Cbase`, весь массив стека (включая ячейки выше `top`; поэтому новые ячейки обязаны быть корректным `nil`), стек кадров (на кадр: прототип, замыкание, база, текущая инструкция, число результатов), счётчик сна, флаг ошибки, имя |
| Значение | 2, 3 | тип; затем число (8 байт) / индекс / **текст строки** |
| Прототип | 2..12, 14, 15 | признак «создан», числа, номера вложенных, байт-код, параметры, `...`, размер стека, отметка, номера строк, локальные (начало, конец, имя-текст), строка определения; 14 — число строк-констант, 15×N — сами строки текстом. Имя исходника (13) **не сохраняется**. |
| Замыкание | 2, 3, 4 | признак C, upvalue, затем **имя C-функции** или номер прототипа |
| Таблица | 2, 3 | пары ключ-значение, тег |
| Userdata | 2..5 | тег, отметка, слабый и владеющий указатели — как ссылки на объекты общего сериализатора (раздел 14) |
| Сведения о вызове | — | 20 байт «как есть» (5 целых) |

### Алгоритм: запись
1. Перед записью состояния регистрируется имя «NOFUNC» для нулевого указателя функции и запоминается «текущее сохраняемое состояние» (нужно для интернирования строк при чтении).
2. Поля пишутся по тегам (раздел 14). Каждое значение-строка пишется **полным текстом** в каждом месте, где встречается (дубли не сжимаются, кроме общего LZ-сжатия файла).
3. Для C-замыкания адрес функции переводится в имя по глобальному словарю «адрес → имя». Нет в словаре — авария (в отладке — assert).
4. Указатели userdata на объекты игры пишутся как ссылки сериализатора: сам объект (юнит, группа, маршрут, позиция, команда интерфейса, окно) сохраняется один раз как объект мира и при чтении связывается.

### Алгоритм: чтение
1. Старое состояние закрывается; создаётся новое пустое состояние (с первым потоком и регистрацией `_ERRORMESSAGE`), затем все поля перечитываются поверх: массивы очищаются и заполняются из файла.
2. Строки из файла заново интернируются в множество нового состояния.
3. Имя C-функции переводится в адрес по словарю «имя → адрес». Словари глобальные и заполняются при **создании любого скрипта**: каждая регистрация глобальной функции (`lua_register`) кладёт пару «имя ↔ адрес»; поэтому на момент загрузки словари уже полны.
4. Потоки восстанавливаются с их стеками кадров; спящий поток продолжит со следующей инструкции после вызова `Sleep` на первом тике после загрузки, с сохранённым остатком счётчика сна.

### Правила словаря имён C-функций
- Ключ — **глобальное имя**, под которым функция зарегистрирована в Lua. Одна функция под двумя именами (`HasInventoryItem` и `WhoHasInventoryItem`; `_ERRORMESSAGE` — три разных функции под одним именем): «адрес → имя» хранит последнее зарегистрированное имя, «имя → адрес» — последнюю зарегистрированную функцию. Сохранённая ссылка на функцию-обработчик ошибок после загрузки станет текущим обработчиком — безвредно.
- Методы тегов, регистрируемые списком, получают имя «имя события + символ с кодом тега» (в игре список пуст; методы тега окна ставятся функциями, уже известными по глобальным именам).
- Переименование функции движка между версиями ломает загрузку старых сохранений, где на неё есть ссылка.

### Особые случаи и прихваты
- После загрузки **скрипты не перезапускаются**: исполняется сохранённый байт-код. Исправление скрипта в базе или моде не влияет на уже начатую миссию из сейва; общие библиотеки (`Common.l` и др.) тоже не перечитываются — в состоянии лежат их функции на момент начала миссии.
- Имя исходного файла прототипа не сохраняется: в сообщениях об ошибках после загрузки нет имени источника.
- Сохранение файла зоны (раздел 15) временно отвязывает у скрипта ссылку на интерфейс, чтобы сериализатор не утянул в файл зоны весь интерфейс миссии.
- Сохранять можно в любой момент между тиками; внутри тика (`nNoWait > 0`) сохранение не происходит — команды сохранения выполняются циклом интерфейса между кадрами.

### Что нужно от движка-носителя
Сериализация корутин вместе с их стеками (для Lua 5.x — Eris или собственный формат), реестр C-функций по стабильным именам, сериализация ссылок «Lua → объект игры» через стабильные идентификаторы объектов (в UE — `FGuid`/путь объекта + таблица фиксации ссылок при загрузке).

## 4. Источники скриптов и порядок их запуска

### Назначение
Определить, какой код Lua попадает в какое состояние Lua и в каком порядке начинает выполняться.

### Данные
- У **каждого мира** (`CWorld`) — своё состояние Lua (`pOwnScript`). Миры есть у миссии, у глобальной карты, у карты главы, у фоновых сцен меню (главное меню, выбор кампании, экран персонажа) — все они «миры», построенные из шаблонов карт.
- У окна интерфейса, загруженного из контейнера с непустым `ScriptID`, — отдельное состояние Lua без мира.
- Таблица `Scripts` (113 записей в базе ноября 2003): `ID`, `UserName`, `CodeText`. Ссылки на скрипты: `TemplVariants.ScriptID` (115 вариантов шаблонов, 95 разных скриптов), `GlobalMaps.ScriptID` (Axis → 91 «GmapAxis», Allies → 90 «GmapAllies»), `ChapterMaps.ScriptID` (92/93 — главы союзников/оси, 103/104 — финальные главы, `BeginZone("ffight")`), `UIContainers.ScriptID` (в базе не заполнен ни у одного контейнера), связь `RPGPers2Scripts` (1 строка, ссылается на несуществующий скрипт 5).
- Таблица `AutoLoadScripts` (`ID`, `FileName`): 1 `scripts\Constants.l`, 2 `scripts\TriggersManager.l`, 3 `scripts\Common.l`, 4 `scripts\Hint.l`.

### Алгоритм: порядок для мира миссии
1. **Создание мира** (конструктор): создаётся скрипт, затем для каждой записи `AutoLoadScripts` в порядке обхода таблицы (хеш-контейнер записей; по `ID` не гарантировано) файл читается **с диска** (`CFileStream`, путь относительно папки игры, не через пакеты ресурсов и не через папки модов) и запускается как буфер — каждый в своём потоке. Ничего ещё не исполняется.
2. **Построение карты**: при обходе дерева шаблонов (см. «Карта 1») скрипт каждого варианта шаблона собирается в список в **обратном (пост-) порядке**: сначала скрипты всех вложенных прямоугольников (рекурсивно, в порядке прямоугольников), затем скрипт самого варианта; скрипт корневого варианта — последний.
3. **Пост-инициализация** (`RunPostInit`): поднимается флаг «первый сегмент» (для `OnEnterZone`); каждый собранный скрипт карты запускается как строка (свой поток на каждый); расставляются ловушки на дверях; затем «разогрев»: 1 сегмент + ещё сегменты, пока скрипт «заморозил старт» (`c_DelayGameStartEx`), + 1 сегмент после разморозки (подробности — 6.5). Разогрев выполняется и для мира, восстановленного из файла зоны. На первом же сегменте разогрева выполняется верхний уровень всех библиотек (в порядке создания их потоков), затем верхний уровень скриптов карты.
4. **Первый сегмент**: после такта потоков вызывается глобальная `OnEnterZone()` (новый поток, раздел 8), флаг сбрасывается.
5. **Загрузка зоны из файла повторного входа** (раздел 15): мир восстанавливается целиком вместе с состоянием Lua; скрипты карты **не** перезапускаются, но флаг «первый сегмент» снова поднимается — поэтому при повторном входе (база!) снова срабатывает `OnEnterZone()`. Скрипты баз пишут логику повторного входа именно в `OnEnterZone`.
6. **Во время игры**: `PlaceTemplate(id, точка)` строит шаблон на лету и запускает скрипты его вариантов (каждый — новый поток, стартует на ближайшем тике).

### Алгоритм: глобальная карта и карта главы
Мир создаётся так же (с библиотеками); затем `RunPostInitScript`: флаг «первый сегмент», запуск одного скрипта из `GlobalMaps.ScriptID` или `ChapterMaps.ScriptID`. Типичный скрипт (90..93): если глобальная переменная кампании «уже был здесь» установлена — `return` с верхнего уровня; иначе `Sleep(10)`, `WaitForUI(ShowHint(47 или 46))`, установить переменную.

### Алгоритм: меню
Главное меню, выбор кампании, экран персонажа — «миры-фоны» из обычных шаблонов карт (варианты 5953 «MainMenu» → скрипт 85, 6000 «SelectCampaign» → 86, 4505/5115 «Axis/AlliesCharScreen» → 15). Их скрипты запускаются тем же `RunPostInit` и общаются с окнами через `OnScriptNotify` (раздел 8). Пока сам мир не сегментирует, интерфейс прокручивает его скрипт каждый кадр (`ExecuteOwnScript`).

### Алгоритм: окно интерфейса со скриптом
При загрузке окна из контейнера с `ScriptID`: создаётся **новое** состояние Lua (без мира, без автозагружаемых библиотек — в нём нет `Common.l`, `TRUE`, `WaitForUI`), к нему привязывается интерфейс окна, скрипт запускается по ID. Тикает при обновлении окна. В данных не используется; пример — скрипт 126 «UI Script» (сетка кнопок, раздел 7.4).

### Алгоритм: консоль
- Строка, начинающаяся с `@`, — исполнить остаток как Lua в текущем скрипте (новый поток, выполнится на ближайшем тике). Строки, начинающиеся с `--`, игнорируются.
- `script_run <ID | имя файла>`: число > 0 — скрипт из таблицы `Scripts`; иначе файл `scripts\<имя>`.
- `script_show all | <имя глобальной>`: дамп глобальных переменных в виде текста Lua и список потоков с размерами стеков.
- `scripterror`: показать последнюю ошибку со стеком вызовов (глубина, файл, функция, строка определения).

### Особые случаи и прихваты
- Автозагрузка читает файлы с диска, а не из ресурсов: моды не могут подменить `Common.l` (только положив файл в папку игры). Релизный `Common.l` (папка `scripts` выпуска) отличается от версии в `Complete\Scripts` (раздел 9).
- Скрипты персонажей (`RPGPers2Scripts`) импортируются в запись персонажа, но нигде не запускаются (в реконструкции; оригинал — не подтверждено).
- Каждый мир — отдельная машина Lua: глобальные переменные миссии не видны на глобальной карте. Для переноса данных между мирами служат «глобальные переменные кампании» (`SetGlobalGameVar`/`GetGlobalGameVar`), хранимые в объекте кампании (раздел 7.8).
- Скрипт карты начинает исполняться **за загрузочным экраном** (во время разогрева); поэтому `DelayGameStart()` в начале скрипта позволяет показать первую сцену так, будто миссия началась уже внутри неё.

### Что нужно от движка-носителя
Отдельный экземпляр VM на каждый «мир»; хук «после построения уровня, до первого кадра» с возможностью прокрутить N сегментов без отрисовки; хук «первый сегмент после входа/повторного входа».

## 5. Триггеры

### Назначение
Простейший механизм «когда условие станет истинным — запусти обработчик». Целиком написан на Lua (`TriggersManager.l`, автозагружается в каждый мир) и сам является бесконечным потоком.

### Данные
Глобальная таблица `triggers` (ключ — порядковый номер), глобальный счётчик `maxTriggerIndex`. Запись: `trigger` (функция-условие), `handler` (функция-обработчик), `latency` (период проверки, по умолчанию **20**), `curLatency` (накопитель, исходно 0), `cycled` (не-nil — многоразовый).

### Алгоритм: регистрация `Trigger(cond, handler, cycled, latency)`
1. `maxTriggerIndex += 1`; создать запись под этим номером; `latency = 20`, если параметр не задан; `curLatency = 0`.
2. Функция ничего не возвращает; отменить триггер можно только присвоив `triggers[i] = nil` (номер нужно вычислить самому).

### Алгоритм: менеджер (верхний уровень файла вызывает `TriggersManager()`, который никогда не возвращается)
Бесконечно:
1. Для каждой пары (номер, запись) таблицы `triggers` в порядке обхода хеш-контейнера:
   1. Пропустить, если номер или запись — `nil` (удалённые записи до сборки мусора ещё видны при обходе).
   2. Если `curLatency ≥ latency`:
      1. Вызвать условие **в потоке менеджера** обычным вызовом.
      2. Если результат не `nil`: `StartThread(handler)` (новый поток в конце списка — стартует в этом же такте). Если триггер одноразовый — удалить запись (`= nil`) и **прервать обход** всех остальных триггеров до следующего прохода.
      3. Если запись не удалена — `curLatency = 0`.
   3. `curLatency += 10`.
2. `Sleep(10)` — один проход в 10 сегментов (0,5 с игрового времени).

### Формулы
Пусть L = `latency`, k = max(1, ⌈L/10⌉). Если условия заканчиваются явным `return`, то:
- первая проверка — на (k+1)-м проходе менеджера (через k×10 сегментов после первого прохода);
- далее проверки каждые k проходов = k×10 сегментов.

При L = 20 (умолчание): первая проверка через 1 с после старта менеджера, затем каждую 1 с. При L = 100 — каждые 5 с. При L ≤ 10 — каждый проход (0,5 с).

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| Период по умолчанию | 20 | «сегментов» между проверками | `TriggersManager.l` |
| Шаг накопителя | 10 | за один проход | `TriggersManager.l` |
| Сон прохода | 10 | сегментов (`Sleep(10)`) | `TriggersManager.l` |

### Особые случаи и прихваты
- За один проход может сработать **не более одного одноразового** триггера: после его срабатывания обход прерывается, и у остальных триггеров в этом проходе не растёт накопитель.
- Многоразовый триггер при истинном условии запускает **новый** поток-обработчик на каждой проверке; одновременно может работать несколько копий обработчика.
- Условие исполняется в потоке менеджера: `Sleep` или долгое ожидание внутри условия останавливает **все** триггеры мира; условие без явного `return` добавляет паузу в один тик.
- Если условие вызывает ошибку (например, юнит удалён и функция движка получила `nil` вместо userdata) — умирает поток менеджера, и **все триггеры мира перестают работать** до перезагрузки. Отсюда в данных повсеместные `IsValid(...)` и функции-обёртки вроде `UnitCanFight`.
- Порядок проверки разных триггеров — порядок хеш-контейнера, а не порядок регистрации.
- Добавление триггера из обработчика безопасно (образец из `Samples\trigger.l`: два триггера по очереди регистрируют друг друга).
- В данных `Trigger` вызывается 10 раз в 7 скриптах; основная логика миссий построена на явных потоках: `StartThread` — 253 вызова, `Sleep` — 712, `WaitForUI` — 345.

### Что нужно от движка-носителя
Ничего: перенести как Lua-библиотеку. При переходе на Lua 5 учесть, что `for k, v in t` → `for k, v in pairs(t)` и что `pairs` не возвращает удалённые ключи.

## 6. Сцены (последовательности) и катсцены

### 6.1. Протокол ожидания команд интерфейса (`WaitForUI`)

**Назначение.** Скрипт живёт в мире, а камера, диалоги, затемнения, «киношные» полосы — в интерфейсе миссии. Скрипт ставит команду в очередь мира и ждёт её завершения по номеру.

**Данные.** У каждой команды интерфейса (`CUICmd`) — номер `nID`, выдаваемый при создании из глобального счётчика (`++счётчик`, начиная с 1). У скрипта — список «ожидаемых номеров» (сохраняется). У мира — FIFO-очередь команд интерфейса (сохраняется).

**Алгоритм.**
1. Функция движка, создающая «ожидаемую» команду (`c_BeginSequence`, `EndSequence`, `CameraMove`, `CameraSequence`, `DialogPlay`, `PlayVideo`, `FadeOut`, `FadeIn`, `ShowHint`), заносит номер в список скрипта, кладёт номер числом в стек Lua как результат и ставит команду в очередь мира.
2. Интерфейс миссии каждый кадр (`ExecWorldCommands`) забирает команды из очереди по одной, пока нет активного «исполнителя» (долгая команда вроде движения камеры занимает исполнителя и блокирует очередь до своего конца). Верхнее окно-«рабочий стол» может отфильтровать команду (`IsValidCommand`); отфильтрованная команда выбрасывается.
3. Когда команда завершилась (камера доехала, полосы появились/исчезли, диалог закрыт, подсказку закрыли, затемнение закончилось), интерфейс кладёт событие «интерфейс: команда N завершена» в очередь событий командира.
4. Мир на ближайшем сегменте разбирает очереди событий всех командиров (до сегментов юнитов) и удаляет N из списка скрипта.
5. Библиотечная `WaitForUI(n)`: если `n == nil` — сразу выход; в релизной `Common.l` также сразу выход, пока поднят флаг «старт задержан» (`G_DelayGameStartFlag`, 6.5); иначе пока номер в списке — `Sleep(2)`.

**Особые случаи и прихваты.**
- `ShowLoseDialog` и `ShowLeaveZoneDialog` регистрируют номер, но не возвращают его скрипту (функция возвращает 0 результатов) — номер навсегда остаётся в списке ожидания (безвредная утечка).
- Если команда не дошла до исполнения (фильтр рабочего стола, неожиданный `EndSequence` без полос) — оригинал номер не освобождает, и `WaitForUI` по нему висит вечно; реконструкция для `EndSequence` освобождает номер (страховка, отклонение).
- Счётчик номеров — статическая переменная, не сохраняется. После загрузки сохранения в новом процессе номера начинаются с 1 и могут совпасть с номерами из сохранённого списка ожидания; совпадение отпустит чужое ожидание раньше времени (не подтверждено, как вёл себя оригинал).
- Шаг опроса 2 тика: ожидание всегда длится не меньше 2 сегментов (100 мс) после фактического завершения, плюс 1 сегмент задержки на событие.

### 6.2. Начало сцены: `c_BeginSequence(bSkipFadeOut = false)` и `BeginSequence(b)`
**Алгоритм (функция движка), строго в этом порядке (по декомпиляции релиза, описанной в комментариях реконструкции):**
1. **Уведомление ИИ**: для каждого юнита, числящегося у командиров ИИ (юниты без игрока, например пустой панцерклайн, пропускаются), — «сцена началась»: сбросить боевую логику, **приостановить** обычный маршрут (патруль, караул, блуждание), очистить старый маршрут сцены (подробно — «ИИ 5», раздел 1). В оригинале — **на каждом** вызове, в том числе вложенном.
2. Мир входит в режим сцены: на стек ходов кладётся «бесхозное» прерывание (по одному на каждый вызов; режим действует, пока не снято последнее) — подробности в «Мир 1», раздел 3. Шаг 1 идёт раньше шага 2 намеренно: пока мир ещё не в режиме сцены, ИИ-юнитам можно менять логику.
3. В очередь интерфейса ставится команда «начать сцену» с номером; номер возвращается.

Реконструкция делает шаг 1 только при переходе глубины вложенности 0 → 1 (счётчик глубины привязан к миру) и добавляет к нему строки, которых в релизе нет: каждому юниту ставится чит «скриптовая сцена» (`CHEAT_SCRIPTSEQUENCE = 16`; в Lua-константах он есть, в релизном исполняемом файле не найден), аниматор переводится в «только дыхание в простое», текущее действие отменяется. См. «Отклонения».

**Обработка в интерфейсе миссии:** счётчик сцен +1; если стал 1 — сохранить текущие ограничения камеры и поставить «киношные» (без ограничений, без автоподъёма над рельефом); текущая поза камеры кладётся в стек поз; поверх создаётся окно «кино» (контейнер 344: чёрные полосы) с плавным появлением (или без него при `bSkipFadeOut`); когда появление закончено — событие с номером.

**Библиотека:** `BeginSequence(b) = WaitForUI(c_BeginSequence(b))`.

### 6.3. Части сцены и пропуск: `EndSequencePart()`
1. `EndSequencePart()` ставит в очередь команду «часть закончена» (без номера); при её обработке интерфейс снимает режим пропуска.
2. Пропуск: пока на экране окно «кино» и полосы ещё не уходят, клавиша «отмена» **один раз на нажатие** включает режим «ждать конца части». В этом режиме интерфейс миссии крутит шаги мира подряд без отрисовки (каждый шаг — полноценный сегмент со скриптами), пока не обработает команду «часть закончена». Диалог, пришедший во время пропуска, не показывается (его номер ожидания сразу освобождается). Если в очереди интерфейса появилась команда главного цикла (загрузка, выход) — перемотка прерывается.
3. Поэтому дизайнер расставляет `EndSequencePart()` как «точки, до которых можно промотать»: каждое нажатие проматывает до ближайшей точки, а `EndSequence` сама ставит «часть закончена» перед завершением.

### 6.4. Конец сцены: `EndSequence(bRestoreCamera = false, bSkipFade = false)`
**Алгоритм (функция движка), строго в этом порядке:**
1. Мир снимает верхнее «бесхозное» прерывание со стека ходов (выход из режима сцены, если оно было последним; в пошаговом режиме ход возвращается владельцу).
2. В очередь: «часть закончена», затем «закончить сцену» с номером (номер возвращается).
3. Немедленный пересчёт видимости мира.
4. **Уведомление ИИ** (в оригинале на каждом вызове; в реконструкции — только при переходе глубины 1 → 0, вместе со снятием чита сцены и режима «только дыхание»): для каждого ИИ-юнита — «сцена закончилась»: сбросить логику, **завершить** маршруты сцены (маршрут сцены никогда не переживает сцену) и **возобновить** обычный маршрут. Уведомление идёт последним, когда мир уже вышел из режима сцены, — чтобы смена логики сработала.

**Обработка в интерфейсе:** если верхнее окно — «кино»: снять позу со стека; при `bRestoreCamera` камера возвращается в позу, снятую при `BeginSequence`; иначе текущая (финальная) поза кинокамеры **становится игровой камерой** активного игрока (камера не «прыгает» назад); на последней сцене восстанавливаются сохранённые ограничения камеры; полосы убираются (мгновенно при `bSkipFade`), по окончании — событие с номером. Если верхнее окно не «кино» — сообщение об ошибке.

**Продолжение маршрута после сцены:** если юнит шёл по скриптовому маршруту, выданному во время сцены, а скрипт хочет, чтобы он дошёл после её конца, нужно вызвать `UnitKeepMoving(u)` сразу после `EndSequence` («ИИ 5», 11.1).

### 6.5. Задержанный старт миссии
Функции движка: `c_DelayGameStartEx()` — «заморозить старт» (флаг мира); `c_StartGameEx()` — снять заморозку. Пока флаг стоит, разогрев мира (раздел 4, шаг 3) продолжает крутить сегменты за загрузочным экраном (каждый +50 мс скрытого времени, не идущего в учёт времени миссии), максимум 9 999 сегментов, после снятия — ещё один сегмент.

Релизная `Common.l`:

| Функция | Тело |
|---|---|
| `DelayGameStartEx()` | `c_DelayGameStartEx()`; `G_DelayGameStartFlag = true` |
| `DelayGameStart()` | `DelayGameStartEx()`; `BeginSequence(true)` — ожидание сразу возвращается (флаг поднят) |
| `StartGameEx()` | `c_StartGameEx()`; флаг = false; `Sleep(1)` |
| `StartGameWithSequence()` | `StartGameEx()` — игра стартует **внутри** сцены |
| `StartGame()` | `StartGameEx()`; `WaitForUI(EndSequence())` |

Пока флаг поднят, любые `WaitForUI` в скрипте возвращаются мгновенно (интерфейс ещё не работает и команды не обработал бы); команды копятся в очереди и исполнятся, когда миссия появится на экране. Типичный шаблон (скрипт 25 «ECom»): `DelayGameStart()` → расстановка юнитов, `CameraSet(...)` → `StartGameWithSequence()` → сцена с `WaitForUnit`, `WaitForUI(DialogPlay(...))` → `EndSequence()`.

### 6.6. Прочие «киношные» команды
`PlayVideo(имя)` — проиграть файл последовательности `.seq` (вставной ролик) с номером ожидания. `FadeOut(r=0, g=0, b=0, мс=1000)` — затемнение в цвет за время, `FadeIn()` — обратное (оба с номером). `CameraMove`, `CameraSequence`, `CameraLock`, `CameraSetClipping`, `Floor` — раздел 7.3. `DialogPlay(code, heroOnLeft=true)` — диалог с номером ожидания; `DialogPlayAsAcks(code)` — те же реплики как «акки» над головами, без окна и ожидания. Библиотечная `DialogPlayWithSequence(id, heroOnLeft)` = `BeginSequence(); DialogPlay(...); EndSequence()` (без ожидания самого диалога — команды исполняются интерфейсом по очереди).

## 7. Каталог функций скриптов

### 7.0. Общие правила функций движка

**Регистрация.** При создании любого скрипта в таблицу глобальных Lua регистрируется единый список из **229** функций (`ScriptFunctions.cpp`, `pRegList`), затем создаются теги 6, 7, 8 и для тега 8 ставятся методы `gettable`/`settable` (доступ `окно.свойство`). Сам список одинаков для мира миссии, меню и окон.

**Строка сигнатуры** проверяется перед выполнением (функция `CheckArgs`), по символу на параметр:

| Символ | Принимает | Результат | Ошибка |
|---|---|---|---|
| `n` | число или строку-число | `float` и `int` (усечение к нулю **через float**) | иначе — «Wrong type of argument N, when calling function F» |
| `s` | строку или число (число превращается в строку) | строка | то же |
| `b` | только число или `nil` | `nil` → ложь, любое число → истина | **строка — ошибка типа** |
| `u` | любую userdata | объект движка из userdata с тегом 6 или 7; если объект уже недействителен (умер) или тег другой — **предупреждение** «Argument N is no more valid» и пустой указатель, без ошибки | не userdata (в т. ч. `nil`) — ошибка типа |
| `o` | любую userdata | «сырой» объект (используется для окон) | не userdata — ошибка |
| `t` | таблицу | — | не таблица — ошибка |
| `.` | дальше что угодно | проверка завершена | — |
| `x[знач]` | параметр необязателен | если не передан — значение из скобок (для `b`: `false` → ложь, любой другой текст → истина; `s[]` — пустая строка) | — |

Если аргументов меньше, чем обязательных параметров, — ошибка «Not enough arguments when calling function F». Лишние аргументы не проверяются. Ошибка проверки = `lua_error` = смерть вызывающего потока (раздел 1). При включённой переменной консоли `lua_showlog` каждый вызов функции движка печатается строкой `LUA(<поток hex>): F( аргументы )` (+ «check failed», если проверка не прошла); userdata печатаются как `Unit[имя]`, `Object[имя]`, `Item[имя]`, `UnitGroup N`, `Route`, `Position[x, y, z]`, `CDBCamera`.

**Возвращаемые значения.** Логические: `1` или `nil`. Ссылки на существующие объекты (юнит, объект, предмет, группа по номеру) — **слабые** userdata (тег 6): не продлевают жизнь объекта. Объекты, созданные самой функцией (новая группа, позиция, команда звука/эффекта, обёртка камеры), — **владеющие** userdata (тег 7): живут, пока на них есть ссылка из Lua, и умирают после сборки мусора. Недействительный объект возвращается как `nil`.

**Приказы юнитам.** Функции, которые «просят юнита что-то сделать», не выполняют действие сразу: приказ кладётся в очередь командира владельца юнита как «установить команду», чаще всего с последующим «продолжить» (продолжить прерванный маршрут/действие). Исполнится на ближайшей выборке приказов командиром (см. «Мир 1», раздел 6). Причина (комментарий релиза): скрипты работают после обновления поз мира, и прямое исполнение видело бы устаревшую позу. Исключения: приказ прямо юниту, минуя очередь командира (`UnitCancelAction`, `UnitStop`, `UnitCheat` — отмена; `DestroyItemInHand` — перемещение предмета «в никуда» + «продолжить»); прямое изменение состояния без приказа (`UnitCreateItem`, `UnitPlaceInPocket`/`UnitRestoreFromPocket`, `UnitHoldItem`, `UnitPlayAnimation` в режиме «простоя», `UnitLockPose`, `UnitSetToHit`, навыки, опыт, перки, критические ранения, `UnitKill`, `KillEmAll`, броски гранат `UnitGrenadeTo*`).

**Долгие функции** — возвращают номер для `WaitForUI` (раздел 6.1): `c_BeginSequence`, `EndSequence`, `CameraMove`, `CameraSequence`, `DialogPlay`, `PlayVideo`, `FadeOut`, `FadeIn`, `ShowHint`. Остальные возвращаются сразу; ожидание выполнения приказа юнитом делается библиотечными `WaitForUnit`, `WaitForUnitRoute` и т. п. (раздел 9).

**Имена точек и объектов.** Путевые точки, юниты, объекты, предметы на земле ищутся по именам, заданным в редакторе (`GetWaypoint`, `GetUnitServer(имя)` …). Ненайденное имя → `nil` и предупреждение в консоль для `GetUnit`, `GetObject`, `GetItem`, `FindItem`.

### 7.7. Шаблоны во время игры

## 8. Обратные вызовы из игры в Lua

### 8.1. Механизм
**Вызов по имени** (`luaCallFunction(имя, параметры)`):
1. Взять текущий скрипт (глобальная ссылка на скрипт мира, выставляемая перед тактом и при создании мира).
2. Создать поток с именем функции, положить в него глобальную функцию с этим именем и аргументы. Если глобальной с таким именем нет или это не функция — **тихо ничего** (пустой поток удалится на ближайшем тике).
3. Создать второй поток «thread made by StartThread», перенести в него функцию и аргументы, начать вызов. Исполнение — на ближайшем тике (если вызов случился во время сегмента — в такте этого же сегмента).
4. Типы аргументов: целое, дробное, строка → числа/строки Lua; объект → **слабая** userdata (недействительный объект → `nil`); «помеченный указатель» → userdata с заданным тегом (окна).

**Вызов через событие** (`CCmdCallScriptFunction`): интерфейс кладёт команду «вызвать функцию F с параметрами» в очередь событий командира (`DoEvent`) или реже в очередь приказов (`Command`). Мир в каждом сегменте (до сегментов юнитов) разбирает очереди событий всех командиров и для такой команды делает «вызов по имени». Команда сохраняется вместе с очередью, поэтому вызов не теряется при сохранении между кадрами.

Следствия: каждый вызов из игры — **отдельный поток**, может спать и ждать; несколько вызовов одной функции работают параллельно (например, `OnShotAtUnit` на каждый выстрел); порядок — порядок возникновения; если в скрипте нет такой функции — событие игнорируется.

### 8.3. Обработчики событий окон
1. `окно.onmessage = f` запоминает в окне пару (скрипт, **индекс замыкания** f). У окна может быть по обработчику от каждого скрипта.
2. Окно перед собственной обработкой событий `notify`, `lbtnup`, `lbtndown`, `lbtndblclk`, `rbtnup`, `rbtndown`, `rbtndblclk` (других нет) для каждого зарегистрированного обработчика: кладёт в **текущий поток** того скрипта вызов f(окно, имя события[, ID для notify]) поверх его кадров и сразу же прокручивает такт этого скрипта. Возврат f игнорируется, событие не поглощается.
3. Прихваты: обработчик выполняется «внутри» текущего потока скрипта — если этот поток спит, обработчик спит вместе с ним и выполнится, когда поток проснётся; индекс замыкания хранится вне Lua и не защищает функцию от сборщика мусора — обработчик должен быть глобальной функцией (иначе индекс может указать на чужой объект).

### 8.4. Проигрыш
1. Интерфейс миссии каждый кадр проверяет: «сценарий провален» или «игрок проиграл» (гибель героя, уничтожение отряда). Срабатывает один раз (защёлка).
2. Провал сценария → событие `OnPlayerLose(1)` сразу.
3. Обычное поражение → отложенный вызов: мир запоминает «вызов `OnPlayerLose(0)`» и крайний срок = сейчас + **4000 мс**. Вызов делается, когда **тело героя перестало двигаться** (рэгдолл остановился), либо по истечении срока — и тогда **в каждом последующем сегменте**, пока мир идёт (запомненный вызов не стирается; ожидается, что скрипт завершит игру окном проигрыша).
4. Релизная `Common.l`: `OnPlayerLose(b)` → `ShowLoseDialog(20985)` при b = 1 («ключевой персонаж погиб, таких надо брать живыми»), иначе `ShowLoseDialog(20984)` («главный герой погиб»).

## 10. Модель базы данных контента

### 10.1. Назначение и источник
Весь «табличный» контент (оружие, персонажи, шаблоны карт, звуки, строки, скрипты, сценарий…) хранится в реляционной базе разработчика `A5GAME` на SQL Server (вход `sa`/`simple`), редактируется собственным редактором и выгружается для игры в `game.db`. Преобразованная копия — `A5GAME.sqlite`: 283 пользовательские таблицы, ~268 тыс. строк; типы столбцов: `int` 1714, `nvarchar` 434, `real` 288, `bit` 129, прочие единичны.

**Соглашения о таблицах:** имя во множественном числе (заканчивается на `s` — проверяется при регистрации); первичный ключ `ID` (целое, задаётся редактором, сквозной внутри таблицы); служебные столбцы редактора `UserName` (имя для людей), `FolderID` (папка в парной таблице `<Имя>Tree`: `ID`, `FolderName`, `ParentID`, `UserColor`), `MEUserColor` (цвет в редакторе). Ссылка на запись другой таблицы — целый столбец с её `ID`, обычно с суффиксом `ID` (`ScriptID`, `TemplateID`), но не всегда (`Background`, `Scenario`, `AckUnit`, `WeaponInHand`). 0 или отсутствующий `ID` — «нет ссылки». Таблицы редактора, которые игра не загружает: `*Tree`, `Paste Errors`, `LUMIGENT_PROFILER`, `dtproperties`, резервные копии (`RPGWeaponsOld`, `RPGWeaponsBefPls`) и др.

### 10.2. Данные: типизированные записи
- На каждую загружаемую таблицу — класс записи с целым `ID`, методом импорта (читает столбцы по именам) и методом сериализации (для отладочного формата `game.db`). Регистрация: номер таблицы (он же идентификатор класса записи), имя таблицы, фабрика. Номера: 1..0x7E для «общих» таблиц (`Models` 1, `Animations` 2, `Textures` 3, `Templates` 4, `TemplVariants` 5, … `Cameras` 88, `AutoLoadScripts` 91, `DifficultyConstants` 98, `TranslatedStrings` 100, `Hints` 0x6D, `RPGAPs` 0x7E) и 0xE0000001..0xE0000028 для RPG-таблиц (`RPGWeaponTypes`, `RPGWeapons` 0xE0000002, `RPGPers` 0xE0000004, `RPGItems` 0xE0000009, `Scripts` 0xE000000C …). Всего ≈150 таблиц.
- Таблица в памяти — хеш-контейнер «ID → владеющая ссылка на запись». Поиск записи по ID; отсутствие → пусто.
- Поле записи-ссылки — указатель на объект записи (в сохранениях игры записывается **как ID**, при загрузке ищется заново, раздел 14.5).
- Типы импорта столбца: целое, логическое (`bit` → целое ≠ 0), дробное (`real`/`float`), узкая строка, широкая строка, ссылка (целое → поиск в таблице назначения), отношение «многие ко многим» (10.6). NULL в исходной базе читается как 0 / 0.0 / ложь / пустая строка.
- **Обратные ссылки** заполняются при импорте самих дочерних записей: вариант добавляет себя в список своего шаблона, экземпляр лута — в список своего сундука, оружие ставит себя «наследником» своего предмета (`pItem->pSuccessor`) и т. д.

### 10.3. Алгоритм: двухпроходный импорт
1. **Проход 1 (оболочки).** Для каждой таблицы в порядке регистрации (импорт из SQL) или в порядке хранения (`game.db`) пройти все строки и создать пустую запись нужного класса с её ID. Загрузить данные всех таблиц-отношений.
2. **Проход 2 (наполнение).** Для каждой таблицы и каждой строки вызвать импорт записи: она читает свои столбцы, и каждая ссылка разрешается в уже существующую оболочку — независимо от того, импортирована ли та запись. Поэтому порядок таблиц не важен для ссылок, но **важен для обратных списков** (порядок вариантов в шаблоне = порядок импорта строк дочерней таблицы).
3. **Достройка связей** (`BuildMapLinks`, раздел 10.7).

Обновление одной таблицы в редакторе (`Refresh`): новые оболочки, но существующие записи с теми же ID **сохраняют свою идентичность** (на них уже ссылаются), затем повторный импорт.

### 10.4. Строки и переводы
- `Strings` (`ID`, `UserName`, `String` — широкая строка, `Comment`): все тексты игры. При импорте из текста удаляются все символы `\r`. Тексты содержат разметку движка: `<br>`, `<font face=… size=…>`, `<center>`, `<color=…>`.
- Остальные таблицы ссылаются на тексты номерами (`NameID`, `DescrID`, `TooltipID`, `BiographyID` …); скрипты — числом (`ShowLoseDialog(20984)`, `SetLeaveZoneMode(false, 20275)`).
- `TranslatedStrings` (`ID`, `String`, `TranslationStatus`: 0 переведено, 1 устарело, 2 утверждено, 3 не переведено, 4 предупреждение): перевод с теми же ID. При выгрузке с ключом `-translate` текст перевода **заменяет** текст `Strings` с тем же ID (отсутствующий ID — ошибка в отладке). Игра при загрузке релизного `game.db` перевод не накладывает (текст уже в `Strings`).
- `AdditionalStrings2Translate` (`StringID`) — список строк для переводчиков; игрой не используется.
- Узкие строковые поля в формате `game.db` хранятся широкими; при импорте каждый символ усекается до байта.

### 10.5. Записи со взвешенным случайным выбором
**Назначение.** Разнообразие без скриптов: «шаблон» модели, материала, эффекта, звука, музыки, освещения, объекта, части здания, сундука и даже карты — это мешок вариантов с весами и условиями; при создании объекта выбирается один.

**Данные.** Запись-шаблон (`ModelTemplates`, `MaterialTemplates`, `EffectTemplates`, `SoundTemplates`, `MusicTemplates`, `AmbientLightTemplates`, `ObjectTemplates`, `ConstructionPartTemplates`, `RPGChestTemplates`, `Templates`) держит список вариантов и «рулетку» — массив накопленных сумм весов, начинающийся с 0. Строка варианта (`Models`, `Materials`, `Effects`, `SoundVariants`, `Musics`, `AmbientLights`, `Objects`, `ConstructionParts`, `RPGChests`, `TemplVariants`) имеет `TemplateID` (свой шаблон), `RndWeight` (вес, дробный) и `Flags` (строка флагов).

**Алгоритм заполнения.** При импорте варианта: если ссылка на шаблон действительна — вариант дописывается в список шаблона, а в рулетку добавляется сектор: `суммы.push(суммы.последняя + вес)`. Вариант без шаблона — ошибка (assert).

**Формат флагов.** Строка из наборов через `;`, в наборе — номера атрибутов (таблица `Attributes`) через `,`. Каждый набор сортируется по возрастанию. Пустой набор допустим (`"1,2;;5"` → {1,2}, {}, {5}).

**Подходит ли вариант к запросу** (запрос — отсортированный список номеров атрибутов, например «ночь», «снег»):
1. У варианта нет ни одного набора → подходит.
2. Иначе подходит, если среди его наборов есть пустой **или** набор, **в точности равный** запросу.
3. Иначе не подходит. (Подмножество не считается: вариант с набором {день} не подойдёт к запросу {день, снег}.)

**Выбор.**
1. Без запроса (или с пустым запросом): `сектор = рулетка.выбрать(rnd)`; вернуть вариант с этим номером.
2. С запросом: собрать подходящие действительные варианты и новую рулетку из **их исходных весов**; выбрать по ней; нет подходящих — «ничего».
3. Пустой список вариантов — «ничего» (assert).

**Рулетка.** Если сумма весов = 0 — всегда вариант 0. Иначе `v = rnd.GetFloat(0, сумма)`; двоичным поиском найти наибольший номер i с `суммы[i] ≤ v` (точнее: сужение интервала `[0, N]` пока `начало + 1 < конец`; середина `с = начало + (конец − начало)/2`; если `v < суммы[с]` — `конец = с`, иначе `начало = с`); ответ — `начало`.

**Генератор для выбора (`SRand`)** — линейный конгруэнтный, как `rand()` MSVC: `seed = seed × 214013 + 2531011` (32 бита), `Get(n) = (((seed >> 16) & 0x7FFF) × n) / 0x8000`; `GetFloat(a, b) = a + Get(0xFFFF) × (b − a) / 0xFFFF`. Конструктор без параметров берёт затравку из системного таймера (мс с запуска Windows) и сразу один раз вызывает `Get(4)`. Для карт сценария затравка задаётся явно (воспроизводимость зоны, «Карта 1»); `PlaceTemplate`, эффекты из скриптов и т. п. берут таймер.

### 10.6. Отношения «многие ко многим»
- Таблица-отношение из двух столбцов `<A>ID`, `<B>ID`. Имена связываемых таблиц выводятся из имён столбцов: отбросить `ID`, дописать `s` (`RPGPerID` → `RPGPers`, `ScriptID` → `Scripts`).
- Данные загружаются как массив пар (A, B). Запись, у которой есть поле-список, при импорте вызывает «собрать отношение»: найти отношение между таблицей записи и таблицей назначения (в любом порядке столбцов) и собрать все записи назначения, парные её ID. Ссылка на несуществующую запись — пропуск (assert).
- Зарегистрировано единственное отношение — `RPGPers2Scripts` (скрипты персонажа). Все остальные связи «многие» в базе сделаны **отдельными таблицами-записями** со своим ID и полями: `RPGWeapon4Pers`, `RPGClip4Pers`, `RPGGrenade4Pers`, `RPGFirstAid4Pers`, `RPGMeleeWeapon4Pers`, `RPGMineDetector4Pers`, `RPGMines4Pers`, `RPGTool4Pers`, `RPGKey4Pers`, `RPGPicklocks4Pers`, `RPGEngGrenade4Pers` (персонаж, предмет, количество, максимум), `RPGItem2Uniforms`, `ScenarioObjective2Clues`, `FaceExpression2Sequences` и т. п.

### 10.7. Достройка связей после загрузки (`BuildMapLinks`)
Выполняется **один раз** после загрузки всей базы (и всех модов), только дописывает в списки — повторный вызов дублирует связи.
1. Анимации: каждая анимация добавляется в список своего скелета по своему типу.
2. Обломки: каждый обломок — в список своего материала обломков.
3. Внешний вид предметов: каждая строка `RPGItem2Uniforms` (предмет, униформа, активная/неактивная модель) — в список «как выглядит» у предмета.
4. Панцерклайны: для каждого персонажа с костюмом — обратная ссылка костюм → персонаж и базовые параметры костюма = базовые параметры персонажа.
5. Только при выгрузке с переводом — наложение `TranslatedStrings` (10.4).
6. Раздача стартового инвентаря персонажей из таблиц `*4Pers` («Бой 2»).

### Особые случаи и прихваты
- Порядок вариантов в шаблоне зависит от порядка импорта строк; при той же затравке другой порядок даст другой вариант. Для бит-в-бит воспроизводимости карт нужен тот же порядок строк, что в оригинальном `game.db`.
- Выбор по флагам требует **точного** совпадения набора; варианты «на все случаи» помечаются пустым набором.
- Таблица `Scripts` хранит код как текст; скрипт — тоже запись, на него ссылаются по ID (шаблон карты, карта главы, глобальная карта, контейнер окна, персонаж).

### Что нужно от движка-носителя
Набор таблиц данных (в UE — `UDataTable`/`UPrimaryDataAsset` с мягкими ссылками по ID), двухфазная загрузка «создать все оболочки → заполнить → достроить обратные списки», собственный ГСЧ `SRand` с той же формулой для воспроизводимости.

## 11. Импорт базы и снимок game.db

### Назначение
Превратить базу SQL в один файл, который игра читает при старте без сервера, и уметь накладывать поверх него частичные файлы модов.

### 11.1. Выгрузчик разработчика (`DataImport`)
Командная строка: `[файл] [-translate] [-dbserver <имя>]`; по умолчанию файл `w:\Complete\game.db`, сервер `a5server`, без перевода. Порядок: подключение по ADO → двухпроходный импорт всех зарегистрированных таблиц (10.3) → достройка связей с переводом или без (10.7) → запись снимка. Этот выгрузчик пишет **типизированный** формат (версия 0): корневой чанк 1 — хеш «номер таблицы → таблица», таблица — хеш «ID → запись», запись — её поля по тегам (с уже достроенными связями). Используется только в отладочных сборках реконструкции.

### 11.2. Релизный формат `game.db` (версия 1, «столбцовый»)
Файл — поток сериализатора (раздел 14) с версией 1, без сжатия (так в релизном файле 34,6 МБ). Содержимое главного чанка:
- **тег 1** — хеш «номер таблицы → владеющая ссылка на хранилище таблицы» (класс 0xA1843130; в релизе 155 таблиц);
- **тег 2** — список отношений: имя таблицы-отношения (2), номер левой таблицы (3), номер правой (4), массив пар (5: число пар + 8 байт на пару). В релизе одно отношение: `RPGPers2Scripts` (0xE0000004 ↔ 0xE000000C, 1 пара).

**Хранилище таблицы** — построчные массивы трёх типов и схема:

| Тег | Содержимое |
|---|---|
| 2 | строки целых: на строку — массив целых (по порядку имён тега 6) |
| 3 | строки дробных (`float`) |
| 4 | строки широких строк |
| 5 | схема столбцов: имя и код типа |
| 6, 7, 8 | имена целых, дробных и строковых столбцов |

Логические столбцы хранятся как целые; `ID` — целый столбец. Узкие строки хранятся широкими.

### 11.3. Алгоритм загрузки
1. Прочитать поток; если версия ≥ 1 — столбцовый путь, иначе — типизированный (11.1).
2. Прочитать хранилища (тег 1) и отношения (тег 2); для каждого отношения найти таблицы по номерам.
3. Проход 1: для каждого хранилища и каждой его строки — если записи с таким ID ещё нет, создать оболочку; **существующая запись не пересоздаётся** (так работают наложения модов).
4. Проход 2: для каждой строки — импорт записи: поле читается по имени столбца из «текущей строки» хранилища; отсутствующий столбец или «пустышка» (12.2) — **поле не меняется**, функция чтения сообщает «нет значения».
5. Если это основная загрузка — достройка связей без перевода (10.7). При загрузке модов — один раз после всех наложений (раздел 12).
6. Запуск игры: показать заставку → добавить папку ресурсов `.\res` → запустить поток загрузки ресурсов → загрузить `game.db` из **текущей папки** (нет файла — сообщение «File game.db not found» и выход) → инициализация графики, звука, ввода → конфигурация (раздел 16).

### Особые случаи и прихваты
- Порядок таблиц при столбцовой загрузке — порядок хеш-контейнера номеров таблиц; порядок строк — порядок хранения. От них зависит порядок обратных списков (10.3).
- В релизном `game.db` столбец `RPGWeapons.DamageMod` записан с **кириллической «о»** (байт 0xEE в имени), а в базе разработчика ноября 2003 — латиницей. Импорт по латинскому имени его не находит, и модификатор урона оружия остаётся значением по умолчанию. Как читал этот столбец релизный исполняемый файл — не установлено (см. «Не установлено»).
- Моды старого образца (`Samplemod`, `TestMod`) записаны без чанка версии (версия 0), но уже в столбцовом формате; загрузчик реконструкции по номеру версии пошёл бы по типизированному пути.

### Что нужно от движка-носителя
Конвертер «таблицы → ассеты» с сохранением ID; при желании поддерживать оригинальные моды — читатель столбцового формата (раздел 14 + хранилище таблицы).

## 12. Моды

### Назначение
Позволить сторонним авторам менять отдельные **ячейки** базы и отдельные **файлы** ресурсов, не трогая файлы игры, и сочетать несколько модов.

### 12.1. Данные
- **Мод** — подпапка в папке игры, содержащая `description.txt` (весь текст файла — отображаемое имя мода; кодировка системная, пример: «Тестовый mainmenu»). Папка без этого файла модом не считается.
- В папке мода: `game.db` (частичная база того же формата, раздел 11) и/или ресурсы: пакеты `<Тип>.res` и/или «россыпью» `<Тип>\<номер>`.
- Состояние менеджера (только в памяти): список активных модов (имя, папка) и **номер версии базы**, увеличиваемый при каждой активации (кэши, построенные по базе — таблица простоев голов, список персонажей генератора, — сравнивают этот номер и перестраиваются).
- Новые записи модов в примерах имеют ID от **1 000 001** (`Samplemod`: `RPGItems` 1000001 «MP43», `UITextures` 1000002, стартовые зоны 1000001/1000006) — соглашение редактора модов, движок его не проверяет.

### 12.2. Наложение базы с «пустышкой» 0xFDFDFDFD
Частичный `game.db` мода содержит только нужные таблицы и строки, но **все столбцы** таблицы. Ячейки, которые мод не меняет, заполнены «пустышкой»:

| Тип столбца | Пустышка |
|---|---|
| целый, логический | 0xFDFDFDFD (−33 686 019) |
| дробный | число с битами 0xFDFDFDFD (≈ −4,22·10^37) |
| строковый | текст `"fdfdfdfd"` |

Чтение поля при импорте: столбца нет → «нет значения»; значение равно пустышке → «нет значения»; иначе записать. «Нет значения» означает, что **поле записи сохраняет прежнее значение** (из базы игры или предыдущего мода); у ссылок — тоже (ссылка не обнуляется). Строка с ID, которого ещё нет, создаёт новую запись (неуказанные поля — значения по умолчанию класса). Существующая запись не пересоздаётся — все ссылки на неё остаются действительными.

### 12.3. Алгоритм активации (`Activate(список модов)`)
1. Если активных модов нет и новых не просят — ничего.
2. Для каждого мода проверить, что `description.txt` открывается; хотя бы один не открылся — вернуть «неудача», **ничего не трогая**.
3. Разрушение: очистить очередь удержания графа зависимостей, дождаться загрузчика и закрыть все пакеты ресурсов (сбросить кэши «есть ли файл»), очистить список папок ресурсов, удалить все записи и отношения базы (остаются пустые таблицы).
4. Загрузить основной `game.db` из текущей папки (без достройки связей). Ошибка — окно «File game.db not found», «неудача» (база при этом уже пуста).
5. Добавить папку ресурсов `.\res`.
6. Для каждого мода **в порядке списка**: наложить `<папка>\game.db` (ошибка чтения проглатывается — база мода пропускается) и **в любом случае** добавить папку мода в список папок ресурсов.
7. Один раз достроить связи (10.7).
8. Номер версии базы += 1; запомнить список активных модов; «успех».

Позже стоящий в списке мод перекрывает раньше стоящий — и в базе (последняя запись поля побеждает), и в ресурсах (12.4).

### 12.4. Перекрытие ресурсов
Список папок ресурсов: `.\res`, затем папки модов в порядке активации. Поиск файла ресурса «тип T, номер N» (раздел 13):
1. «Россыпью»: папки просматриваются **с последней до второй**; первый существующий файл `<папка>T\N` побеждает. Если ни в одной — используется путь в первой папке (`.\res\T\N`), даже если файла нет.
2. Если файл «россыпью» существует — берётся он (россыпь важнее пакета; так работали обновлённые файлы патча 1.2).
3. Иначе пакеты `<папка>T.res` всех папок (собираются один раз и кэшируются) просматриваются с последнего до первого; первый пакет, в оглавлении которого есть N, отдаёт файл.
То есть мод может заменить **один файл** пакета, положив свой маленький `T.res` только с этим номером или файл `T\N`.

### 12.5. Где выбираются моды и как их помнят сохранения
- Меню «своя игра» (Custom game): слева активные, справа доступные (найденные подпапки с `description.txt`); активные, которых уже нет на диске, не показываются. «Применить» → активация списка слева в его порядке → главное меню. При запуске игры модов нет (список не сохраняется в конфигурации).
- Сохранение пишет в заголовок число активных модов и их **папки** (раздел 15). Загрузка сначала активирует этот набор (строковая форма: папки без `description.txt` **молча выбрасываются** — сейв с удалённым модом загрузится без него), затем читает игру.

### Особые случаи и прихваты
- Наложение строки варианта случайного выбора (10.5), уже существующего в базе, **повторно добавляет** его в список шаблона и в рулетку (импорт варианта всегда дописывает) — вариант начинает выпадать чаще. Оригинал — не подтверждено.
- Если в `game.db` мода есть чанк отношений, он **заменяет** весь список отношений базы; записи, импортируемые после этого, соберут отношения только из списка мода. Если чанка нет — список не трогается.
- Мод не может удалить запись или ячейку (только переписать).
- Скрипты автозагрузки (`scripts\*.l`) мод заменить не может — они читаются с диска из папки игры (раздел 4).

### Что нужно от движка-носителя
Слой «переопределений» данных по ключу (таблица, ID, столбец) поверх базовых ассетов с поддержкой «не задано»; виртуальная файловая система с приоритетом папок модов и подменой отдельных файлов пакета; сохранение списка модов в заголовке сохранения.

## 13. Ресурсы: адресация, пакеты, поток загрузки

### Назначение
Тяжёлые данные (геометрия, текстуры, анимации, звуки, рельеф, здания, заранее посчитанные данные ИИ) лежат не в базе, а в файлах ресурсов; запись базы ссылается на ресурс своим ID. Загрузка — фоновая и ленивая.

### 13.1. Адресация
- Ресурс = (**тип**, **номер**). Тип — имя «полки»: `AIBSPTrees`, `AIBinds`, `AIGeometries`, `Animations`, `Binds`, `Buildings`, `Chapters`, `Effects`, `Fonts`, `Geometries`, `Globals`, `Groups`, `Heads`, `LRTextures`, `Lights`, `Locators`, `Sequences`, `Skeletons`, `Sounds`, `Terrain`, `Textures`, `Units`, `Waypoints`. Номер — обычно `ID` записи базы (геометрии, текстуры, варианта шаблона…).
- Составной ключ (номер записи, часть): номер файла = `ID + (часть << 16)`. Так хранятся части одной геометрии по слотам материалов (`Geometries`, часть 0, 1, … — «есть ли часть N» проверяется перед созданием).
- Файл ресурса чаще всего — поток сериализатора (раздел 14), читаемый по тегам.

### 13.2. Формат пакета `.res`

| Смещение | Содержимое |
|---|---|
| 0 | сигнатура: 0x95938921 (разработка) или 0x96948A22 (релиз: каждый байт +1, «версия 1») |
| 4 | смещение оглавления |
| 8 … | данные файлов подряд |
| оглавление | поток сериализатора (без сжатия): тег 1 — хеш «номер файла → (начало, длина)», тег 2 — даты изменения исходных файлов (только у пакетов, обновлённых упаковщиком) |

Упаковщик (`PkgBuilder`) обновляет пакет **инкрементально** из папки с файлами, названными десятичными номерами: неизменённый (по дате) файл пропускается; изменённый, если помещается на старое место (новая длина ≤ старой), пишется туда же, иначе — в конец данных; файлы, исчезнувшие из папки, удаляются из оглавления (место не освобождается); оглавление переписывается после данных. Нечисловые имена файлов игнорируются с сообщением.

### 13.3. Алгоритм поиска файла
Список папок ресурсов: `.\res` (добавляется при запуске), далее папки активных модов (раздел 12). Для (T, N):
1. Путь «россыпью»: перебрать папки с последней до второй, первый существующий `<папка>T\N` — ответ; если нет — `<первая папка>T\N`.
2. Если файл по этому пути существует — читать его (россыпь важнее пакетов).
3. Иначе — пакеты: для имени T один раз собираются пакеты `<папка>T.res` всех папок (каждый открывается и читает оглавление; пакет `LRTextures` целиком читается в память); перебор с последнего пакета до первого, первый, где есть N, отдаёт файл (поток с собственным смещением и длиной, буфер чтения 1024 байта).
4. Нигде нет — попытка открыть путь россыпью (ошибка чтения).
Проверка «существует ли ресурс» (используется, например, для частей геометрии) в игре смотрит **только пакеты** (в редакторе — и россыпь); кэшируется трекером на тип, сбрасывается при закрытии ресурсов.

### 13.4. Поток загрузки
1. При запуске создаётся один фоновый поток (стек 100 КБ).
2. Ленивый загрузчик ресурса при первом обращении создаёт «запрос файла» и ставит его в очередь; запрос удерживается списком удержания, пока очередь не опустеет.
3. Очередь работает **стеком (LIFO)**: новый запрос ставится в начало и поток берёт из начала — первым читается самый свежий запрос (то, что нужно кадру прямо сейчас).
4. Поток спит на событии; проснувшись, читает запросы по одному: весь файл (россыпью или из пакета) в память; по готовности помечает запрос.
5. Основной поток при очередном обращении видит «готово» и разбирает данные (в основном потоке); запрос отпускается.
6. «Есть ли запросы в полёте» — для экрана загрузки; «дождаться всех» — активное ожидание с `Sleep(0)` (перед закрытием ресурсов при активации модов).
7. Остановка: в начало очереди кладётся пустой запрос — поток выходит.

### 13.5. Общие кэши ресурсов в сохранениях (`BasicShare`)
- Загруженные ресурсы держатся в кэшах «ключ → объект-загрузчик»; у каждого кэша свой номер (например, 121 — геометрия, 122 — части геометрии; номер ≤ 255, т. к. он служит тегом чанка). Повторный запрос по ключу отдаёт тот же объект; недействительный объект пересоздаётся.
- Сохранение пишет все кэши в корень потока (тег = номер кэша), а загрузчик ресурса сохраняет **только ключ**. При чтении сначала все текущие объекты кэшей удерживаются; затем кэш читается; для каждого ключа, который уже был загружен до чтения, содержимое старого объекта копируется в новый — ресурсы не перечитываются с диска. Остальные догрузятся лениво.
- Объекты «предзагрузки», прочитанные из сохранения, регистрируются и обновляются на ближайшем кадре (`LoadPrecached`).

Виртуальная ФС с несколькими корнями (база + моды) и пофайловой подменой; асинхронная загрузка с приоритетом последних запросов; кэш загруженных ресурсов по ключу, переживающий загрузку сохранения.

## 14. Сериализатор

### Назначение
Один механизм для сохранений, файлов зон, `restart.sav`, `game.db`, файлов ресурсов и оглавлений пакетов: сохранить произвольный граф объектов с указателями и прочитать его, переживая добавление и удаление полей в классах.

### 14.1. Модель объектов и ссылок
- У каждого сохраняемого объекта два счётчика: **владельцев** и **ссылок**. Счётчик владельцев устроен как битовое поле: владеющий указатель `CObj` добавляет 1 (младшие 20 бит), «совладеющий» `CMObj` — 0x100000 (биты 20..30); бит 31 — флаг «объект недействителен». Слабый указатель `CPtr` увеличивает счётчик ссылок.
- Освобождение владельца: если после вычитания владельцев (без флага) и ссылок не осталось — объект удаляется. Если остались только ссылки, а владельцев данного вида (маска 0x000FFFFF для `CObj`, 0x7FF00000 для `CMObj`) больше нет — объект **становится недействительным**: выставляется флаг, его содержимое уничтожается и заменяется состоянием «только что создан» (деструктор + конструктор по умолчанию на том же месте), память живёт, пока на неё есть слабые ссылки. Освобождение последней слабой ссылки при нуле владельцев — удаление.
- Итог: слабая ссылка **никогда не висит** — она указывает либо на живой объект, либо на «пустой недействительный»; проверка `IsValid(p)` = не пусто и флаг не стоит. На этом держатся и скрипты (`IsValid(unit)` в Lua), и сохранения.
- Удаления внутри удаления откладываются в очереди «удалить»/«обнулить» и выполняются по окончании внешнего, без рекурсии.

### 14.2. Реестр классов
Каждый сохраняемый класс регистрируется с постоянным 32-битным номером (`REGISTER_SAVELOAD_CLASS(номер, класс)`), например: скрипт 0x70652130, поток Lua 0x70813170, параметр вызова Lua 0x51822131, позиция Lua 0x52122170, обёртка камеры 0x52302140, хранилище таблицы базы 0xA1843130, команда интерфейса 0xB1011160, «начать сцену» 0xB3115171, «закончить сцену» 0xB3115172, «часть закончена» 0x53115170, «вызвать функцию скрипта» 0x51822130. Реестр: номер → фабрика, тип → номер (поиск по точному типу объекта). Номер неизвестного класса при чтении → объект не создаётся, ссылки на него станут пустыми, чтение продолжается.

### 14.3. Чанки
Поток — последовательность чанков: **1 байт номера** (тег), затем длина: если `длина × 2 < 256` — 1 байт со значением `длина × 2` (младший бит 0), иначе 4 байта `длина × 2 + 1` (младший бит 1), затем данные. Чанки вложенные: данные чанка сами являются последовательностью чанков либо «сырыми» байтами. Тег 0 зарезервирован системой. Повторяющиеся чанки с одним тегом нумеруются по порядку появления (1, 2, …) — так пишутся элементы контейнеров.

### 14.4. Единая функция «туда-обратно»
У каждого класса одна функция `operator&(сериализатор)`, перечисляющая поля: `Add(тег, &поле[, номер])`. При записи она дописывает чанк; при чтении ищет в текущем уровне чанк с этим тегом и номером (с кэшем «следующий по порядку» для последовательного чтения, иначе линейный поиск) и читает его. Правила:

| Вид поля | Запись |
|---|---|
| Простое значение без собственной функции сериализации | сырые байты размера типа (1 чанк) |
| Объект с функцией сериализации | вложенный чанк с полями объекта |
| Базовая часть класса | по соглашению `Add(1, (База*)this)` |
| Строка | байты без завершающего нуля; широкая — по 2 байта на символ |
| Вектор простых значений | чанк 1 — число элементов (int), чанк 2 — весь массив сырыми байтами |
| Вектор, список прочих | по чанку с тегом 1 на элемент, номера 1..N; при чтении размер = число таких чанков |
| Вектор `bool` | число + по байту на элемент |
| Хеш-контейнер | ключи — чанки 1 (номера 1..N), значения — чанки 2 (номера 1..N) |
| Двумерный массив | размер X (1), Y (2), данные (3) |
| Указатель на объект (`CPtr`/`CObj`) | 4 байта — адрес объекта на момент записи (0 — пусто) |
| Ссылка на запись базы | ID записи (тег 1), −1 — пусто; при чтении запись ищется в загруженной базе |

**Терпимость к изменениям классов:** отсутствующий при чтении чанк простого поля → поле **обнуляется**; отсутствующий чанк составного поля → поле не трогается (остаётся значение конструктора); лишние чанки, которых класс не читает, игнорируются; несовпадение размера простого поля — в отладке assert, в релизе копируется ожидаемое число байт. Поэтому новые поля добавляют с новыми тегами, а удалённые просто перестают читать.

### 14.5. Указатели и порядок
**Запись:**
1. Корневые поля пишутся в «главные данные». Встреченный указатель на ещё не записанный объект ставит объект в очередь (FIFO) и запоминается как записанный.
2. В конце очередь обрабатывается: для каждого объекта в таблицу объектов пишется (номер класса, адрес, «действителен» — 9 байт), а в «данные объектов» — чанк 1 с номером объекта, внутри — чанк 0 (адрес) и чанк 1 (поля объекта). Новые встреченные указатели дописываются в очередь.

**Чтение:**
1. По таблице объектов создаются **все** объекты (пустыми, через реестр); «недействительные» создаются и тут же переводятся в недействительное состояние; запоминается соответствие «старый адрес → новый объект».
2. Для каждого объекта по порядку читаются его поля; указатели переводятся через соответствие (несуществующий адрес — пусто, assert).
3. Только после этого читаются корневые поля из «главных данных».
Следствие: при чтении объект может ссылаться на объекты, чьи поля ещё не прочитаны, — функции сериализации не должны пользоваться содержимым других объектов.

### 14.6. Файл
Порядок чанков верхнего уровня при записи: **4** — версия формата (int, всегда без сжатия; сейчас 1), **1** — главные данные, **0** — таблица объектов, **2** — данные объектов, **3** — метка `"A3\0"`, если чанки 0, 1, 2 сжаты (каждый своим независимым сжатием). Чтение ищет чанки по номеру, порядок не важен; отсутствие чанка 4 → версия 0. Чанк верхнего уровня длиннее 100 000 000 байт считается испорченным. Версия доступна классам (так, «ячейка» интерфейса в версии 1 хранит состояние подсветки).

### 14.7. Сжатие (LZ с битовыми кодами)
Упакованный чанк: `[u32 исходная длина]` + битовый поток. Биты пишутся младшим вперёд в байт, **вставленный в поток в момент записи первого бита** очередной восьмёрки; обычные байты пишутся в поток следом (схема «байт флагов среди данных»). Распаковка (окно — кольцо 1024 байта, курсор с 0):
1. Пока осталось > 0: прочитать бит.
2. Бит 0 — литерал: следующий байт потока → вывод и в кольцо.
3. Бит 1 — повтор: длина L и смещение D по кодам ниже; скопировать L байт из кольца с позиции `(курсор − D − 1) & 0x3FF` (побайтно, с перекрытием), не больше оставшегося.

Длина L (биты читаются по одному слева направо; «Nb» — N-битное число младшими битами вперёд):

| Биты | L |
|---|---|
| `0 0` | 2 |
| `0 1` | 4 |
| `1 0 0 0` | 3 |
| `1 0 0 1` + 3b | 11 + x |
| `1 0 1` + 2b | 7 + x |
| `1 1 0 0` | 5 |
| `1 1 0 1` + 6b | 35 + x |
| `1 1 1 0` | 6 |
| `1 1 1 1 0` + 4b | 19 + x |
| `1 1 1 1 1` + 7b | 99 + x |

Смещение D:

| Биты | D |
|---|---|
| `1 1` + 10b | 354 + x |
| `1 0` + 12b | 1378 + x |
| `0 1 1` + 8b | 98 + x |
| `0 1 0` + 6b | 34 + x |
| `0 0 0 1` + 2b | 2 + x |
| `0 0 0 0` + 3b | 10 + x |
| `0 0 1 0` + 2b | 6 + x |
| `0 0 1 1 1` + 1b | x (0 или 1) |
| `0 0 1 1 0` + 4b | 18 + x |

Упаковщик: хеш пары соседних байтов `(пред × 4) xor байт` → цепочки по кольцу; совпадение ищется на расстояниях < 0x31E (798), максимальная длина совпадения 0xE2 (226), минимальная 2. Для чтения оригинальных сохранений достаточно распаковщика; формат сжатия при записи может быть любым, если читает только ваш движок.

### 14.8. Строки в потоках (вне чанков)
Длина: < 128 — 1 байт (`длина × 2`), иначе 4 байта (`длина × 2 + 1`); затем байты. Используется для списка модов в заголовке сохранения.

### Особые случаи и прихваты
- Указатели пишутся как 32-битные адреса; формат привязан к 32-битной сборке (на 64 битах нужен иной ключ объекта, например порядковый номер).
- Объекты пишутся в порядке обнаружения (FIFO), поэтому один и тот же мир в разные моменты даёт разный порядок таблицы объектов — сравнивать сохранения побайтно бессмысленно.
- В реконструкции при чтении добавлены диагностика «аудит расхождения полей» и защита от повторного освобождения при разборе таблицы объектов (отладочные средства, не поведение оригинала).

### Что нужно от движка-носителя
В UE — собственный архив поверх `FArchive` с тегированными полями (или `FStructuredArchive`) + таблица объектов «старый ID → новый объект» с отложенной фиксацией ссылок; слабые ссылки «никогда не висят» (`TWeakObjectPtr` даёт похожее поведение — становится недействительной).

## 15. Сохранения

### 15.1. Что сохраняется
Сохранение — сериализация (раздел 14) **всего стека интерфейсов** главного цикла (список экранов: например, «глобальная карта» → «миссия» → открытое поверх меню) плюс общих кэшей ресурсов. Всё остальное достаётся по ссылкам: у миссии — мир (юниты, объекты, обломки, мины, ИИ, командиры с очередями приказов и событий, очередь команд интерфейса, скрипт Lua со всеми потоками), камера и стек её поз, окна-«рабочие столы» (полосы сцены, диалог, затемнение), список звуков, счётчики времени; у всех — объект кампании (сценарий, улики, зоны, игроки и деньги, показанные подсказки, глобальные переменные кампании, сложность). Записи базы сохраняются только номерами. Сам `game.db`, ресурсы и скрипты автозагрузки не сохраняются.

Никакой «переинициализации» после загрузки в оригинале нет: интерфейс получает только уведомление «загружено» (полоса загрузки), пошаговое состояние продолжается как было сохранено (ход не перезапускается). Реконструкция дополнительно перестраивает кэши, которые она не сохраняет (оболочки зданий, источник высоты для камеры, связи командиров ИИ) — отклонение.

### 15.2. Папки

| Путь | Что |
|---|---|
| `temp\` (в папке игры) | Рабочий «активный слот»: файлы зон для повторного входа `<ID зоны>_<ID шаблона>.sav`, снимок `restart.sav`. Создаётся при запуске, **удаляется при нормальном выходе**, очищается при начале новой кампании. |
| `save\<профиль>\` | Профиль игрока (имя — переменная `game_profile`, по умолчанию `default`). |
| `save\<профиль>\<слот>\` | Слот: `game.sav` + **копия всех файлов `temp\`** на момент сохранения. |

Профиль: если имени из переменной нет среди папок `save\*`, берётся первая найденная папка; если папок нет — создаётся профиль по умолчанию. Список слотов — подпапки профиля, кроме `temp`. Имя слота не может содержать `.<>\/|"*^:?`; зарезервированы локализованные имена строк 20241 «QuickSave(1)», 20242 «QuickSave(2)», 20243 «AutoSave(Begin mission)», 20244 «AutoSave(End mission)» (пользователь не может назвать так свой слот).

### 15.3. Формат `game.sav`

| Часть | Размер | Содержимое |
|---|---|---|
| Метка | 4 | 0x828CA022 (v1.x; при чтении принимается и старая 0x818B9F21 — формат тот же) |
| Число модов | 4 | N |
| Снимок экрана | 320 × 200 × 4 = 256 000 | RGBA, уменьшенный билинейно снимок на момент постановки команды сохранения |
| Папки модов | N строк | строки формата 14.8 |
| Поток | остаток | сериализатор со сжатием: корневой тег 2 — список интерфейсов; затем общие кэши |

Время слота (для списка и быстрых сохранений) — время изменения файла `game.sav`; в списке показывается дата в порядке, заданном региональными настройками Windows (день/месяц/год, месяц/день/год или год/месяц/день), и время.

### 15.4. Алгоритм сохранения в слот
1. Проверить имя (запрещённые символы → сообщение, отказ).
2. Снимок экрана берётся **в момент постановки** команды (а не исполнения).
3. Если не «тихое» — показать заставку «сохранение» (контейнер 349) со снимком.
4. Слот: удалить папку слота, создать заново, скопировать в неё все файлы `temp\`.
5. Записать `game.sav` (15.3) прямо в папку слота.
6. В журнал игры — строка 20259 («игра сохранена»), только при успехе.

### 15.5. Алгоритм загрузки слота
1. Проверить имя; показать один кадр экрана загрузки (если не «тихо»).
2. Прочитать заголовок; неизвестная метка → отказ.
3. Прочитать папки модов и активировать этот набор (раздел 12; отсутствующие папки выбрасываются). Неудача активации → отказ, текущая игра не тронута.
4. Очистить стек интерфейсов, удержать объекты общих кэшей, прочитать поток (стек интерфейсов + кэши).
5. Слот → `temp\`: удалить `temp\`, скопировать туда все файлы слота (файлы зон и `restart.sav` этого сохранения становятся рабочими).
6. В журнал — строка 20260.
Любая ошибка чтения (исключение) прерывает загрузку до шага 5.

### 15.6. Быстрое сохранение, автосохранения, разрешения
- **Быстрое сохранение** пишет в **более старый** из слотов QuickSave(1)/(2), **быстрая загрузка** читает **более новый** — два слота чередуются. Сравнение: ключ даты = `((год × 12 + месяц) × 31 + день) × 24 + час` (год с 1900, месяц 0..11); при равенстве — ключ времени = `минуты × 3660 + секунды` (необычный множитель сохранён из оригинала). Если слот отсутствует, его ключи 0 (он «старше»). Запуск с ключом `-load` — загрузка более нового быстрого слота.
- **Автосохранение «начало миссии»** (20243): переход с карты главы/глобальной карты в миссию выполняется как пара команд [сохранить, начать миссию], если переменная `game_autosaves` ≠ 0 (по умолчанию 1). Сохраняется состояние **до** перехода (карта главы).
- **Автосохранение «конец миссии»** (20244): подтверждение «покинуть зону» **всегда** выполняет [закрыть окно, сохранить со снимком, конец миссии → `OnRealExit`] — независимо от `game_autosaves`.
- **Разрешение сохранять** (пересчитывается в миссии каждый кадр): на базе — всегда; иначе по полю `CanSave` сложности: `chapter` — нельзя, `realtime` — только в реальном времени и не во время сцены, `always` — всегда. В базе: Easy — `always`, Normal и Hard — `realtime`. Запрещённое быстрое сохранение печатает строку 19881; меню сохранения открывается сразу в режиме загрузки.

### 15.7. Файлы зон (повторный вход)
1. **При уходе из миссии** (`Terminate`): если мир — база, или «связанная» зона из нескольких шаблонов, или скрипт вызвал `EnableFeature("reenter")` — убрать из мира тела, которые несут уходящие бойцы, убрать игроков отряда, затем записать мир в `temp\<ID зоны>_<ID шаблона>.sav` (поток со сжатием: корневой тег 2 — мир, затем кэши; старый файл предварительно удаляется со снятием атрибутов; ссылка скрипта на интерфейс на время записи отвязывается).
2. **При входе в миссию**: попытаться прочитать этот файл; если он есть — мир восстанавливается (привязывается к текущей кампании, обновляются здания), скрипты карты **не** запускаются, но в первом сегменте снова вызывается `OnEnterZone()`; если нет — мир строится заново по случайному зерну зоны.
3. Файлы зон живут в `temp\`, поэтому переносятся между слотами вместе с сохранениями и пропадают при начале новой кампании.

### 15.8. `restart.sav`
1. В конце инициализации миссии в очередь главного цикла ставится команда «снимок перезапуска»: она выполнится **после** того, как новая миссия установлена в стек интерфейсов, и запишет весь стек в `temp\restart.sav` (без заголовка, без снимка экрана, без списка модов, со сжатием); затем завершает инициализацию (сбрасывает накопленный за загрузку ввод).
2. «Перезапустить миссию» (игровое меню, если перезапуск разрешён; меню проигрыша) — заменить стек интерфейсов содержимым `restart.sav` без подтверждения; моды и `temp\` не трогаются.
3. `restart.sav` копируется в слот при каждом сохранении, поэтому после загрузки сейва «перезапуск» возвращает к началу **той** миссии.

## 16. Консольные команды, переменные и конфиг-файлы

### Данные
Глобальный реестр «имя → запись»: список обработчиков-команд, список обработчиков-переменных, текущее значение, значение по умолчанию (первое зарегистрированное), признак «сохранять в конфиг». Значение хранит одновременно число (`float`) и строку: из числа строка получается форматом `%.2f` (поэтому в конфиге `0.10`, `1.00`), из строки число — разбором как десятичного.

### Алгоритм: строка консоли
1. Пустая строка или начинающаяся с `--` — пропуск; начинающаяся с `@` — Lua (раздел 4).
2. Разбить на слова по пробелу, табуляции и `\r`; внутри скобок `()`, `[]`, `{}` и кавычек `""` пробелы не делят.
3. Первое слово — имя. Нет в реестре — «Unknow command name'…'» и подсказка `help`.
4. Есть обработчики-команды — вызвать все по порядку регистрации. Нет — поведение «переменной»: без аргументов печатать `имя string = '…' float = '…'`, с аргументом — установить значение первым словом (вызвав все обработчики-переменные).
5. Встроенные: `help` (все имена по алфавиту), `exec <файл…>` (выполнить файлы), `setvar <имя> = <значение>`.

### Конфиг-файлы
- Выполнение файла: разбить по строкам, отбросить пустые, обрезать `\r\n`, пропустить строки, начинающиеся с `;` или `//`, остальное — как строки консоли.
- Запуск: `.\cfg\autoexec.cfg` (релиз: `gfx_autodetect`, `exec .\cfg\input.cfg`, `exec .\cfg\config.cfg`, затем пользовательские настройки камеры), затем ключи командной строки (`-windowed`, `-fullscreen`, `-800` и т. п., `-nosound`, `-noai`, `-load`, `-cfg <файл>`), затем стартовый файл `start.cfg` (или из `-cfg`) — его исполняет первый экран; в релизе: `sequence .\cfg\intro.seq`.
- Выход: `.\cfg\config.cfg` перезаписывается: три строки комментария («generated by S^2, do not modify») и `setvar <имя> = <значение>` для всех переменных с признаком «сохранять», **по алфавиту**.
- Файлы последовательностей `.seq` (используются `sequence` и `PlayVideo`): строки `play <файл .bik>` и `exec <команда консоли>`; например `intro.seq`: четыре ролика логотипов и вступления, затем `exec mainmenu`; `loose.seq`: ролик провала и главное меню; `win.seq`: финальный ролик и `exec credits final`.

## Все прихваты списком

**Виртуальная машина Lua**
- Все объекты Lua — номера ячеек в пяти массивах состояния; ссылки — номера; строки интернированы и никогда не собираются.
- Вызов Lua-функции — запись в явный стек кадров потока, без рекурсии C; поэтому поток можно сохранить посреди любой функции.
- Неявный конец любой Lua-функции (без `return`) отдаёт управление до следующего тика.
- `return f(...)` с Lua-функцией f не исполняет f и возвращает `nil`; все библиотеки пишут `local a = f() return a`.
- Синхронные вызовы (методы тегов, сборщик) игнорируют `Sleep`.
- `Sleep(n)` = n тиков (сегментов по 50 мс); дробь отбрасывается; `Sleep(0)`, `Sleep(0.5)` — без паузы; без аргумента — 1.
- Потоки исполняются в порядке создания; поток, созданный в такте, стартует в этом же такте.
- Вызов из игры в Lua — всегда новый поток, отложенный до тика; нет функции — тихо ничего.
- Ошибка Lua убивает только текущий поток; неверный тип аргумента функции движка — тоже ошибка.
- Нет стандартной библиотеки Lua (ни `tostring`, ни `getn`, ни `floor`); `Floor(n)` — это этаж камеры.
- Двоичные (предкомпилированные) чанки не поддерживаются.
- `t[k] = nil` оставляет ключ с `nil` до сборки мусора; обход таблицы видит такие ключи.
- Порядок обхода таблиц — порядок хеш-контейнера.
- Сборка мусора — каждые 1000 проверок (вызовов/созданий), не по памяти.
- Одна и та же сущность движка упаковывается в одну и ту же userdata (линейный поиск), поэтому `==` работает для одинаковых слабых ссылок; слабая и владеющая — не равны.
- Чтение глобальной `nil` печатает предупреждение, кроме имени `FALSE` (`false` — печатает).
- `TRUE = 1`, `FALSE = nil`, `true = 1`, `false = nil` — глобальные переменные, а не ключевые слова.
- Целые аргументы функций движка проходят через `float` (точность 2^24).
- Параметр `b` принимает только число или `nil`; строка — ошибка.
- Параметр `u` с умершим объектом — только предупреждение и пустой указатель.
- `random()` без аргументов = 0; `random(a, b)` не включает b; `random(0)` — деление на ноль.

**Сохранение Lua**
- Сохраняются байт-код, все потоки со стеками (вся ёмкость стека), счётчики сна; после загрузки скрипты не перезапускаются.
- C-функции сохраняются по глобальному имени регистрации; переименование ломает старые сейвы.
- Имя файла-источника прототипа не сохраняется.

**Скрипты и события**
- У каждого мира своя машина Lua; общение между мирами — только глобальные переменные кампании (строки).
- Библиотеки читаются с диска (`scripts\*.l`), не из ресурсов и не из модов.
- Скрипты вариантов шаблона запускаются в пост-порядке (вложенные раньше, корень последним), за загрузочным экраном.
- При повторном входе в зону из файла скрипты не перезапускаются, но снова вызывается `OnEnterZone()`.
- Менеджер триггеров — бесконечный Lua-поток с проходом раз в 10 сегментов; период триггера по умолчанию 20 сегментов.
- За проход срабатывает максимум один одноразовый триггер (обход прерывается).
- Ошибка в условии триггера убивает менеджер — все триггеры мира перестают работать.
- Многоразовый триггер запускает новый поток-обработчик на каждой успешной проверке.
- `WaitForUI` — опрос раз в 2 тика; пока старт задержан, возвращается сразу.
- Номер ожидания команд интерфейса не освобождается, если команда отброшена фильтром — ожидание вечное.
- Счётчик номеров команд интерфейса не сохраняется — после загрузки возможны совпадения номеров.
- Начало/конец сцены: уведомления ИИ на каждом вызове (вложенные сцены тоже), «бесхозное» прерывание на стеке ходов на каждый вызов.
- Конец сцены без `bRestoreCamera` делает финальную позу кинокамеры игровой камерой.
- Пропуск сцены — перемотка мира без рендера до ближайшего `EndSequencePart`/`EndSequence`; диалоги в пропущенной части не показываются.
- Задержанный старт крутит сегменты за загрузочным экраном до 9 999 раз.
- `OnPlayerLose(0)` откладывается до остановки тела героя или 4000 мс, затем повторяется каждый сегмент.
- Две разновидности кнопок меню кодируют `OnScriptNotify` по-разному (1/2/0 и 1/0/2).
- Обработчик окна выполняется поверх текущего потока скрипта окна и спит вместе с ним; функция-обработчик должна быть глобальной.
- `OnClickUsable` — в момент получения приказа, `OnOpenObject` — после окончания анимации; при открытии скриптом «пользователь» = `nil`.
- `ObjectOpen` не открывает запертую или сломанную дверь; заминированная взрывается.

**Функции движка**
- Приказы юнитам идут через очередь командира с «продолжить», а не напрямую.
- `UnitIsDead` от недействительной ссылки ничего не возвращает (для Lua — `nil`, то есть «жив» в `not UnitIsDead`).
- `UnitSetXPLevel` округляет к ближайшему, остальные целые параметры усекаются.
- `UnitSetSkill` обрезает значение по текущему максимуму; номер навыка не проверяется.
- `UnitInArea` — строгие неравенства: стоящий на границе считается снаружи.
- `HasInventoryItem`: владелец из рюкзака — первый найденный, из руки — последний найденный; обходит только не-ИИ игроков.
- `GetItem` и `FindItem` возвращают объекты разной природы.
- `SetDiplomacy` одностороннее (только отношение первого игрока ко второму).
- `SetTimeOfDay` возвращает собственный аргумент.
- `ShowLoseDialog`/`ShowLeaveZoneDialog` регистрируют номер ожидания, но не возвращают его.
- `ShowHint` показывает каждую подсказку один раз за кампанию.
- Результат `PlaySound`/`PlayEffect` нужно хранить в переменной, иначе сборщик может уничтожить команду до исполнения.
- `GetWaypointPos` — контрольная точка клетки, не высота из редактора (совпадает с `GetPos` юнита в точке).
- `GetDistance` — в тайлах (м / 0,625).
- `PlaceTemplate` выбирает вариант по таймеру — не воспроизводимо; ставит в заданную в редакторе позицию точки.
- `Difficulty(n)` устанавливает сложность.
- `KillEmAll` убивает врагов игрока 0 по таблице игроков (не по личной дипломатии юнитов).
- `UnitPlayAnimation(u, id, true)` делает анимацию постоянным «простоем» юнита.
- `UnitCanSeeUnit` работает через имя юнита — безымянного «увидеть» нельзя.
- `GroupIsDead` никогда не истинна, если в группе удалённый юнит.
- Релизный `WaitForUnitRoute` игнорирует свой второй параметр.
- `WaitForUnitWaypoint` с погибшим юнитом висит вечно.
- Старая `Common.l` вызывала несуществующие функции задержанного старта.

**База и моды**
- Двухпроходный импорт: сначала все оболочки, потом поля — ссылки разрешаются независимо от порядка таблиц.
- Обратные списки (варианты шаблона) заполняются в порядке импорта — от него зависит, какой вариант даст тот же случайный бросок.
- Флаги вариантов: подходит только точное совпадение набора атрибутов или пустой набор.
- Рулетка с нулевой суммой весов всегда даёт вариант 0.
- `SRand` — LCG MSVC (214013, 2531011), 15 бит результата.
- Отношения «многие ко многим» выводят таблицы из имён столбцов (`XxxID` → `Xxxs`); в игре одно такое отношение.
- Достройка связей только дописывает — повторный вызов дублирует связи.
- Перевод накладывается при выгрузке, а не в игре.
- В релизном `game.db` столбец `DamageMod` записан с кириллической «о».
- Наложение мода: «пустышка» 0xFDFDFDFD / биты 0xFDFDFDFD / `"fdfdfdfd"` = «не менять поле»; отсутствующий столбец — тоже.
- Существующие записи при наложении не пересоздаются (ссылки на них живы).
- Повторный импорт варианта при наложении дублирует его в рулетке.
- Чанк отношений в базе мода заменяет весь список отношений.
- Мод с отсутствующей папкой при загрузке сейва молча выбрасывается.
- Ошибка чтения базы мода проглатывается, но его ресурсы подключаются.
- Россыпь (`T\N`) важнее пакетов; папки модов — важнее `.\res`; поиск с последней папки.
- Проверка «есть ли ресурс» в игре смотрит только пакеты.
- Очередь загрузки ресурсов — стек: свежий запрос первым.

**Сериализатор и сохранения**
- Отсутствующее в файле простое поле обнуляется, составное — остаётся по умолчанию, лишнее — игнорируется.
- Указатели пишутся 32-битными адресами; объекты — в порядке обнаружения.
- Слабая ссылка не висит — объект становится «пустым недействительным».
- При чтении все объекты создаются и читаются раньше корневых полей.
- Чанк верхнего уровня > 100 000 000 байт отвергается.
- Сохраняется весь стек интерфейсов; после загрузки ход не перезапускается.
- Слот = `game.sav` + копия всего `temp\` (файлы зон и `restart.sav`).
- Быстрые сохранения чередуют два слота по времени файла; ключ времени с множителем 3660.
- Автосохранение в начале миссии зависит от `game_autosaves`, в конце миссии — всегда.
- Сохранять можно: на базе всегда; иначе по сложности (Easy — всегда, Normal/Hard — только в реальном времени вне сцен).
- Файл зоны пишется только для базы, связанных зон и при `EnableFeature("reenter")`.
- `restart.sav` пишется уже после установки миссии в стек интерфейсов.
- `temp\` удаляется при нормальном выходе.
- Значения конфигурации пишутся с двумя знаками после запятой, по алфавиту.

## Примеры

### Пример 1. Короткий скрипт миссии с триггером и ожиданием (скрипт 26 «ECom»)

```lua
function HeroSeeBoss()
	local a = GroupCanSeeUnit( GetParty(), GetUnit("boss") )
	return a
end
function HeroSay()
	-- out(...); DialogPlayAsAcks("EComE4"); kaban = GetUnit("Kaban"); поза и маршрут
	SleepForTurn( random( 1, 3 ) )
	PlaceTemplate( 2955, "AG1" )  PlaceTemplate( 2955, "AG2" )
end
Trigger( HeroSeeBoss, HeroSay )
```
(Строка с комментарием сокращает пять строк оригинала: `out("Hero see boss.")`, `DialogPlayAsAcks("EComE4")`, `local kaban = GetUnit("Kaban")`, `UnitSetPose(kaban, POSE_RUN)`, `UnitMoveToWaypoint(kaban, "Target")`; две `PlaceTemplate` в оригинале на отдельных строках.)

Построчно:
1. Скрипт привязан к варианту шаблона карты. Во время разогрева миссии (раздел 4) его верхний уровень выполняется в отдельном потоке: определяются две глобальные функции, `Trigger` регистрирует запись № k (`latency = 20`, одноразовая). Поток верхнего уровня заканчивается и удаляется.
2. Поток менеджера триггеров (из `TriggersManager.l`, спит по 10 сегментов) на третьем проходе, увидевшем эту запись (через 20 сегментов = 1 с после её первого прохода; поскольку в первом тике менеджер выполняется раньше скрипта карты, это ≈1,5 с от старта), вызывает `HeroSeeBoss()` в своём потоке. `GetParty()` создаёт **новую** группу юнитов игрока 0 (владеющая userdata — мусор для сборщика); `GetUnit("boss")` — слабая ссылка. `GroupCanSeeUnit` строит временную группу из босса и спрашивает пересечение «видимых отрядом» с ней. Результат пишется в локальную и возвращается явным `return` (без лишней паузы, раздел 1). Пока результат `false` (`nil`) — проверка повторяется каждые 20 сегментов (1 с).
3. Когда отряд увидел босса: `StartThread(HeroSay)` — новый поток в конце списка, стартует в этом же сегменте; запись триггера удаляется, обход триггеров в этом проходе прерывается.
4. `HeroSay`: печать в консоль; реплики диалога «EComE4» как акки (без окна и ожидания); ссылка на юнита «Kaban»; `UnitSetPose` и `UnitMoveToWaypoint` кладут приказы в очередь его командира (исполнятся при ближайшей выборке приказов; ИИ-юниту назначается маршрут, «ИИ 5»).
5. `random(1, 3)` возвращает **1 или 2** (верхняя граница не включается) — пауза на 1–2 хода, хотя автор, вероятно, хотел 1–3. `SleepForTurn(n)`: запоминает номер хода и опрашивает его раз в 10 сегментов.
6. Затем два раза ставится шаблон 2955 (подкрепление) в точки «AG1» и «AG2»; у каждого варианта могут быть свои скрипты — они стартуют на ближайшем тике. Поток `HeroSay` завершается неявным концом функции и удаляется.
7. Опасность: если «boss» был убран со сцены (`UnitRemove`), `GetUnit` вернёт `nil`, `GroupAddUnit(tempgroup, nil)` вызовет ошибку типа — и умрёт **поток менеджера триггеров**, все триггеры миссии перестанут работать.

**Что лежит в сохранении, сделанном посреди `SleepForTurn`:**
- В списке потоков состояния Lua мира: поток автозагрузки `TriggersManager.l` (кадры: главный чанк → `TriggersManager`, остановлен после `Sleep(10)`, счётчик сна, например 7) и поток «thread made by StartThread» с `HeroSay`: стек кадров `[HeroSay (currPC — инструкция после вызова SleepForTurn), SleepForTurn (currPC — после Sleep(10) внутри while)]`, счётчик сна (0..9), стек значений: метки вызовов, `kaban` (userdata-индекс), `n`, `startTurn`, `k`; ячейки стека выше `top` тоже записаны.
- Таблица глобальных: `HeroSeeBoss`, `HeroSay`, `triggers` (запись k уже `nil` или удалена сборщиком), `maxTriggerIndex`, все функции `Common.l` и константы.
- Массивы: прототипы этих функций (байт-код, строки-константы `"Hero see boss."`, `"EComE4"`, `"Kaban"`…), замыкания (C-функции — по именам `"GetUnit"`, `"Sleep"`…), userdata юнита Kaban — ссылкой сериализатора на объект юнита мира.
- После загрузки: на первом сегменте счётчик сна уменьшается, поток просыпается в цикле `while (GetTurn() − startTurn) < k`; номер хода мира сохранён вместе с миром, так что пауза продолжится ровно с того места.

### Пример 2. Мод, меняющий одно поле одного оружия
Цель: у STG-43 (`RPGWeapons`, ID 39) поднять `DamageModMax` с 109 до 130.

Папка `StgBoost\` в папке игры:
```
StgBoost\description.txt     "STG-43 hits harder"
StgBoost\game.db
```
Содержимое `game.db` (раздел 11, 14), без сжатия:
- чанк 4: версия = 1;
- главные данные: тег 1 — хеш с одной парой «0xE0000002 → объект 1»; тега 2 нет (список отношений игры не трогается);
- таблица объектов: одна запись (класс 0xA1843130, адрес, действителен);
- объект 1 (хранилище): имена целых столбцов — все целые столбцы `RPGWeapons` релиза (`ID`, `InnerClip`, …, `DamageModMax`, …), дробных (`Silencer`, `TrailSpeed`), строковых (`UserName`, `AnimationName`, `WeaponRPGLogics`); одна строка: `ID = 39`, `DamageModMax = 130`, все остальные целые = 0xFDFDFDFD, дробные — биты 0xFDFDFDFD, строки — `"fdfdfdfd"`.

Что произойдёт: игрок включает мод в меню «своя игра» → база перезагружается: основной `game.db`, затем наложение — запись 39 уже есть и не пересоздаётся; при её импорте все поля, кроме `DamageModMax`, видят «пустышку» и остаются как были; `DamageModMax = 130`. Достройка связей. Номер версии базы +1.

Результат для патрона 7,92×33 (`DmgMin = 32`): максимальный урон выстрела `32 × 130 / 100 = 41` вместо `32 × 109 / 100 = 34` (целочисленное деление); минимальный `32 × 91 / 100 = 29` — не изменился. Любое сохранение, сделанное с модом, запишет в заголовок папку `StgBoost` и при загрузке включит его снова.

### Пример 4. Расписание `Sleep` и триггеров в сегментах
- Поток вызывает `Sleep(3)` в сегменте 100 → счётчик 3. Сегмент 101: 3→2, пропуск; 102: 2→1, пропуск; 103: 1→0, поток продолжает. Итого пауза 3 сегмента = 150 мс игрового времени.
- `WaitForUI(id)`, если команда завершилась в сегменте 200 (событие разобрано в сегменте 201): поток спит по 2 сегмента, поэтому продолжит в сегменте 201 или 202 — не позже чем через 2 сегмента после разбора события.
- Триггер с `latency = 100`, зарегистрирован перед проходом менеджера P: проверки на проходах P+10, P+20, … (каждые 100 сегментов = 5 с).

### Пример 5. Взвешенный выбор варианта
Шаблон модели 4585 имеет варианты 7520 (вес 0,6) и 7521 (вес 0,8): рулетка `[0; 0,6; 1,4]`. Генератор с зерном 12345: первый вызов даёт зерно 0x9DA03218, `Get(0xFFFF) = 15167`, `v = 15167 × 1,4 / 65535 ≈ 0,324` → сектор 0 → вариант 7520; второй вызов: зерно 0x4ADC687B, `Get(0xFFFF) = 38327`, `v ≈ 0,819 ≥ 0,6` → сектор 1 → вариант 7521. С запросом флагов {3} при флагах 7520 = «3» и 7521 = «2;5» подходит только 7520 — он выбирается всегда.

### Пример 6. Чанк в байтах
Объект с полями: тег 2 — `int 7`, тег 3 — строка `"abc"`. Запись:
`02 08 07 00 00 00` (тег 2, длина 4 → байт 8, значение) и `03 06 61 62 63` (тег 3, длина 3 → байт 6, «abc»). Всего 11 байт; объект, вложенный в тег 5 родителя, даст `05 16 …` (длина 11 → 22 = 0x16). Поле длиной 200 байт: `тег, 91 01 00 00`, затем 200 байт данных (200 × 2 + 1 = 401 = 0x191, младший бит 1 — длина в 4 байтах).

### Пример 7. Типичные приёмы в скриптах миссий (выборка из таблицы `Scripts`)
1. **Задержанный старт со сценой** (25 «ECom»): `DelayGameStart()` → подготовка (спрятать агента `UnitPlaceInPocket`, назначить диалог `UnitSetDialog`) → `CameraSet(GetCamera(60))` → `StartGameWithSequence()` → `PartyMoveToDeploy("_d")`, `Sleep(55)`, `CameraMove(GetCamera(61), 4000)`, `WaitForUnit(GetHero())`, `WaitForUI(DialogPlay("EComE1"))` → `EndSequence()`. Логика дальше — в `OnDialogFinished(code)`: смена диалога, `FadeOut`/`SetTimeOfDay(NIGHT)`/`FadeIn`, цели `ScenarioSetTaskComplete`, запуск штурма `StartThread(StartAssault)`.
2. **Опрос расстояния в потоке** (110 «GermanVault»): `officer = CreateUnit(847, 2, "AxisOfficer", "wpt"..num, 1)`, выключение ИИ `UnitAIMode(officer, false)`, поза и направление, `UnitApplyCritical` для «раненого» вида; поток `CheckNear` каждые 20 сегментов проверяет `GetDistance(GetPos(officer), GetPos(боец)) <= 3` (тайла), затем выдаёт офицеру взрывчатку и **передаёт его игроку 0** (`UnitSetPlayer`). Обратите внимание: `prob = random(100)` тут же перезаписывается `prob = 30` — отладочный «прихват» в данных.
3. **Бесконечный опрос объекта на верхнем уровне** (113 «GermanRepairPlace»): `Floor(4)`, затем `SwitchCheck()` — цикл раз в 40 сегментов сравнивает состояние выключателя и при изменении открывает/закрывает ворота с паузой `Sleep(random(20))` между створками. Поток верхнего уровня никогда не завершается.
4. **Условие победы** (115 «RRBridge»): выдача оружия бойцам по `UnitGetName`, `UnitSetXPLevel(…, 4)`, `ShowHint(86)`, `ScenarioAddGoal(424)`; цикл раз в 20 сегментов: если `GroupCanFight(enemies)` ложно — задача и цель выполнены, `Sleep(40)`, `ShowLeaveZoneDialog(20268)`.
5. **Первое посещение глобальной карты** (90 «GmapAllies»): `if GetGlobalGameVar("gmapefirstenter") then return else Sleep(10) WaitForUI(ShowHint(47)) SetGlobalGameVar("gmapefirstenter", 1) end` — флаг кампании переживает смену миров и сохранения.
