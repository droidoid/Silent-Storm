# Карта 1 — Сборка карты и рельеф

Источник: `Main\MapBuild.*`, `Main\MapBuildTerrain.*`, `Main\MapBuildingInfo.h`, `Main\TerrainInfo.*`, `Main\PolyUtils.*`, `Main\BetaSpline.*`, `Main\wMainWaypoints.*`, часть `Main\wMain.cpp`, `DBFormat\DataMap.*`, `Main\GTerrain*.cpp`, `Main\GTerrainTexture.cpp`, `Main\2DSceneSW.cpp`, `Main\GGrass.cpp`; база `A5GAME.sqlite`; карты `Complete\Terrain|Buildings|Waypoints\<id>`.

Все файлы среза прочитаны целиком. `BetaSpline.*` в сборке карты не участвует: единственный пользователь — сглаживание поля высот камеры в `wHeightLayers.cpp` (сплайн Барского с параметрами 0,5 и 10), это описано в «ИИ 1 — Сетка и проходимость.md» и «Мир 1 — Время, ход, приказы, камера.md». Для правил наложения дыр дополнительно прочитаны `Main\wTerrain.cpp` (потребитель списков дыр и стен), для генератора — `Misc\RandomGen.*`, для рулетки вариантов — `DBFormat\DataConst.h` и `DataFormat.cpp`.

## Суть

Игровая зона не хранится как готовая карта. Она каждый раз собирается при загрузке из дерева **шаблонов**. Шаблон — это прямоугольник W×H клеток с несколькими взаимозаменяемыми **вариантами**; вариант содержит собственный кусок рельефа (высоты, типы тайлов, траву, дыры), здание (если есть), объекты, юнитов, путевые точки, пятна и — главное — список вложенных прямоугольников, каждый из которых ссылается на другой шаблон, повёрнутый, сдвинутый, поднятый на этаж и на dZ. Сборщик спускается по дереву от корня: на каждом узле разыгрывает вариант (по весам, с фильтром по флагам времени суток), «штампует» рельеф варианта в общий рельеф корня (заменой по альфе, сложением или вычитанием), рекурсивно обходит детей, затем добавляет объекты, юнитов и точки, а для зданий создаёт решётку прочности и при необходимости отдельную повёрнутую навигационную сетку. Все случайные выборы идут через один линейный конгруэнтный генератор со стартовым зерном зоны, поэтому одно и то же зерно даёт ту же карту (за исключениями, перечисленными в «прихватах»). В конце все объекты поднимаются на высоту рельефа в своей точке привязки (или в центре здания), авторские взрывы заранее разрушают здания, из дыр рельефа булевыми операциями над многоугольниками строятся подвалы и их стены, по краю карты ставятся пограничные пятна и невидимые блоки 5×5 м, вычисляется прямоугольник безопасного выхода. Отрисовка рельефа — это программный «сплат»: на каждый блок 8×8 тайлов рисуются тайлы по приоритету с 4-битной маской углов, случайным вариантом и поворотом на блок 2×2, затем пятна, подложка травы и умножение на цветовую карту.

## Термины и единицы

| Термин | Значение |
|---|---|
| Тайл, клетка | Квадрат сетки 0,625 м (`FP_GRID_STEP`). Координаты в базе (позиции объектов, юнитов, центры прямоугольников) — в тайлах, если не сказано иное. |
| Узел, отсчёт | Точка решётки на углах тайлов. Карта W×H тайлов имеет (W+1)×(H+1) узлов. Высоты, типы тайлов, плотность травы, альфа и цвет — массивы **узлов**. |
| Единица высоты рельефа | 1/64 м (`FP_TERRAIN_H_SCALE`). Высота узла — 16-битное беззнаковое целое 0…65535, то есть 0…1023,98 м. Не путать с 16-битной высотой тайла ИИ-сетки из «ИИ 1» (там 25 м на 65536). |
| Этаж | 2,5 м (`WALL_HEIGHT`). Номер этажа целый, может быть отрицательным (подвалы). |
| Шаблон (`Templates`) | Прямоугольник W×H тайлов с набором вариантов и рулеткой весов. |
| Вариант (`TemplVariants`) | Одно наполнение шаблона. Его ID — ключ ресурсов `Terrain\<ID>`, `Buildings\<ID>` и записей всех таблиц содержимого. Синоним в коде — «размещение», `nPlacementID`. |
| Прямоугольник (`Rects`) | Вложение шаблона в вариант: центр, размеры, поворот, этаж, dZ, параметры. |
| Финальный элемент (`FinalElements`) | Размещение «размещаемого» (`PlacableObjects`) — объекта мира или предмета — в варианте. |
| Позиция `SMapPosition` | Мировая точка (м), масштаб, поворот (градусы), этаж. |
| Точка привязки `ptAlignTo` | Точка XY, высота рельефа в которой прибавляется к Z элемента после сборки. |
| Корень, глубина | Корневой шаблон зоны имеет глубину 1, его дети — 2 и т. д. |
| Группа слоёв | Навигационная сетка со своим началом и поворотом (подробно в «ИИ 1»). |
| Округление `Float2Int` | Инструкция FPU «к ближайшему, половина к чётному». «Отбросить дробь» — обычное приведение к целому. |
| Углы | В базе и в позициях — градусы; против часовой стрелки при оси X вправо и оси Y вверх. Внутри рельефа — радианы. |

## 1. Модель шаблонов и вариантов

### Назначение
Описать данные, из которых собирается зона, и смысл каждого столбца базы, который читает сборщик.

### Данные

**Templates** (2666 строк) — шаблон.

| Столбец | Смысл |
|---|---|
| `ID` | ключ |
| `UserName` | имя для редактора |
| `Width`, `Height` | размер в тайлах (W, H). Задаёт размер корневого рельефа, полуразмер для центра здания и размер навигационной группы |

| `AmbientMusic`, `CombatMusic`, `DiplomacyID` | int | используются миссией и миром, не сборщиком |

**Rects** (19684 строки) — вложенный прямоугольник.

| Столбец | Смысл |
|---|---|
| `VariantID` | вариант-родитель |
| `TemplateLink` | вложенный шаблон |
| `CenterX`, `CenterY` | центр прямоугольника в тайлах родителя (14115 строк имеют дробный центр) |
| `Width`, `Height` | размер в тайлах; используются только при импорте для перевода центра в угол |
| `Rotation` | поворот в градусах, любое вещественное (0 — 11167 строк, 90 — 2777, 180 — 1625, 270 — 817, −90 — 278, 360 — 276, 450 — 171, а также 51,1; 45; −19 и сотни других) |
| `Floor` | смещение по этажам (−2…4; 0 у 18317 строк) |
| `DeltaZ` | дополнительный подъём в метрах (0 у 18878 строк; 0,1; 0,625; 1,25; −0,378…) |
| `Params` | атрибуты, добавляемые к флагам поддерева, через «;». В БД пусто во всех строках |

При импорте центр сразу переводится в **угол** прямоугольника (локальное начало координат вложенного шаблона) в метрах: угол = центр·0,625 − R(Rotation)·(W·0,625/2, H·0,625/2), где R — поворот против часовой стрелки. Поле `nPinID` (закрепление варианта, −1) существует только в памяти, в базе его нет.

### Алгоритм
Импорт базы (однократно при загрузке):
1. Каждая строка `TemplVariants` дописывается в список вариантов своего шаблона (без повторов), а её `RndWeight` — новым сектором в рулетку шаблона. Порядок — порядок строк при импорте.
2. Каждая строка `Rects`, `FinalElements`, `Units`, `Waypoints`, `Explosions`, `TerrainSpots` дописывается в соответствующий список своего варианта в порядке импорта. Порядок важен: в этом порядке обходятся дети, создаются объекты и тратятся случайные числа.
3. Центр прямоугольника переводится в угол (формула выше).

### Формулы
- Угол прямоугольника: `c = (CenterX·0,625, CenterY·0,625)`; `s = (−W·0,3125, −H·0,3125)`; `угол = c + (cosθ·s.x − sinθ·s.y, sinθ·s.x + cosθ·s.y)`, θ = Rotation в радианах (используется исходное вещественное значение, без отбрасывания дробной части).

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| `FP_GRID_STEP` | 0,625 м | шаг сетки | `Grid.h` |
| `FP_TERRAIN_H_SCALE` | 1/64 м | единица высоты рельефа | `Grid.h` |
| `WALL_HEIGHT` | 2,5 м | высота этажа | `MapBuild.cpp` |
| `CLUE_SLOT_ID` | 188 | предмет «место улики» | `MapBuild.cpp`, `RPGItems` |
| `EXPLOSION_ID` | 189 | предмет «авторский взрыв» | `MapBuild.cpp`, `RPGItems` |
| `HINT_SLOT_ID` | 438 | предмет «место подсказки» | `MapBuild.cpp`, `RPGItems` |

### Особые случаи и прихваты
- Порядок вариантов определяется порядком строк при импорте, а не ID. В `A5GAME.sqlite` физический порядок совпадает с порядком ID везде, кроме 4 строк (например, вариант 4830 шаблона 2808 лежит после 4834). Какой порядок строк в релизном `game.db` — не подтверждено. От порядка зависит, какой вариант выпадет при данном случайном числе.
- Вес 0 — способ «выключить» вариант, не удаляя его: шаблоны солдат («AlliedSoldier» 2349, «AlliedOfficer» 2403 и др.) имеют один вариант с весом 1 и 9–11 вариантов с весом 0.
- `ColorMap`, `Layer` пятна, `RoomParamID`, `RoomID`, `Width`/`Height` прямоугольника после импорта не используются.
- NULL в целом столбце читается как 0 (для `Border`, `ExitBorder`, `NoAttack` это существенно) — для релизного `game.db` не подтверждено.

### Что нужно от движка-носителя
Табличное хранилище с сохранением порядка строк; бинарные ассеты на вариант (рельеф, здание, путевые точки, маршруты).

## 2. Выбор варианта: веса, флаги, закрепления, генератор случайных чисел

### Назначение
Детерминированно выбрать вариант каждого шаблона дерева.

### Данные
- Генератор `SRand`: одно 32-битное знаковое целое `seed`.
- Рулетка шаблона: массив накопленных сумм `m[0]=0, m[i+1]=m[i]+вес_i` (float).
- Флаги запроса: отсортированный массив номеров атрибутов.

### Алгоритм
**Генератор.** `Get(n)`: `seed = seed·214013 + 2531011` (с переполнением 32 бит); `r = (seed >> 16) & 0x7FFF`; результат `r·n / 32768` (целочисленное деление). `GetFloat(a, b) = a + Get(65535)·(b − a)/65535` (произведение в double, результат приводится к float). Так как `Get(65535)` = 0 при r = 0 и 2r − 1 иначе, максимум `GetFloat` строго меньше b (65532/65535·b). Конструктор `SRand()` без аргумента берёт зерно `GetTickCount()` и сразу делает один холостой `Get(4)`; конструктор с зерном холостого шага не делает.

**Рулетка** (`GetRandomSector`): если полная сумма `m.back()` = 0 — вернуть 0, **не тратя** случайное число. Иначе `f = GetFloat(0, m.back())` (ровно один шаг генератора) и двоичный поиск: `b = 0, e = len(m) − 1`; пока `b + 1 < e`: `c = b + (e − b)/2`; если `f < m[c]` то `e = c`, иначе `b = c`. Ответ — `b`. Нулевые секторы никогда не выпадают (если сумма > 0).

**Выбор варианта** `GetTemplVariant(шаблон, флаги, nVarID, rand)`:
1. Если `nVarID > 0` — вернуть вариант шаблона с этим ID (линейный поиск); случайные числа не тратятся; если такого нет — «нет варианта».
2. Если флаги пусты — рулетка по всем вариантам шаблона.
3. Иначе: отобрать «подходящие» варианты (действующие, и их `Flags` пусты, или хотя бы один набор пуст, или хотя бы один набор **в точности равен** массиву флагов запроса). Если подходящих нет — «нет варианта». Иначе построить новую рулетку из весов подходящих (в исходном порядке) и разыграть её.

**Флаги и их наследование.** Корневые флаги: строковые параметры зоны переводятся в номера атрибутов по `Attributes.UserName` (неизвестные строки отбрасываются), массив сортируется. Для зоны сценария параметры — одна строка `ScenarioZones.TimeOfDay` («Day» — 31 зона, «Night» — 21, NULL — 1); для обучения — «Day» (из кода меню). Флаги ребёнка = флаги родителя + переведённые `Rects.Params`, затем сортировка (дубликаты не удаляются). Время суток при сборке карты **не** выбирается случайно: случайный выбор Day/Night делает только мир для своего набора флагов (освещение), если ни Day, ни Night не заданы.

**Закрепления.** В игре закреплён только корень: зона заранее разыгрывает вариант корневого шаблона (раздел 3, «Зерно») и передаёт его ID как `nPlacementID`; на глубине ≥ 2 всегда идёт розыгрыш. В редакторе (построение превью рельефа) у каждого прямоугольника есть закрепление `nPinID`: если оно < 0 или запрошен сброс, вариант разыгрывается и запоминается в `nPinID`, затем используется (см. «Карта 2»).

**Порядок трат генератора на одном узле дерева** (игра, есть навигационная сеть):
1. Выбор варианта (0 или 1 шаг).
2. Только для глубины ≥ 2: штамповка рельефа; для каждого пятна варианта в порядке приоритета — выбор материала пятна по рулетке шаблона материала с теми же флагами (0 или 1 шаг на пятно).
3. Рекурсивно все дети в порядке прямоугольников.
4. Элементы варианта в порядке записей: для объекта — розыгрыш варианта объекта и далее для каждой из 5 стадий разрушения — модели (1 шаг), до 4 материалов (по шагу), эффекта (шаг), затем дочернего объекта; для запертого элемента без сундука и с `LockHardness` = 0 — `Get(20)`; для элемента с сундуком — розыгрыш добычи (см. «Бой 2»), `Get(9)` и по `Get(N)` на каждую полку; для юнита с персонажем — розыгрыш рюкзака, оружия в руках и `Get(N)` выбора предмета в руку.
5. Здание варианта разыгрывает свои части **своим** генератором (раздел 8).

### Формулы
- `Get(n) = ((seed' >> 16) & 0x7FFF)·n div 32768`, `seed' = seed·214013 + 2531011 mod 2³²`.
- `GetFloat(0, S) = S·g/65535`, `g = max(0, 2r − 1)`.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| множитель ЛКГ | 214013 | | `RandomGen.cpp` |
| приращение ЛКГ | 2531011 | | `RandomGen.cpp` |
| разрядность выхода | 15 бит (`& 0x7FFF`), делитель 32768 | | `RandomGen.cpp` |
| квант `GetFloat` | 65535 | | `RandomGen.h` |
| атрибуты времени суток | 5 Night, 6 Day | | `Attributes` |

### Особые случаи и прихваты
- Любая рулетка с ненулевой суммой тратит ровно один шаг, даже если вариант единственный. Поэтому однозначные шаблоны (деревья, кусты, солдаты) всё равно сдвигают поток случайных чисел.
- Сравнение флагов — точное равенство множеств. Если бы в `Params` прямоугольника появился атрибут, вариант с флагом «6» перестал бы подходить к запросу «6,10». На практике `Params` пусты.
- Если ни один вариант не подходит, поддерево пропускается целиком (без рельефа, объектов, юнитов): шаблон 2229 «Base_GTVip» имеет единственный вариант 3775 с флагом «6» — ночью вся его начинка исчезла бы. Зоны, где он вложен (GTVip 2289, 3261), дневные.
- При пустых флагах (зона без `TimeOfDay`) подходят все варианты, включая помеченные «Night».
- Предварительный розыгрыш корня зоны всегда идёт с **пустыми** флагами (время суток не учитывается).
- Зерно сборки совпадает с зерном предварительного розыгрыша корня, а это отдельный экземпляр генератора: первое случайное число сборщика равно числу, которым был выбран корень.
- `SRand()` без зерна (время системы) используется в местах, которые поэтому не воспроизводятся: выбор времени суток мира, создание объектов пограничной полосы (раздел 16), материал подложки травы (раздел 7), зерно решётки здания (раздел 8).

### Что нужно от движка-носителя
Собственная реализация этого ЛКГ (не `rand()` платформы) с точной 32-битной арифметикой, double-умножением в `GetFloat` и приведением к float.

## 3. Обход дерева и накопление преобразований

### Назначение
Пройти дерево шаблонов, вычислить мировое положение каждого узла и элемента и собрать всё в единую структуру карты.

### Данные
- Позиция узла: `ptPos` (м, XYZ), `fRotation` (градусы, целые после первого шага), `nFloor`.
- Флаг «выравнивать по рельефу» и точка-якорь здания `ptBuilding` (раздел 9).
- Стек поворотов и начал навигационных групп предков (раздел 8).
- Временный контейнер поддерева `nested` и итоговый `info`.

### Алгоритм
Вход `BuildMap(вариант корня, параметры, сеть, зерно, глубина = −1, уровень миссии)`:
1. Глубина 0 — отказ. Создаётся сборщик: `rand.seed = зерно`, начальная позиция (0,0,0), поворот 0, этаж 0; «выравнивание по рельефу» = да; якорь здания (0,0).
2. Флаги корня из параметров (раздел 2).
3. Корневой рельеф: ширина/высота = W/H шаблона корня; загрузка рельефа корня (раздел 4). У корня штамповки нет — его рельеф и есть основа.
4. Шаблон освещения корня (`DefaultLight`) запоминается как есть (розыгрыш освещения делает мир при каждом обращении).
5. Обход `Traverse(шаблон корня, позиция, глубина 1, флаги, закреплённый вариант)`.
6. Если есть сеть: подъём всех элементов на высоту рельефа (раздел 9), матрицы зданий, авторские взрывы (раздел 13), дыры и стены (раздел 14), альтернативные сетки и лестницы (раздел 8). Без сети (подсчёт мест для улик, поиск переходов) этих шагов нет.
7. Звуковая карта шагов и средний цвет (раздел 6), граница (раздел 16), безопасная зона (раздел 17).

**Зерно и детерминизм.** Зерно — 32-битное целое на пару (зона сценария, шаблон). Оно создаётся один раз при построении графа сценария (`GetTickCount()` в момент создания записи шаблона внутри объекта зоны), сохраняется вместе с зоной и переиспользуется при каждом входе в этот шаблон (подробности хранения — «Кампания 1»). Все шаблоны одной зоны и зоны, созданные в пределах одного кванта системного таймера, получают одинаковое число в качестве зерна. Сразу при создании зоны вариант корня разыгрывается генератором с этим зерном и пустыми флагами; при входе в миссию тот же розыгрыш повторяется и даёт тот же вариант. Случайная встреча и обучение зоны не имеют: зерно = `GetTickCount()` в момент начала миссии. Вход в уже посещённую зону загружает сохранённый мир (`<зона>_<шаблон>.sav`), а не собирает карту заново.

`Traverse(шаблон, pos, глубина, флаги, закрепление)`:
1. Если шаблон отсутствует или глубина > максимальной (если она задана ≥ 0) — выход.
2. Выбрать вариант (раздел 2). Нет варианта — выход (поддерево пропущено).
3. Если глубина > 1 и есть сеть — штамповка рельефа варианта в позицию `pos` с поворотом `pos.fRotation` (раздел 5).
4. Загрузить описание здания варианта; «выравнивание» и якорь (раздел 9).
5. Место навигационной группы (раздел 8); на глубине 1 создать корневую группу.
6. Для каждого прямоугольника варианта по порядку: позиция ребёнка (формулы ниже), флаги ребёнка, рекурсивный `Traverse` с глубиной +1 (без закрепления).
7. Скрипт варианта — в список скриптов.
8. Элементы, юниты, взрывы варианта (разделы 9–13), путевые точки, разрешение маршрутов в поддереве (раздел 12).
9. Если есть сеть и вариант содержит здание — создать здание, при необходимости отдельную сетку, переложить элементы поддерева в итог по этажам, записать лестницы (раздел 8).
10. Перенести всё оставшееся из `nested` в контейнер родителя. На глубине 1 перед этим переложить всё в `info`, ещё раз разрешить маршруты и скопировать у корневого варианта `NoAttack`, `Weather`, `ShowTerrain`.

### Формулы
Поворот точки на α градусов (используется везде): `x' = cosα·x − sinα·y`, `y' = sinα·x + cosα·y`, Z не меняется.

Ребёнок прямоугольника `R` в узле `pos`:
- `local = (R.угол.x, R.угол.y, R.Floor·2,5 + R.DeltaZ)` → повернуть на `pos.fRotation` → `child.ptPos = pos.ptPos + local`;
- `child.nFloor = pos.nFloor + R.Floor`;
- `child.fRotation = (int)(pos.fRotation + R.Rotation + 36000) mod 360` — сумма с отбрасыванием дробной части после сдвига на 36000, то есть фактически `floor(сумма) mod 360` (51,1° → 51°; −0,7° → 359°; 450° → 90°).

Элемент `E` (объект, предмет, юнит, путевая точка, взрыв) в узле `pos`:
- `local = (0,625·E.x, 0,625·E.y, E.nFloor·2,5)` → повернуть на `pos.fRotation` → `ptPos = pos.ptPos + local`;
- `ptPos.z += E.DeltaZ` (для путевой точки — непрерывная высота из её ресурса);
- `nFloor = pos.nFloor + E.nFloor`; `fRotation = pos.fRotation + E.Rotation` (без округления).
- Итоговая высота после сборки: `z = Σ(Floor·2,5 + DeltaZ прямоугольников по пути) + E.nFloor·2,5 + E.DeltaZ + h(ptAlignTo)`, где `h` — высота рельефа (раздел 9).

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| сдвиг нормализации угла | 36000° | 100 оборотов перед `mod 360` | `MapBuild.cpp` |
| начальная позиция | (0,0,0), 0°, этаж 0 | корень всегда в начале координат | `MapBuild.cpp` |

### Особые случаи и прихваты
- Угол ребёнка теряет дробную часть, а угол прямоугольника при переводе центра в угол — нет: у шаблона с поворотом 51,1° угол вычислен по 51,1°, а содержимое повёрнуто на 51°.
- Повороты элементов дробные и не нормализуются; ресурс путевой точки хранит поворот целым.
- Порядок работы на узле важен для генератора: сначала собственный рельеф, потом дети, потом собственные элементы.
- Рельеф штампуется сверху вниз (родитель раньше ребёнка): ребёнок перекрывает родителя.
- Элементы поддерева перекладываются в итог «по этажам здания» (раздел 8), поэтому порядок списков итоговой карты: содержимое зданий раньше содержимого открытой местности, а внутри — порядок обхода.

### Что нужно от движка-носителя
Рекурсивная сборка уровня из префабов с собственными трансформациями; детерминированный порядок обхода.

## 4. Модель рельефа

### Назначение
Единый рельеф зоны: высоты, типы покрытия, трава, цвет, дыры, пятна, звук шагов.

### Данные
Рельеф (`STerrainInfo`), все двумерные массивы индексируются `[y][x]`, x — столбец:

| Поле | Размер | Смысл |
|---|---|---|
| `nWidth`, `nHeight` | — | размер в тайлах; у корня округлён вверх до кратного 8 |
| `heightMap` | (W+1)×(H+1), uint16 | высота узла в единицах 1/64 м |
| `typeMap` | (W+1)×(H+1), байт | номер записи `TerrainTiles` в узле; 11 — «прозрачный» |
| `color` | (W+1)×(H+1), ARGB | цвет-множитель узла; 0xFFFFFFFF — без изменения |
| `grass[]` | список слоёв | слой: `nGrassID` (запись `Grass`), плотность в узлах (W+1)×(H+1), байт 0…255; `fMaxDensity` — травинок на тайл при плотности 255; цвет травы на половинной сетке; список отдельных травинок `blades` (точки в тайлах); служебный `nID` |
| `holes[]` | список | дыра: многоугольник в тайлах, смещение высоты `nHeight` в единицах 1/64 м относительно рельефа, флаг видимости дна |
| `spots[]` | список | пятно: материал, угол-точка (м), размер (м), угол (рад), материал звука шагов |
| `soundmap` | как `typeMap` | материал звука шагов в узле (вычисляется) |
| `avrgColor` | как `typeMap` | средний цвет узла для грубой текстуры (вычисляется) |
| `nMaxGrassLayerID` | — | счётчик редактора |

Файл варианта `Terrain\<V>` хранит этот рельеф плюс **альфу** (`alphaMap`, uint16 на узел, 0…65535 — сила влияния высот этого варианта при штамповке) и диапазон `fMinH`/`fMaxH` для редактора. Пустые слои хранятся массивами 1×1. Пятна в файле есть, но при загрузке **отбрасываются**: используются пятна из таблицы `TerrainSpots`.

Пример (корень обучения, вариант 6008): 80×96, типы — все 11, высоты 316…319 (4,94–4,98 м), альфа — все 0, цвет 1×1. Вложенный «Main Map (Tutorial)» (5900): типы 1×1 (нет), высоты 637…640, альфа — все 0, один слой травы (ID 16 «Grass00», 930 ненулевых узлов из 81×97, `fMaxDensity` 3,0, цвет травы 41×49).

### Алгоритм
Загрузка корневого рельефа (`LoadRootTerrain`):
1. Прочитать `Terrain\<V>` (если файла нет — пустой рельеф с размером шаблона). Сгенерировать дыры подвала по описанию здания этого варианта (раздел 14).
2. Пятна: взять записи `TerrainSpots` варианта, отсортировать по `Priority` по возрастанию; для каждой: материал = розыгрыш шаблона материала из `Spots.MaterialID` с флагами карты (раздел 2), звук шагов = `Spots.RPGArmorID`; позиция и размер — из записи, угол = `Rotation` в радианах. Запись без `Spots` или без шаблона материала пропускается; если же у шаблона нет подходящего по флагам варианта, пятно добавляется с пустым материалом (не рисуется, но участвует в звуковой карте).
3. `nWidth = max(2, ширина из файла)`, `nHeight = max(2, …)`, обе округлить вверх до кратного 8.
4. Привести размеры: высоты — (W+1)×(H+1) с заполнением 0; типы — с заполнением 11; цвет — с заполнением 0xFFFFFFFF; у каждого слоя травы плотность — (W+1)×(H+1) с заполнением 0, цвет травы — `Float2Int((W+1)·0,5)`×`Float2Int((H+1)·0,5)` с заполнением 0xFFFFFFFF. Правило приведения: если размер уже совпадает — ничего; иначе новый массив заполняется значением по умолчанию, и, если старый был больше 1×1, в него копируется перекрывающаяся часть (по индексам, от угла [0][0]).

Высота рельефа в точке (м) — `GetMeterHeightCheck(x, y)`:
1. `fx = x/0,625`, `fy = y/0,625`; зажать `fx` в [0, XSize − 1,01], `fy` в [0, YSize − 1,01].
2. `nx = (int)fx`, `ny = (int)fy`; `a = lerp(h[ny][nx], h[ny][nx+1], fx − nx)`, **отбросить дробь** (промежуточное значение хранится как uint16); `b` — то же для строки `ny+1`; результат `lerp(a, b, fy − ny)/64`.

### Формулы
- Размер корня: `W8 = ((max(2, W) + 7) & ~7)`, массивы (W8+1)×(H8+1).
- Высота в метрах = значение/64; максимум 65535/64 = 1023,98 м.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| `TRANSPARENT_TILE` | 11 | «прозрачный» тип: не переписывает родителя при штамповке; заполнитель корня | `MapBuildTerrain.cpp`, `TerrainTiles` |
| кратность размера корня | 8 | блоки рельефа 8×8 | `MapBuildTerrain.cpp` |
| минимальный размер | 2 тайла | | `MapBuildTerrain.cpp` |
| `FP_GRASS_COLOR_SCALE` | 0,5 | разрешение цвета травы относительно узлов | `TerrainInfo.h` |
| зажим билинейной выборки | размер − 1,01 | последний узел никогда не читается «чисто» | `Interpolate.h` |
| `N_DEF_BUMP_ID` | 606 | бамп по умолчанию | `DataFormat.cpp` |

### Особые случаи и прихваты
- Билинейная выборка с промежуточным отбрасыванием дроби до целого типа массива (uint16 для высот и альфы, байт для травы): значение, которое должно читаться точно, может уменьшиться на 1, если координата на миллионную долю меньше целого (пример в разделе «Примеры»).
- Из-за зажима до «размер − 1,01» выборка на последнем столбце/строке даёт 0,01·предпоследний + 0,99·последний.
- Высота объекта берётся билинейно, а меш рельефа рисуется двумя треугольниками на тайл с диагональю от (x+1, y) к (x, y+1) (раздел 14): на склонах объект может слегка висеть или утопать.
- Размеры, ширина и альфа в файле нужны только при штамповке; цвет вложенных шаблонов не штампуется вообще (раздел 5), поэтому цветовая карта зоны — только из файла корня.
- В исходных данных корни часто имеют рельеф 1×1 (например, GCom 5004): после приведения размеров высоты нулевые, а весь рельеф даёт вложенный шаблон.

### Что нужно от движка-носителя
Карта высот с вершинами на сетке 0,625 м и 16-битной точностью 1/64 м; набор весовых карт покрытий (splat), слои травы-плотности, вершинный цвет, «вырезы» в ландшафте (для UE5 — Landscape с visibility layer/дырами либо собственный меш).

## 5. Штамповка вложенного рельефа в родителя

### Назначение
Наложить собственный рельеф вложенного варианта на общий рельеф зоны с учётом его положения и поворота.

### Данные
Вход: общий рельеф (рельеф корня, уже с предыдущими штампами), ID варианта, мировая точка начала ребёнка `p` (угол прямоугольника, м), поворот φ (рад), генератор, флаги. Источник: файл `Terrain\<V>` варианта (рельеф + альфа) и записи `TerrainSpots`.

### Алгоритм
Вызывается для каждого узла дерева глубины ≥ 2 сразу после выбора его варианта (только при наличии навигационной сети, то есть не в проходах «без сети»).
1. Загрузить рельеф варианта и сгенерировать его дыры подвала. Если файла нет — перейти к шагу 8.
2. Если ширина **и** высота ребёнка (из файла) больше ширины и высоты общего рельефа — прекратить штамповку целиком (без дыр и пятен).
3. Если массив типов ребёнка больше 1×1 хотя бы по одной оси — штамповка типов: в каждый узел, куда попадает ребёнок, записать ближайший узел ребёнка, если он не 11.
4. Цвет ребёнка не штампуется (код закомментирован с пометкой «надо будет смешивать по альфе»).
5. Трава: для каждого слоя ребёнка найти в общем рельефе слой с тем же `nGrassID` (первый найденный); если нет — создать новый (плотность (W+1)×(H+1) нулей, цвет `Float2Int(W·0,5)`×`Float2Int(H·0,5)` из 0xFFFFFFFF, `fMaxDensity` ребёнка). Плотность в зоне ребёнка **заменяется** билинейной выборкой ребёнка (с отбрасыванием дроби до байта). Если цвет травы ребёнка больше 1 по X — цвет травы заменяется ближайшей выборкой на половинной сетке.
6. Высоты, если массив высот ребёнка больше 1 по обеим осям: для каждого узла в зоне ребёнка взять `A` — билинейная выборка альфы ребёнка, делённая на 65535, и `H` — билинейная выборка высот ребёнка; затем по `HMBlendType` варианта:
   - Normal: `h = Float2Int((1 − A)·h + A·H)`;
   - Add: `h += Float2Int(A·H)` (по модулю 65536);
   - Subtract: `h −= Float2Int(A·H)` (по модулю 65536).
7. Дыры ребёнка: каждый многоугольник переносится точным поворотом на φ и сдвигом на `p/0,625` (тайлы) и **дописывается** в список дыр (сама дыра своей высоты и видимости).
8. Пятна ребёнка: загрузить из `TerrainSpots` с розыгрышем материалов (как у корня, раздел 4), перенести: позиция = R(φ)·pos + p (м), размер тот же, угол = угол + φ; дописать в список пятен рельефа.

**Перебор узлов** (общий для типов, травы, цвета травы и высот): для каждого узла `(nX, nY)` целевого массива целиком:
- `X0 = p.x/0,625`, `Y0 = p.y/0,625` (для цвета травы — умноженные ещё на 0,5);
- `xa = nX − X0 + 0,5`, `ya = nY − Y0 + 0,5`;
- `x = xa·cosφ + ya·sinφ − 0,5`, `y = −xa·sinφ + ya·cosφ − 0,5` — координаты в узлах ребёнка;
- узел обрабатывается, если `x ≥ −0,49`, `y ≥ −0,49`, `x ≤ Xsrc − 0,51`, `y ≤ Ysrc − 0,51` (Xsrc, Ysrc — размеры массива ребёнка).
- Ближайшая выборка: узел `[Float2Int(y)][Float2Int(x)]`; билинейная — как в разделе 4 (с зажимом и отбрасыванием промежуточной дроби).

### Формулы
- Обратное отображение: `(x, y) = R(−φ)·((nX, nY) + ½ − (X0, Y0)) − ½`.
- Смещение относительно точного поворота узлов: штамп сдвинут на вектор `R(φ)·(½, ½) − (½, ½)` тайла. При φ = 0 — (0, 0); 90° — (−1, 0); 180° — (−1, −1); 270° — (0, −1); при промежуточных углах — дробный сдвиг.
- Альфа: `A = bilinear(alpha)·(1/65535)`.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| порог попадания | −0,49 / размер − 0,51 | граница зоны ребёнка в узлах | `MapBuildTerrain.cpp` |
| нормировка альфы | 1/65535 | | `MapBuildTerrain.cpp` |
| прозрачный тип | 11 | не переписывает | `MapBuildTerrain.cpp` |
| режимы | Normal / Add / Subtract | `HMBlendType` | `DataMap.cpp` |

### Особые случаи и прихваты
- Перебор идёт по **узлам** с поправкой «центра клетки» ±0,5. Для массивов узлов (а высоты, типы и трава — массивы узлов) это сдвигает повёрнутый штамп на один узел относительно здания, объектов и дыр того же варианта, которые поворачиваются точно (формулы выше). Пример с реальными данными — в разделе «Примеры».
- Режим Add/Subtract не насыщается: переполнение uint16 заворачивается (вычитание ниже нуля даёт высоту ≈ 1024 м). В данных Subtract есть у одного варианта (1596, шаблон «8x8»).
- Альфа 0 делает высоты ребёнка невидимыми в любом режиме. У многих вариантов зданий и даже у «Main Map (Tutorial)» альфа нулевая — их высоты игнорируются, рельеф целиком задаёт корень.
- Плотность травы ребёнка **заменяет** плотность того же слоя в прямоугольнике ребёнка (в том числе нулями); другие слои не трогаются.
- Типы ребёнка переписывают только значением ≠ 11 — «прозрачный» тип позволяет штамповать лишь часть покрытия.
- Условие отказа сравнивает ширину **и** высоту: ребёнок, больший только по одной оси, штампуется (его часть за пределами массива просто не попадает в перебор).
- Перебор идёт по всему массиву корня для каждого вложенного шаблона, даже крошечного (2×2 тайла куста), — квадратичная стоимость, поведения не меняет.
- Штамповка выполняется только при наличии навигационной сети: проходы без сети (подсчёт мест под улики, поиск переходов) не тратят на пятна случайные числа, и дальнейший розыгрыш вариантов в них идёт по другим числам (раздел «Все прихваты»).

### Что нужно от движка-носителя
Редактируемая карта высот и весовых карт, процедурная запись в неё при загрузке уровня (или предварительное «запекание» результата сборки на каждое зерно).

## 6. Слои тайлов, переходы, пятна (правила для splat-материала)

### Назначение
Правила, по которым из `typeMap`, пятен, травы и цветовой карты получается вид земли. Сам программный растеризатор будет заменён движком; здесь — то, что нужно воспроизвести в материале.

### Данные
- Блок рельефа 8×8 тайлов (`N_TERRA_STEP`), начало блока — кратно 8; на блок своя текстура 256×256 (вблизи) или 128×128 (вдали) и своя карта нормалей.
- Виртуальный холст блока 256×256 «текселей», 32 текселя на тайл (`N_TEXEL_TILE`).
- Текстура покрытия: варианты 64×64 рядом по горизонтали (вариант k — столбцы 64k…64k+63); один вариант покрывает блок 2×2 тайла.
- Маска покрытия 256×256: варианты по 64 по горизонтали; 4 строки по 64 текселя — виды переходов (ниже).
- Зерно блока: `y0·nWidth + x0`, где (x0, y0) — угол блока в тайлах, `nWidth` — ширина рельефа (кратная 8). Генератор — `SRand` из раздела 2, без холостого шага.

### Алгоритм
1. Список покрытий: все записи `TerrainTiles`, у которых есть маска и текстура (для цвета) или маска и бамп (для нормалей); отсортировать по `Priority` по убыванию. Поскольку бамп по умолчанию подставляется при импорте, в обоих проходах участвуют все 11 записей.
2. Отметка «клетка уже закрашена» для 64 клеток блока — ложь.
3. Для каждого покрытия T по порядку списка:
   1. Для строк y = 0…7: если y чётное — для каждого столбца x = 0…7 выполнить три розыгрыша подряд: вариант маски `Get(MaskVariants_T)`, вариант текстуры `Get(TextureVariants_T)`, ориентация `Get(3)` → 0 — без поворота, 1 — 90°, 2 — 180°.
   2. Для каждого x: код углов `c = [t(x,y)=T]·1 + [t(x+1,y)=T]·2 + [t(x+1,y+1)=T]·4 + [t(x,y+1)=T]·8`, где t — `typeMap` в узлах (с началом блока).
   3. Если x чётное — взять розыгрыш столбца x (так один розыгрыш управляет блоком 2×2 клеток с чётными координатами младшего угла: строки y и y+1, столбцы x и x+1; блоки 2×2 выровнены по чётным координатам всей карты).
   4. Источник в текстуре покрытия для клетки — четверть 32×32 варианта v; при повороте четверть выбирается так, что весь вариант 64×64 поворачивается целиком на блок 2×2 (формулы ниже).
   5. Если клетка ещё не закрашена и `c ≠ 0` — нарисовать четверть непрозрачно и пометить клетку. Иначе нарисовать четверть через маску вида `c` (таблица ниже) с вариантом маски m; коды 0 и 15 в этой ветви ничего не рисуют.
4. Поверх: все пятна рельефа в порядке списка (раздел 4: сначала пятна корня по приоритету, затем пятна вложенных шаблонов в порядке обхода, затем пограничные пятна).
5. Поверх: подложка травы (раздел 7).
6. Только для цвета: умножение на цветовую карту — инвертированные значения `color` 9×9 узлов блока растягиваются билинейно на всю текстуру и используются как маска для чёрного цвета, то есть каждый канал умножается на `(c + 1)/256` (c — канал цвета узла, интерполированный).
7. Мипмапы — усреднение 2×2.

Смешивание:
- Непрозрачная клетка — копия.
- Клетка через маску: `dst = (src·m + dst·(256 − m)) >> 8` **по каналам**: R маски для R, G для G, B для B (маски серые, так что фактически по яркости маски). В проходе нормалей используется канал R маски.
- Пятно (цвет): «предумноженная альфа» — `dst = src + dst·(1 − a/255)` (векторная реализация с приближённым умножением). Пятно (нормали): `dst = (bump·a + dst·(256 − a))/256`, где a — альфа цветовой текстуры пятна; если у материала пятна нет бампа — используется нейтральная нормаль (128,128,255).
- Геометрия пятна: прямоугольник с углом в `pos`, сторона «вправо» = size.x·(cosα, sinα), «вверх» = size.y·(−sinα, cosα); текстура пятна растягивается на прямоугольник целиком.

Виды масок (строка маски по вертикали; ориентации — как у текстуры, см. ниже):

| Код углов | Какие углы клетки заняты | Строка маски | Ориентация |
|---|---|---|---|
| 1 | (x, y) | 3 — один угол | 270° |
| 2 | (x+1, y) | 3 | 180° |
| 4 | (x+1, y+1) | 3 | 90° |
| 8 | (x, y+1) | 3 | 0° |
| 3 | (x, y), (x+1, y) | 2 — сторона | 180° |
| 6 | (x+1, y), (x+1, y+1) | 2 | 90° |
| 12 | (x+1, y+1), (x, y+1) | 2 | 0° |
| 9 | (x, y+1), (x, y) | 2 | 270° |
| 5 | (x, y), (x+1, y+1) | 0 — диагональ | 180° |
| 10 | (x+1, y), (x, y+1) | 0 | 90° |
| 7 | все, кроме (x, y+1) | 1 — три угла | 180° |
| 14 | все, кроме (x, y) | 1 | 90° |
| 13 | все, кроме (x+1, y) | 1 | 0° |
| 11 | все, кроме (x+1, y+1) | 1 | 270° |

Ориентация прямоугольника (u, v — локальные координаты клетки 0…1 по x и по y узлов; t — координаты в исходном прямоугольнике текстуры/маски): 0° — t = (u, v); 90° — t = (1 − v, u); 180° — t = (1 − u, 1 − v); 270° — t = (v, 1 − u). Отсюда в исходных масках «включённый» угол одиночной маски — тексель (0, 1) прямоугольника (левый столбец, последняя строка), сторона — последняя строка, диагональ — углы (0,0) и (1,1), у «трёх углов» выключен угол (1, 0).

### Формулы
Источник четверти для клетки (x, y) блока, вариант v, сдвиг в текстуре покрытия (тексели):
- 0°: `tx = (x mod 2)·32 + 64v`, `ty = (y mod 2)·32`;
- 90°: `tx = (1 − y mod 2)·32 + 64v`, `ty = (x mod 2)·32`;
- 180°: `tx = (1 − x mod 2)·32 + 64v`, `ty = (1 − y mod 2)·32`;
- 270° (недостижим): `tx = (y mod 2)·32 + 64v`, `ty = (1 − x mod 2)·32`.
Маска: прямоугольник `[64m, 64m+64) × [64·строка, 64·строка+64)`.

Итог для splat-материала: базой клетки служит покрытие с **наибольшим** `Priority` среди четырёх углов; затем каждое другое присутствующее покрытие накладывается его маской перехода в порядке убывания приоритета (то есть покрытие с меньшим приоритетом оказывается сверху).

### Особые случаи и прихваты
- Ориентация 270° никогда не выбирается: `Get(3)` даёт 0…2.
- Случайные числа тратятся на каждое покрытие из таблицы в каждом блоке (по 96 на покрытие: 3 × 8 столбцов × 4 чётные строки), даже если покрытия в блоке нет; результат зависит от состава и порядка таблицы `TerrainTiles`. При равных приоритетах порядок — порядок перебора таблицы и сортировка (при 11 записях — сортировка вставками, устойчивая); точный порядок перебора хеш-таблицы записей — не подтверждено.
- Половина розыгрышей (нечётные столбцы) не используется.
- Покрытие 11 «Transparent» — реальное покрытие с белой текстурой 10 и приоритетом 0: где корень не закрашен, земля белая под пятнами. Корень обучения целиком из него; вид задают 79 пятен и трава.
- Пятна рисуются строго в порядке списка, без учёта приоритета вне одного варианта.
- Нормали: тот же алгоритм с бампами; затем вектор (du, dv, 1) нормируется и пакуется `·127 + 128`.
- Грубая «запасная» текстура блока, пока настоящая не готова, — из `avrgColor`: цвет узла × средний цвет текстуры покрытия (поле `AverageColor` текстуры), поверх — средние цвета пятен (позиция пятна округлена до 1/1024 м).
- Звук шагов (`soundmap`) считается после сборки: в каждом узле — `RPGArmorID` его покрытия; затем каждое пятно (в порядке списка) переписывает узлы, центры которых попадают в его прямоугольник (тот же перебор, что в разделе 5, с размером пятна в тайлах), значением своего `RPGArmorID` — в том числе пустым. Запрос звука в точке — узел `(Float2Int(x/0,625), Float2Int(y/0,625))`; пустое значение означает «материал по умолчанию».

### Что нужно от движка-носителя
Материал ландшафта с весовыми слоями на вершинах сетки 0,625 м, масками переходов (можно взять оригинальные `Mask1/Mask2`), случайным вариантом и поворотом на блок 2×2 (детерминированно от координат блока), декалями-пятнами с порядком отрисовки и умножением на вершинный цвет; физический материал поверхности для звука шагов.

## 7. Трава: правила размещения

### Назначение
Детерминированно расставить травинки по картам плотности.

### Данные
- Слой травы рельефа (раздел 4): `nGrassID`, плотность в узлах, `fMaxDensity`, список явных травинок.
- Запись `Grass`: `TextureID`, `ScaleX/Y` (размер травинки), `PivotX/Y`, `SpotMaterialID` (шаблон материала подложки), `SpotScale`, `SideSize` (атлас N×N спрайтов), `ScaleRange` (зажимается в 0…1). Пример: 16 «Grass00» — текстура 1906, 0,7×0,6, опора (0; −1), без подложки, `SpotScale` 1, атлас 4×4, разброс 0,4; 18 «Grass02» — 1,0×0,8, подложка 942, `SpotScale` 0,6, разброс 0,3.
- Сектор — 8×8 тайлов.

### Алгоритм
1. Слои трекера: для каждого слоя рельефа (индекс i), у которого есть запись `Grass`. Материал подложки — розыгрыш шаблона материала генератором со временем системы (один раз на слой).
2. Секторов по X: `ceil((nWidth − 1)/8)`, по Y аналогично. В игре сектор создаётся, только если в его 9×9 узлах есть ненулевая плотность или в нём есть явная травинка.
3. Расстановка в секторе (sx, sy) слоя i: `x0 = 8·sx`, `y0 = 8·sy`; генератор `SRand((i << 24) ^ (y0 << 14) ^ x0)`. Для каждого тайла (tx, ty), `x0 ≤ tx < min(x0+8, Xузлов − 1)`, аналогично по y:
   1. Плотности углов: `lb = g[ty][tx]/255`, `rb = g[ty][tx+1]/255`, `lt = g[ty+1][tx]/255`, `rt = g[ty+1][tx+1]/255`.
   2. Число травинок `n = Float2Int((lb + lt + rb + rt)/4 · fMaxDensity)`.
   3. Для каждой травинки — отбор с отказами, не более 63 попыток: `x = GetFloat(0,1)`, `y = GetFloat(0,1)`, `s = GetFloat(0,1)`, `p = (1−x)(1−y)·lb + x(1−y)·rb + (1−x)y·lt + xy·rt`; принять, если `s ≤ p`. Если попытки кончились — берутся последние x, y.
   4. Позиция `((tx + x)·0,625, (ty + y)·0,625)`, Z — высота первой точки выхода вертикального луча по геометрии рельефа на сетке 4 отсчёта на тайл; если пересечения нет — травинка не ставится.
4. Явные травинки слоя, попавшие в сектор (в тайлах), — с той же проверкой высоты.
5. Подложка (рисуется в текстуру рельефа, раздел 6, только если у слоя есть материал подложки): для травинки с номером k в списке сектора — угол `α = frac((x + y)·10)·2π` (x, y в метрах, frac — через отбрасывание целой части), размер `s = SpotScale·(1 − r_k·ScaleRange)`, где `r_k = ((k·0x24B) & 0x3FF)/1024`; прямоугольник s×s, центр — в травинке.
6. Колыхание: сетка тайлов хранит метку времени последнего «касания» (юнит прошёл); амплитуда `0,15·(1 − Δ/128)`, Δ — в шагах по 0,02 с (затухание за 2,56 с).

### Формулы
- Зерно сектора: `(слой << 24) ^ (y0 << 14) ^ x0`.
- Вероятность отбора — билинейная плотность.
- Псевдослучайность травинки: `((k·587) & 1023)/1024`.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| `N_GRASS_SECTOR_SIZE` | 8 тайлов | сектор травы | `GGrass.h` |
| `N_SAMPLES_PER_TILE` | 4 | шаг трассировки высоты травинки 0,156 м | `GGrass.cpp` |
| попыток отбора | 63 | | `GGrass.cpp` |
| множитель псевдослучайности | 0x24B = 587, маска 0x3FF | | `GGrass.h` |
| амплитуда колыхания | 0,15 | | `GGrass.cpp` |
| шаг времени колыхания | 0,02 с, 128 шагов | | `GGrass.cpp` |

### Особые случаи и прихваты
- Если 63 попытки не дали травинку, она всё равно ставится в последнюю точку — редкая трава на краях пятен плотности получает лишние травинки.
- Зерно сектора зависит от индекса слоя в списке рельефа, а этот индекс зависит от порядка, в котором вложенные шаблоны создавали слои при штамповке.
- Материал подложки выбирается генератором со временем системы — у шаблона материала с несколькими вариантами подложка от загрузки к загрузке разная.
- Трава стоит на геометрии рельефа (с дырами), а не на карте высот: над невидимым дном подвала травы нет.

### Что нужно от движка-носителя
Процедурная расстановка экземпляров (Foliage/PCG) по карте плотности с детерминированным зерном на сектор; декали подложки; реакция на прохождение юнитов.

## 8. Здания внутри шаблонов

### Назначение
Поставить здание варианта в мир, создать для него встроенные объекты (окна, двери), решить, нужна ли ему собственная повёрнутая навигационная сетка, и разложить содержимое по этажам. Устройство здания, решётка прочности и разрушение — в «Мир 2 — Здания и разрушение.md».

### Данные
- `Buildings\<V>` (`CBuildInfo`): фрагменты стен и «солидов» (часть конструкции, позиция x, y в игровых тайлах, z в этажах — промежуточный этаж = .5, номер поворота 0…3, подблок, флаги объекта: бит 0 — открыто), `nMaxX`, `nMaxY`, этажи, лестницы, подвал (булев массив на тайл), комнаты, проецируемые пятна. Нет файла — пустое описание.
- Вариант «является зданием», если у него есть хотя бы один фрагмент стены или солида и не (`nMaxX` = 0 и `nMaxY` = 0).
- Место навигационной группы узла: начало, размер в узлах, поворот.

### Алгоритм
Место группы (`CalcLayerPlace`) вычисляется для **каждого** узла дерева:
1. Отступ `b` = на глубине 1 `min(max(Border, 0), min(W/2, H/2))`, иначе 0.
2. Начало = `(pos.x + 0,625b, pos.y + 0,625b) + R(pos.fRotation)·(−0,625, −0,625)`; размер = `(W + 3 − 2b) × (H + 3 − 2b)` узлов; поворот = `pos.fRotation` в радианах. Группа шире шаблона на один тайл с каждой стороны.
3. Место кладётся в стек предков (снимается при выходе из узла). На глубине 1 сразу создаётся корневая группа с первым этажом −2.

Создание здания (только при наличии сети, после обработки детей и элементов узла):
1. Запись здания: позиция узла (`mpos`), точка привязки = якорь здания `ptBuilding` (раздел 9), вариант.
2. Новая решётка прочности; её зерно — время системы. Генератор частей `brnd` = это зерно.
3. Этажи: `min = 100`, `max = −100`. Сначала солиды, потом стены: для каждого фрагмента разыграть часть конструкции (`brnd`, флаги карты); `max = max(max, (int)(z + 0,5) + SizeZ части)`, `min = min(min, floor(z))`. Если у части есть встроенный объект и не (`SizeY` части = 0 при подблоке ≠ (1,1,1)) — создать элемент мира: позиция = `pos + R(pos.fRotation)·(0,625·(x + dx), 0,625·(y + dy), 2,5·z)`, где для солидов `(dx, dy)` по повороту фрагмента: 90° → (2·SizeY, 0), 180° → (2·SizeX, 2·SizeY), 270° → (0, 2·SizeX), 0° → (0, 0); для стен (0, 0); этаж = `pos.nFloor + floor(z)`; поворот = `pos.fRotation + 90°·номер`; масштаб 1; «открыт» = бит 0 флагов фрагмента; привязка — к якорю здания. Неизменённые `min`/`max` превращаются в 0.
4. Решётка настраивается по `nMaxX`, `nMaxY`, этажам (без матрицы), вычисляется прочность — «Мир 2». Базовый этаж решётки = `pos.nFloor`.
5. Решение о сетке: на глубине 1 — нет (корневая группа уже есть). На глубине ≥ 2 — сравнить место группы узла со **всеми** предками в стеке: «тот же поворот», если `|sinL − sinR|`, `|sinL + sinR|`, `|sinL − cosR|` или `|sinL + cosR|` < 1e-5 (L — узел, R — предок); «согласованное начало», если разность начал в осях предка (`dx·cosR + dy·sinR` и `dx·sinR − dy·cosR`) кратна 0,625 с точностью 0,001 тайла (частное округляется к ближайшему целому). Если нашёлся предок с обоими совпадениями — своя сетка не нужна. Иначе создаётся группа на месте узла с первым этажом −2; если у варианта `Grid` = 0 — предупреждение в лог «шаблон не помечен как создающий сетку».
6. Для каждого относительного этажа `f` от `min` до `max`: переложить в итог карты элементы поддерева, у которых абсолютный этаж ≤ `f + pos.nFloor` (точки высадки, предметы, места улик и подсказок, группы, скрипты переносятся все; объекты, юниты, путевые точки — по этажу); записать этаж (относительный, абсолютный).
7. Добавить здание в карту. Записать лестницы (раздел 15).
8. Дерево альтернативных сеток: если создана своя группа — узел становится дочерним в дереве групп родителя со всеми найденными ниже; иначе найденные ниже группы поднимаются к родителю. В конце сборки корень дерева = группа 0, сеть создаёт исключения (см. «ИИ 1», «Альтернативные сетки»).
9. После обхода: матрица здания = сдвиг `mpos.ptPos + (0, 0, h(ptAlignTo))`, поворот `mpos.fRotation` вокруг Z, масштаб 1.

### Формулы
- Проверка кратности: `n = Float2Int(|f|/0,625)`, годно, если `|n − |f|/0,625| < 0,001`.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| первый этаж группы | −2 | два подземных этажа | `MapBuild.cpp` |
| расширение группы | +1 тайл с каждой стороны (размер W+3) | | `MapBuild.cpp` |
| допуск поворота | 1e-5 по синусу/косинусу | | `MapBuild.cpp` |
| допуск начала | 0,001 тайла | | `MapBuild.cpp` |
| стартовые min/max этажей | 100 / −100 | | `MapBuild.cpp` |

### Особые случаи и прихваты
- Сравнение поворотов только по синусу текущего узла: углы θ и 180° − θ, θ и 90° − θ считаются «тем же поворотом» (для 30° и 150°, 30° и 60° сетка не создаётся).
- Сравнение идёт со всеми предками, включая шаблоны без здания и без собственной сетки: здание, повёрнутое вместе с промежуточным «пустым» шаблоном на 45°, «совпадает» с ним и своей сетки не получает, хотя сетки на 45° не существует.
- Зерно решётки и генератор частей здания берутся из времени системы: варианты частей и встроенных окон/дверей не воспроизводятся зерном карты.
- Расчёт этажей «не учитывает повороты» (пометка автора CRAP в коде).
- Описание здания общее для всех экземпляров варианта, и `nMinFloor`/`nMaxFloor` в нём перезаписываются при каждом создании.
- Фоновый свет объектов узла (раздел 9) записывается в здание этого узла и пропадает, если узел — не здание.
- Функция подготовки сеток для солидов (`CreateGrids`) разыгрывает части генератором времени системы и ничего не делает с результатом.

### Что нужно от движка-носителя
Префабы зданий с этажами, отдельные навигационные области для повёрнутых зданий (или единая навмеш-система без привязки к осям), детерминированный выбор частей, если нужна повторяемость.

## 9. Объекты

### Назначение
Разместить объекты мира и предметы варианта, вычислить их начальное состояние и поднять на рельеф.

### Данные
Записи `FinalElements` варианта (раздел 1), шаблоны объектов (`ObjectTemplates` → варианты `Objects` с весами и флагами: 5 моделей стадий разрушения `Model0…Model4`, материал обломков, «точка высадки», граната самоподрыва, раскладка и сундук по умолчанию, дочерний объект), уровень миссии `L` (относительный уровень зоны, ≥ 0).

### Алгоритм
**Привязка к рельефу.** На узле: «выравнивать» = «выравнивать» родителя И у варианта нет фрагментов здания (у корня родительское значение — да). Якорь: если у родителя «выравнивать» — центр текущего шаблона `pos + R(pos.fRotation)·(W·0,3125, H·0,3125)`, иначе якорь родителя. Каждый элемент узла (объект, предмет, юнит, путевая точка, место улики/подсказки, точка высадки, взрыв) получает `ptAlignTo` = собственная XY, если узел «выравнивается», иначе якорь. В итоге всё внутри здания (и во вложенных в него шаблонах) поднимается на высоту рельефа в центре **самого внешнего** шаблона-здания.

**Элемент-объект** (размещаемое — шаблон объекта):
1. Разыграть вариант объекта (флаги карты; раздел 2) и создать его модели. Нет подходящего варианта — элемент пропускается.
2. Если объект — точка высадки: добавить точку высадки (позиция с `DeltaZ`, поворот, привязка).
3. Если у объекта есть модель стадии 0 — элемент мира: позиция, масштаб `Scale*`, относительный этаж, `Lightmap`, «открыт», привязка, переходы (`PassageZoneID`, `PassageObjectID`), `APRadius`, имя, стадия `ObjectPhase`, `DC = Float2Int(Power)`, окно активности света.
4. Граната-ловушка: по умолчанию — граната самоподрыва объекта; если у элемента задана `Grenade` — она, и `DC = 7L + 16`.
5. Замок: `IsLocked`, `KeyID`, `LockHardness`. Если у элемента есть сундук — `LockHardness = 7L + 16` (значение из базы игнорируется), «прозрачен, когда открыт». Иначе, если заперт и `LockHardness` = 0 — `LockHardness = (Get(20) + 2L)·3 − 3`.
6. Точечный свет: если цвет `PointLight` ненулевой — в модель стадии 0 записываются цвет, позиция, радиус, радиус и текстура блика, позиция блика, тень.
7. Сундук (`RPGChestID`): разыграть добычу с уровнями `[max(0, L − 4), L]` (при L = 0 — `[0, 100]`), см. «Бой 2». Каждый выпавший предмет становится предметом на карте внутри короба: позиция элемента + 0,1 м по Z; половины размеров короба — половины габаритов геометрии модели стадии 0 (если нет — 0,2 м); при раскладке «как сейф» Y-половина делится на 2, и все предметы сдвигаются на эту новую половину в сторону +Y; модель предмета разыгрывается отдельным статическим генератором, оси предмета переставляются (стоя: x ← z; лёжа: y ← z); свободный ход по осям = половина короба − половина предмета (если хоть одна ось < 0 — весь ход 0); сдвиг по X и Y = ход·(`(s mod 3)/3 − 0,5`) − центр предмета, где `s` — «номер полки», начальное `Get(9)`, затем `s = (s + 2) mod 9` для каждого предмета; по Z = половина высоты − 2·центр.z; сдвиг поворачивается на угол элемента; если у раскладки есть полки — `+ полки[Get(число полок)]` по Z; предмет повторяется `Quantity` раз. Попутно на каждый предмет делаются два розыгрыша клетки 3×3 статическим генератором (не влияют на позицию).
8. Фоновый цвет модели стадии 0 (если ненулевой) — в список фонового света здания узла.

**Элемент-предмет** (размещаемое — запись `RPGItems`):
- 188 — место улики (позиция с `DeltaZ`, привязка);
- 438 — место книги подсказок;
- 189 — авторский взрыв (раздел 13);
- иначе — предмет на карте: позиция, масштаб, относительный этаж, «открыт», привязка, имя, `DC = Float2Int(Power)`, `Armed`.

**Подъём на рельеф** (после обхода, при наличии сети): для объектов, взрывов, точек высадки, предметов, мест улик и подсказок, юнитов и путевых точек `z += GetMeterHeightCheck(ptAlignTo)` (раздел 4).

**Создание в мире** (порядок списков): объект — с текущей стадией, трансформация = позиция, масштаб, угол в радианах, этаж (подробно — «Мир 3»). Предмет: если это мина и `Armed` — взведённая мина с `DC`, этажом и поворотом, приведённым к целому отбрасыванием дроби; иначе «замороженный» предмет, повёрнутый так, что лежит плашмя (рыскание = угол, тангаж −90° для вертикальной раскладки сундука, иначе 0; крен 90°); имя регистрируется в верхнем регистре для скриптов.

### Формулы
- `DC_ловушки = 7L + 16`; `Hardness_сундука = 7L + 16`; `Hardness_случайная = 3·(Get(20) + 2L) − 3` (от 6L − 3 до 6L + 54).
- Уровни добычи: `[max(0, L − 4), L]`, при L = 0 — `[0, 100]`.

### Константы

| подъём предметов из сундука | 0,1 м | | `MapBuild.cpp` |
| половина короба по умолчанию | 0,2 м | нет геометрии | `MapBuild.cpp` |
| доли полок | −1/2, −1/6, +1/6 | по `s mod 3` | `MapBuild.cpp` |
| шаг номера полки | +2 mod 9 | | `MapBuild.cpp` |

### Особые случаи и прихваты
- Розыгрыш варианта объекта и всех его моделей выполняется до проверки «есть ли модель»: точка высадки без модели (объект 564 «deploy») всё равно тратит случайные числа.
- Случайная прочность замка может быть отрицательной (−3 при `Get(20)` = 0 и L = 0). Сундук на элементе всегда получает прочность `7L + 16`, даже если в базе задано другое значение.
- Сдвиг предмета в сундуке по Z дважды вычитает центр предмета (так в оригинале).
- В оригинале модель предмета из сундука разыменовывается без проверки — предмет без модели обрушил бы игру (в реконструкции стоит защита, см. «Отклонения»).
- Окно активности света: в релизной базе элемент несёт значение 0 (всегда), 5 (ночью) или 6 (днём), и мир включает/выключает свет по времени суток. Столбец `LightParam` редактора («Night» по умолчанию) соответствует этим значениям (Always/NULL → 0) — соответствие строк числам в импорте релиза не подтверждено.
- Высота берётся из карты высот, а не из геометрии: элемент на дне подвала (дыра −200) всё равно получает высоту поверхности над подвалом; это компенсируется `Floor`/`DeltaZ` в данных.

### Что нужно от движка-носителя
Спавн акторов из префабов с вариантами, стадией разрушения, замками и добычей; функция «высота ландшафта в точке», совпадающая с используемой при сборке.

## 10. Юниты и группы

### Назначение
Перенести юнитов из шаблонов в карту и создать их в мире на нужном этаже, с уровнем, снаряжением и группой.

### Данные
Записи `Units` (раздел 1); `UnitGroups`; ресурсы маршрутов `Units\<ID юнита>` и `Groups\<ID группы>` (список маршрутов, каждый — список ID имён точек; используется только первый маршрут).

### Алгоритм
Сборщик (на узле, после элементов):
1. Для каждой записи юнита: позиция по формуле элемента (раздел 3; X, Y — целые тайлы), привязка (раздел 9), ID записи, персонаж, «место улики-персонажа», относительный уровень, имя, дипломатия из базы, номер игрока сценария, поза, логика, радиус блуждания, «страх с прицелом», анимация караула.
2. Снаряжение (при наличии персонажа; уровни добычи как в разделе 9): рюкзак = розыгрыш сундука `BackpackWeapon` персонажа; оружие в руках = розыгрыш сундука `HandWeapon`: записи без предмета или без «наследника» отбрасываются, магазины переносятся в рюкзак (рюкзак создаётся, если его не было), из оставшихся одна выбирается `Get(число)` и становится предметом в руках. Подробности розыгрыша — «Бой 2».
3. Если юнит — место улики-персонажа или место улики в инвентаре: записать место (позиция, ID юнита, персонаж, оба флага).
4. Если у юнита есть группа — добавить ID юнита в список группы карты.

Мир (`CreateAIUnits`, после зданий, мест улик и путевых точек):
1. Юнит-место улики создаётся, **только если** сценарий положил сюда улику-персонажа; тогда персонаж заменяется персонажем улики, а пустое имя — именем улики. Остальные места пропускаются без юнита.
2. Имя обрезается по краям. Дипломатия берётся из таблицы дипломатии варианта корня по номеру игрока сценария (столбец `Units.Diplomacy` игнорируется).
3. Для каждого нового номера игрока сценария создаётся игрок под управлением ИИ.
4. Уровень = `max(0, уровень миссии + RelativeLevel + nAIUnitsLevel сложности)`; у не-панцерклейнов ОЗ и ОД масштабируются коэффициентами сложности («Бой 2»).
5. Постановка: на этаж `nFloor` в точке позиции (снап к слою этого этажа — «ИИ 1»), направление — ближайшее из 8 к повороту, поза из базы.
6. Юнит-место улики получает отдельный «запас смерти» сложности. Маршрут и реакция по логике — «ИИ 5».
7. Группы (`CreateUnitGroups`): для каждой группы карты — найти или создать группу мира с тем же ID, добавить созданных юнитов по ID записи, построить маршрут группы (раздел 12) и, если он не пуст, назначить его группе.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| `Units.Player` | 1 по умолчанию | номер игрока сценария | БД |
| `Units.Logic` | Guard → «пусто», Sentry/Default → «по умолчанию», Roaming, Fear | | `DataMap.cpp` |
| `Units.Pose` | Stand / Crouch / Crawl; иное → Stand | | `DataMap.cpp` |

### Особые случаи и прихваты
- Позиции юнитов в базе целые (центр тайла-узла), повороты дробные.
- Неиспользованное место улики-персонажа не создаёт юнита вовсе — дизайнеры ставят на такие места «заглушки».
- Группа хранит ID записей юнитов; если юнит не создан (неиспользованное место улики), в группу добавляется пустая ссылка — не подтверждено, как это обрабатывается дальше.
- Ресурсов маршрутов мало (в `Complete\Units` 169 файлов на 4854 юнита); у юнитов обучения маршрутов нет.

### Что нужно от движка-носителя
Спавн ИИ-персонажей с параметрами из данных; привязка к этажу навигации.

## 11. Точки высадки игроков

### Назначение
Определить, где появляется отряд игрока при входе в зону.

### Данные
Источники точек (в порядке приоритета при постановке):
1. Путевые точки «UnitHero», «Unit1»…«Unit9» (схема релиза).
2. Объекты-точки высадки (`IsDeployPoint`; запись 564 «deploy», без модели; 56 элементов в БД).
3. Переход из другого шаблона той же зоны (объект-переход с тем же `PassageObjectID`).
4. Запасная клетка (1, 8) корневого слоя.

### Алгоритм
Сборщик: каждая точка-объект — запись (позиция с `DeltaZ`, поворот, привязка); после подъёма на рельеф список идёт в мир в порядке обхода.

Мир, при создании (`CreateRandom`), для точки k списка:
1. Искать места сети в шаре радиуса 0,63 м вокруг точки; если пусто — радиус ×2, пока радиус < 5 (то есть пробуются 0,63; 1,26; 2,52). Ничего — точка пропускается.
2. Из найденных взять место с наименьшим этажом (при равенстве — первое в списке).
3. Направление — ближайшее к повороту точки, поза «стоя». Запомнить как точку высадки игрока-партии k (номер в списке = номер партии).

Мир, при добавлении игрока (`AddPlayer`; p — номер добавляемой партии, 0 для одиночной игры):
1. Предварительная точка высадки игрока (если у него нет бойцов) — запасная клетка.
2. Если игрок пришёл не через переход и в мире есть путевые точки: искать без сообщений об ошибках «UnitHero» (обязательна; нет — схема выключена), затем «Unit1», «Unit2»… до первой отсутствующей. Точка — место путевой точки; если оно непроходимо — ближайшее свободное место (поиск «куда сдвинуть юнита», «ИИ 2»).
3. Бойцы: постоянные + временные бойцы зоны; мёртвые и без сознания пропускаются. Для бойца i:
   - схема путевых точек: место = точка i, если i < числа точек, иначе точка 0; смещение 0;
   - иначе: место = точка высадки партии p; смещение `i − n/2` (n — число бойцов, деление целое). Если точки партии нет — запасная клетка;
   - переход (тогда схема путевых точек не применяется): место = первый подход к объекту-переходу этого бойца, смещение — как во втором случае; особый случай: зона «ETStore» и шаблон 2291 — путевая точка `Unit<i+1>_l` (из перехода 1) или `Unit<i+1>_g`, поза «пригнувшись», без смещения.
4. Место первого бойца становится точкой высадки игрока (от неё стартует камера).
5. Окончательное место (`GetDeployPlace`): при смещении d ≠ 0 — сдвиг на `(dx, dy) = ((d+4) div 3 − 1, (d+4) mod 3 − 1)` клеток с зажимом в пределы корневого слоя; направление — ближайшее к направлению от места к центру корневого слоя.

### Формулы
Смещения отряда из 6 бойцов (n/2 = 3): d = −3…2 → (−1, 0), (−1, 1), (0, −1), (0, 0), (0, 1), (1, −1).

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| начальный радиус поиска | 0,63 м, удвоение, предел < 5 м | | `wMain.cpp` |
| запасная клетка | (1, 8) тайла → (0,625; 5,0) м, слой 0, направление 0 | | `wMain.cpp` |
| имена точек | «UnitHero», «Unit1»…«Unit9» | | `wMain.cpp` |
| особый шаблон | 2291 зоны «ETStore», суффиксы `_l`/`_g` | | `wMain.cpp` |

### Особые случаи и прихваты
- Номер точки-объекта в списке — это номер партии: первая точка — игроку, вторая — второму игроку hot-seat и т. д. Режим «по точке на бойца» запрашивает номера 1…n, которых не бывает, и всех ставит на запасную клетку (по умолчанию выключен).
- Схема путевых точек имеет приоритет над точками-объектами; в обучении (вариант 6008) стоит «UnitHero».
- Больше бойцов, чем точек «Unit…», — лишние встают в точку «UnitHero».
- Смещения отряда больше 4 по модулю (отряд из 10+ бойцов) дают нелогичные сдвиги из-за деления отрицательных чисел.
- Запасная клетка (1, 8) — в углу карты; на неё же стартует камера, если точек нет.

### Что нужно от движка-носителя
PlayerStart-точки с номером партии и «снапом» к навигации; построение отряда 3×3.

## 12. Вейпоинты и разрешение имён маршрутов

### Назначение
Собрать именованные точки маршрутов со всего дерева и связать маршруты юнитов и групп с точками, определёнными в любых шаблонах дерева.

### Данные
- Запись `Waypoints` → имя (`WaypointNames`), флаг 3D; ресурс точки: позиция (X, Y в тайлах, Z — непрерывная локальная высота в м), этаж, поворот (целый), команды.
- Таблица сборщика «ID имени → последняя добавленная точка с этим именем».
- Маршрут юнита/группы в карте — список точек (настоящих или «заглушек» с одним именем).

### Алгоритм
Добавление (на узле, после элементов): для каждой записи точки варианта с именем и загружаемым ресурсом — точка карты: «существует», имя, 3D, команды, позиция по формуле элемента + Z ресурса, привязка (раздел 9). Точка сразу добавляется в итоговый список карты (в порядке обхода: дети раньше родителя) и в таблицу имён (более поздняя перезаписывает).

Разрешение маршрута (`ResolveRoutes`) выполняется на каждом узле для юнитов и групп поддерева, ещё не перенесённых в итог, и ещё раз на корне для всех:
1. Загрузить ресурс маршрутов юнита (группы); нет ресурса или маршрутов — маршрут не трогать.
2. Запомнить уже найденные «существующие» точки текущего маршрута по ID имени.
3. Очистить маршрут и для каждого ID имени первого маршрута ресурса: если точка с этим именем уже была в маршруте — взять её; иначе если она есть в таблице имён сборщика — взять; иначе вставить заглушку с этим именем.

Так юнит из глубокого шаблона может ходить по точкам, расставленным в родителе или в соседнем шаблоне: на уровне ребёнка вместо них стоят заглушки, на уровне общего предка (или корня) они заменяются найденными.

Мир:
1. Все существующие точки регистрируются по имени в нижнем регистре; при повторном имени остаётся **первая**, о второй выводится предупреждение. 3D-точки «висят» в воздухе, остальные прилипают к сетке («ИИ 5»).
2. Маршрут юнита/группы превращается в маршрут ИИ по **именам** через этот реестр; имена, которых нет в реестре (заглушки), выбрасываются с сообщением в лог.

### Особые случаи и прихваты
- Таблица имён сборщика хранит последнюю точку имени, реестр мира — первую; поскольку маршрут в итоге переводится по имени, при дублях имён действует точка, добавленная **первой** (дети раньше родителя).
- Используется только первый маршрут ресурса.
- Поворот точки в ресурсе целый.
- Путевые точки нужны и для высадки (раздел 11) и для скриптов (`PlaceTemplate` ставит шаблон в позицию точки — см. «Особые случаи» раздела 18).

### Что нужно от движка-носителя
Глобальный реестр именованных точек (регистронезависимый) с поздним связыванием маршрутов по имени.

## 13. Авторские взрывы (руины при загрузке)

### Назначение
Позволить дизайнеру заранее разрушить здания и объекты карты.

### Данные
- Элемент-предмет 189 «Explosion»: позиция (с `DeltaZ`), `Power` — мощность, `Radius` — радиус по зданиям, `ObjStageDelta` — число стадий разрушения для объектов, `ObjRadius` — радиус по объектам, привязка. В базе 1040 таких элементов; типичные значения: мощность 5000, радиус 2–5, дельта 0–3, радиус по объектам 1–2 (у части элементов мощность и радиус пусты).
- Старая таблица `Explosions` (21 запись): позиция, этаж, `DeltaZ`, `Power` (3…2000); радиус по зданиям 10, без воздействия на объекты.

### Алгоритм
1. Взрывы собираются в общий список при обработке элементов узлов (порядок обхода: дети раньше родителя; внутри варианта — сначала элементы, потом записи `Explosions`).
2. После обхода (только при наличии сети) все взрывы поднимаются на рельеф (раздел 9), строятся матрицы зданий.
3. Для каждого взрыва по порядку: каждому зданию карты передаётся «взрыв» (матрица здания, мировая точка, мощность, радиус) — решётка прочности решает сама, что повреждено; обрушение и перестройка — «Мир 2».
4. Если `ObjStageDelta` > 0 и `ObjRadius` > 0: каждому объекту карты, у которого квадрат расстояния до взрыва (по трём осям, в метрах) меньше `(ObjRadius/0,625)²`, увеличить начальную стадию на `ObjStageDelta`.
5. Затем строятся дыры (раздел 14) и сети.

### Формулы
- Условие для объекта: `|p_obj − p_expl|² < (ObjRadius / 0,625)²` — расстояние в метрах сравнивается с радиусом, переведённым в тайлы, то есть фактический радиус = `1,6·ObjRadius` м.

### Особые случаи и прихваты
- Перевод радиуса по объектам в тайлы при сравнении с метрами: радиус 2 действует на 3,2 м, и это сфера (учитывается Z).
- Стадия объекта может превысить число стадий его модели; ограничение — при создании объекта («Мир 3»).
- У взрывов из старой таблицы `Explosions` точка привязки не инициализируется: высота рельефа для них берётся из произвольной точки (значение мусора с зажимом в пределы карты).
- Каждый взрыв передаётся каждому зданию карты, даже далёкому.
- Взрывы из шаблонов, обработанных без сети (подсчёт мест улик), никакого действия не имеют.

### Что нужно от движка-носителя
Возможность применить разрушение к зданиям и объектам до первого кадра (или запечь руины в префаб).

## 14. Дыры в рельефе и стены подвалов

### Назначение
Вырезать в рельефе подвалы зданий и нарисованные дизайнером ямы, получить непересекающиеся области с одной глубиной и вертикальные стенки между уровнями.

### Данные
- Дыра рельефа: многоугольник (тайлы), `nHeight` — смещение поверхности в единицах 1/64 м (отрицательное — вниз), «дно видно».
- Подвал здания (`CBuildInfo.cellar`): булев массив на тайл варианта.
- Итог: список областей `SMapHole` (набор многоугольников, глубина, видимость, этаж 0) и список стен `SMapWall` (отрезок, нижняя и верхняя глубина).

### Алгоритм
**Дыры подвала** (при загрузке рельефа любого варианта, если размер массива подвала равен размеру рельефа варианта W×H):
1. Для каждой клетки подвала добавить её стороны, за которыми нет подвала (или край массива), направленными отрезками так, чтобы клетка обходилась против часовой стрелки: левая (x, y+1)→(x, y), правая (x+1, y)→(x+1, y+1), нижняя (x, y)→(x+1, y), верхняя (x+1, y+1)→(x, y+1). Перебор клеток — x во внешнем цикле, y во внутреннем.
2. Пока отрезки есть: начать новую дыру (глубина −200, дно не видно); взять первый отрезок списка, добавить его начало в многоугольник, удалить; следующий — первый в списке отрезок, начинающийся в конце предыдущего; до тех пор, пока такого нет. Если первая точка совпала с последней — последнюю убрать.
3. Вершины — по одной на каждую единичную сторону (коллинеарные не сливаются).

**Объединение** (`BuildHolesList`, после обхода и взрывов, при наличии сети), список областей изначально пуст; для каждой дыры H по порядку (дыры корня, затем дыры вложенных шаблонов в порядке штамповки):
1. Если многоугольник H обходится по часовой стрелке — развернуть.
2. `src = {H}`; новый список пуст.
3. Для каждой существующей области G: `I = G ∩ src`, `S = G − src`, `O = src − G`. Если I не пусто — область (I, глубина G + глубина H, видимость = (видимость G **равна** видимости H)). Если S не пусто — область (S, глубина G, видимость G). `src = O`.
4. Если src не пусто — область (src, глубина H, видимость H). Список областей = новый список.

**Стены** (`GenerateWalls`), для каждой области A по порядку списка (глубина `hA`):
1. Рёбра A — все рёбра всех её многоугольников.
2. Для каждой области от первой до A **включительно**: удалить рёбра A, у которых есть встречное ребро (те же концы в обратном порядке, допуск 1e-5) в этой области (общие границы с более ранними областями и внутренние рёбра самой A).
3. Для каждой области B после A: для ребра A, у которого есть встречное ребро в B, — стена от `hB` до `hA`, ребро удалить.
4. Оставшиеся рёбра (граница с нетронутой землёй) — стены от 0 до `hA`.

**Булевы операции над многоугольниками** (`ClipPolygon` → пересечение и/или разность):
1. Все точки привязываются к сетке 1/4096 тайла (округление к ближайшему) и объединяются по точному равенству.
2. Каждое ребро каждого многоугольника разрезается в точках пересечения с рёбрами другого набора (для коллинеарных перекрывающихся рёбер — в концах другого ребра); точки пересечения сортируются вдоль ребра. Пересечение в концевой точке ребра не режет его.
3. Внутри многоугольника встречные двойники рёбер помечаются удалёнными.
4. Классификация рёбер: совпадает с ребром другого набора в том же направлении («общее попутное») или во встречном («общее встречное»); в точках, где сходятся рёбра обоих наборов, по угловой сортировке и счётчикам обхода — «внутри»/«снаружи» для одиночных рёбер; метки распространяются вдоль многоугольника; оставшиеся — проверкой середины ребра на попадание в многоугольники другого набора (попадание в многоугольник, обходимый по часовой стрелке, означает «в дыре» и снимает попадание).
5. Сборка результата: для разности — рёбра источника «снаружи» или «общие встречные» (вперёд) и рёбра отсекателя «внутри» или «общие встречные» (назад); для пересечения — «внутри» или «общие попутные» (вперёд). В каждой вершине следующее ребро ищется перебором исходящих рёбер по убыванию угла от входящего (правый поворот) до первого, удовлетворяющего правилу. Многоугольники из двух и менее точек отбрасываются.

**Потребитель** (мир, если у корня `ShowTerrain` = 1; см. `wTerrain.cpp`): рельеф режется на блоки 8×8 тайлов; в каждом блоке для каждой области — её пересечение с квадратом блока рисуется (если дно видно) на высоте «рельеф + глубина» (вершины — билинейная высота плюс глубина, триангуляция «отрезанием ушей»), остаток блока — на высоте рельефа; блок без дыр — обычная решётка, каждый тайл — два треугольника с диагональю (x+1, y)–(x, y+1). Стена — вертикальная полоса вдоль отрезка, разрезанного на каждой линии сетки, от «рельеф + нижняя глубина» до «рельеф + верхняя»; текстура 2, координата u растёт на длину/8 тайлов. По четырём краям карты — «юбки» глубиной 200 единиц (3,125 м) кусками по 8 тайлов, текстура 3693 `Terrain\Wall.tga`. Геометрия рельефа с дырами идёт и в карту ИИ (проходимость, видимость, укрытия).

### Формулы
- Ориентация: многоугольник «вывернут» (по часовой стрелке), если `Σ (y₂ + y₁)(x₂ − x₁) > 0`.
- Привязка точки: `round(4096·x)/4096`.

### Константы

| глубина подвала | −200 единиц = −3,125 м | | `MapBuildTerrain.cpp` |
| видимость дна подвала | нет | | `MapBuildTerrain.cpp` |
| сетка привязки точек | 1/4096 тайла | | `PolyUtils.cpp` |

### Особые случаи и прихваты
- Видимость пересечения двух дыр — **равенство** флагов, а не «и»: две невидимые дыры дают видимую область. Следствие: если у подвала есть «остров» (кусок земли внутри подвала), его внутренний контур, развёрнутый в отдельную дыру, накладывается на внешнюю и даёт видимую яму глубиной −400 (6,25 м). В подвалах обучения островов нет (по одному контуру).
- Глубины перекрывающихся дыр складываются.
- Подвал игнорируется, если размер его массива не совпадает с размером рельефа варианта (например, если файл рельефа отсутствует или другого размера).
- Стены строятся и для невидимых дыр; их текстура — системный шрифт; обычно их закрывают стены подвала здания.
- Тяжёлые случаи булевых операций (касание вершиной, «восьмёрки» подвала при диагонально соседних клетках) обрабатываются эвристически; вывод многоугольников может зациклиться на ошибочных данных (в коде есть защитный выход с отладочным дампом).

### Что нужно от движка-носителя
Дыры в ландшафте (Landscape Hole material/visibility layer) или процедурный меш рельефа; надёжная булева библиотека для многоугольников (например, Clipper2) с привязкой к сетке 1/4096; генерация вертикальных стенок.

## 15. Лестницы

### Назначение
Зарегистрировать в навигационной сети приставные лестницы зданий.

### Данные
`CBuildInfo.ladders`: ID (> 0 — действующая), позиция (x, y в тайлах здания, z — начальный этаж, может быть дробным), сторона 0…3, высота `nHeight` (в шагах сети; см. «ИИ 1»). Поля начальной/конечной высоты и «стороны лазания» в данных не инициализированы и сборщиком не читаются.

### Алгоритм
1. Только для узла-здания при наличии сети, после создания здания.
2. Для каждой лестницы с ID > 0: точка низа = начало группы узла + R(поворот узла)·((x + 1)·0,625, (y + 1)·0,625), что равно `pos + R·(0,625x, 0,625y)` (поправка +1 компенсирует сдвиг группы на −1 тайл); точка «на шаг вверх» = низ + шаг 0,625 по оси узла: сторона 0 → −X, 1 → −Y, 2 → +X, 3 → +Y; этаж = `Float2Int(z + этаж узла)`.
3. Записи копятся в мировых координатах и передаются сети (`CreateLadder`) только в самом конце сборки, когда созданы все группы (иначе лестница рядом с позже созданным зданием попала бы не в ту группу). Дальше — «ИИ 1».

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| поправка позиции | +1 тайл по x и y | | `MapBuild.cpp` |
| шаг к верхней точке | 0,625 м | | `MapBuild.cpp` |

### Особые случаи и прихваты
- Этаж лестницы округляется «к чётному»: лестница с z = −0,5 (полэтажа ниже) получает этаж 0 (пример — «PaintBall Polygon», раздел 19).
- Лестницы в шаблонах без здания (без фрагментов) не регистрируются.

### Что нужно от движка-носителя
Навигационные ссылки (NavLink/Smart Link) с высотой и стороной подъёма.

## 16. Граница карты: пограничные пятна и объекты

### Назначение
Затемнить край и не пустить юнитов за пределы карты.

### Данные
Место корневой группы (раздел 8): начало `(Ox, Oy)`, размер `Nw × Nh` узлов (`W + 3 − 2b`).

### Алгоритм
**Пятна** (если строится рельеф): материал 1904 (шаблон материала 1275 «T_B», текстура 3099 `Terrain\Spots\TestB.tga` 32×64), размер 0,625×0,3125 м, без звука шагов:
- для k = 0…Nw: нижнее — угол `(Ox + (k − 1)·0,625, Oy − 0,625)`, угол 0°; верхнее — `(Ox + k·0,625, Oy + Nh·0,625)`, угол 180°;
- для k = 0…Nh: левое — `(Ox − 0,625, Oy + k·0,625)`, угол 270°; правое — `(Ox + Nw·0,625, Oy + (k − 1)·0,625)`, угол 90°.
Пятна дописываются в конец списка (рисуются последними).

**Объекты** (если строится рельеф): объект 1836 (шаблон объекта 1380 «AIblock», модель 3426, геометрия 3206; в ИИ-геометрии 2096 есть координаты ±2,5 м — блок 5×5 м в плане), созданный генератором со временем системы и пустыми флагами. Позиция Z = 0, этаж 100, масштаб 1, признак «граница»:

- для x = X1, X1 + 5, … пока x ≤ X2: объекты в (x, Y1) и (x, Y2);
- для y = Y1, Y1 + 5, … пока y ≤ Y2: объекты в (X1, y) и (X2, y).
Пограничные объекты не поднимаются на рельеф (добавляются после подъёма). Мир создаёт их только при обычном создании зоны (не при `PlaceTemplate`).

### Формулы
При отступе 0 и ширине W (кратной 8): `X1 = −2,5`, `X2 = 0,625W + 2,5`; блоки 5×5 м ложатся вплотную снаружи края карты (от −5 до 0 и от 0,625W до 0,625W + 5).

## 17. Зона безопасного выхода

### Назначение
Прямоугольник, внутри которого камера может прокручиваться, а выход за который означает «юнит у края карты» (условие ухода из зоны).

### Алгоритм
1. `size = ((Nw − 1)·0,625, (Nh − 1)·0,625)`, `org = (Ox, Oy)` (раздел 16), `e = ExitBorder корня · 0,625`.
2. Зона = `[Ox + e, Ox + size.x − e] × [Oy + e, Oy + size.y − e]`.
3. Мир: прямоугольник ограничивает камеру; юнит «у края», если его точка лежит на границе зоны или вне её (`x ≤ minx`, `x ≥ maxx`, аналогично по y). Уйти из зоны можно в реальном времени, при победе или когда все живые бойцы у края (подробнее — «Мир 1»/«Кампания 1»).

### Формулы
При отступе 0: зона = `[0,625(ExitBorder − 1), 0,625(W + 1 − ExitBorder)] × [0,625(ExitBorder − 1), 0,625(H + 1 − ExitBorder)]`.

### Константы

| Имя | Значение | Смысл | Источник |
|---|---|---|---|
| `ExitBorder` | 4 (у 4702 вариантов) | полоса выхода в тайлах | `TemplVariants` |

### Особые случаи и прихваты
- Зона отсчитывается от начала группы (на тайл раньше карты), поэтому реальная полоса выхода от края карты = (ExitBorder − 1) тайла = 1,875 м при значении 4.

### Что нужно от движка-носителя
Прямоугольные границы камеры и триггер «у края карты».

## 18. Что предвычисляет редактор, а что считается при загрузке

### Назначение
Разделить работу между инструментом и игрой, чтобы на новом движке решить, что «запекать».

### Данные и разделение

| Готовит редактор (на вариант) | Считается при каждой сборке зоны |
|---|---|
| строки БД: шаблоны, варианты, веса, флаги, прямоугольники, элементы, юниты, точки, пятна, взрывы | выбор вариантов по зерну и флагам |
| `Terrain\<V>`: **собственный** рельеф варианта (высоты, альфа, типы, трава, цвет, дыры); пятна в файле дублируются, но игрой не читаются | композиция рельефа дерева (штамповка), материалы пятен, звуковая карта, средний цвет |
| `Buildings\<V>`: фрагменты здания с материалами, лестницы, подвал, комнаты, проецируемые пятна | решётка прочности, части здания (свой генератор), встроенные объекты, дыры подвалов и стены |
| `Waypoints\<ID>`: позиция и команды точки; `Units\<ID>`, `Groups\<ID>`: маршруты по именам | разрешение маршрутов, реестр точек |
| — | мировые позиции, подъём на рельеф, авторские взрывы, навигационные группы и лестницы, граница, безопасная зона |
| — | навигационная сетка: запекается лениво уже в игре («ИИ 1») |
| — | текстуры рельефа по блокам 8×8, трава по секторам 8×8 — на лету при отрисовке |

Редактор хранит у каждого варианта только его собственный слой: превью с вложенными шаблонами он строит тем же кодом сборки (`BuildTerrain` — только рельеф с закреплениями вариантов по прямоугольникам; `BuildMapEditMap` — содержимое подшаблона без рельефа в заданной позиции, с заданным флагом выравнивания и якорем). Подробности — «Карта 2 — Редактор карт.md».

Варианты вызова сборки в игре:

| Кто | Сеть | Зерно | Флаги | Глубина | Уровень | Зачем |
|---|---|---|---|---|---|---|
| создание мира зоны | есть | зерно (зона, шаблон) или время | параметры зоны («Day»/«Night») | без предела | уровень миссии | обычная загрузка |
| подсчёт мест улик при создании зоны (только у зон из 2–3 шаблонов; у зоны из одного шаблона числа берутся из `ScenarioZones.ItemSlots/PersonSlots` без сборки) | нет | то же зерно | пусто | без предела | 0 | сколько мест под улики-предметы и улики-персонажи |
| поиск перехода в другой шаблон зоны | нет | зерно того шаблона | пусто | без предела | 0 | найти объект-переход с нужным номером |
| скрипт `PlaceTemplate(шаблон, точка)` | есть (живая сеть мира) | время | пусто | без предела | 0 | дозагрузка шаблона во время игры |

### Особые случаи и прихваты
- Проходы без сети не штампуют рельеф и потому тратят меньше случайных чисел; после первого же вложенного шаблона с пятнами их поток расходится с настоящей сборкой. Вложенные варианты в подсчёте мест улик и в поиске перехода могут отличаться от реально построенных — число мест под улики берётся по «другой» карте (корень одинаков, он закреплён).
- В проходах без сети флаги пустые (время суток не учитывается), что тоже меняет набор подходящих вариантов.
- `PlaceTemplate`: шаблон строится в начале координат (сеть получает лишнюю группу на месте (−0,625; −0,625) размером с шаблон), высоты элементов берутся из **собственного** рельефа шаблона, затем объекты, предметы, точки и юниты сдвигаются на позицию путевой точки (включая её Z); здания, точки высадки, места улик и подсказок, пограничные объекты при этом не создаются; скрипты шаблона выполняются сразу.

### Что нужно от движка-носителя
Решение: собирать уровень процедурно при загрузке (как оригинал) или запекать результаты сборки на конкретное зерно в редакторе UE (тогда нужен экспортёр, повторяющий алгоритмы разделов 2–17).

## Все прихваты списком

1. Порядок вариантов шаблона = порядок строк при импорте, а не ID; от него зависит результат рулетки.
2. Вес 0 «выключает» вариант; если веса всех подходящих вариантов 0 — берётся первый подходящий без траты случайного числа.
3. Центр прямоугольника переводится в угол при импорте по исходному (дробному) углу, а содержимое поворачивается на угол с отброшенной дробью.
4. Угол ребёнка = `(int)(родитель + прямоугольник + 36000) mod 360`; углы элементов не округляются и не нормализуются.
5. `Rects.Params` во всех данных пусты; `TemplVariants.ColorMap`, `TerrainSpots.Layer`, `FinalElements.RoomParamID/RoomID` не используются.
6. `Border` по умолчанию в схеме 15, в данных 0 (или NULL).
7. ЛКГ 214013/2531011, 15-битный выход, `Get(n) = r·n div 32768`; `GetFloat` использует `Get(65535)` и никогда не достигает верхней границы.
8. Любая рулетка с ненулевой суммой тратит ровно один шаг, даже из одного варианта.
9. `SRand()` без зерна берёт время системы и делает холостой `Get(4)`.
10. Корень зоны предварительно разыгрывается с пустыми флагами тем же зерном, что и сборка: первое число сборки повторяет число выбора корня.
11. В игре закреплён только корень; вложенные шаблоны разыгрываются всегда. Закрепления по прямоугольникам (`nPinID`) — только в редакторе и только в памяти.
12. Флаги сравниваются точным равенством множеств; нет подходящих вариантов — поддерево молча пропускается (с рельефом, объектами, юнитами).
13. Пустые флаги (зона без времени суток) допускают и ночные, и дневные варианты.
14. Время суток для сборки не разыгрывается; случайный выбор Day/Night делается только для флагов мира (освещение).
15. Проходы сборки без сети (подсчёт мест улик, поиск перехода) не штампуют рельеф, не тратят шаги на пятна и строятся с пустыми флагами — их вложенные варианты могут отличаться от реальной карты.
16. Части здания, встроенные окна и двери, пограничные объекты и материал подложки травы выбираются генераторами со временем системы — не воспроизводятся зерном карты.
17. Пятна сортируются по приоритету неустойчивой сортировкой (для > 16 пятен порядок равных не гарантирован).
18. Текстура блока тратит по 96 случайных чисел на каждое покрытие таблицы `TerrainTiles`, даже отсутствующее в блоке; зерно блока = `y0·nWidth + x0`.
19. Поворот покрытия на 270° никогда не выпадает (`Get(3)`); половина розыгрышей (нечётные столбцы) не используется.
20. Высота элемента — билинейная выборка карты высот с отбрасыванием промежуточной дроби до uint16, а не высота нарисованных треугольников (диагональ (x+1, y)–(x, y+1)).
21. Всё внутри здания и вложенных в него шаблонов поднимается на высоту рельефа в центре **самого внешнего** шаблона-здания; «Main Map (Tutorial)» сам является зданием (18 солидов), поэтому привязка всей учебной карты — точка (25; 30).
22. `Floor·2,5` и `DeltaZ` прямоугольников по пути складываются.
23. Размер корня округляется вверх до кратного 8, минимум 2; недостающие узлы — высота 0, тип 11, белый цвет; копируется только перекрывающаяся часть от угла [0][0].
24. Тип 11 «Transparent» — настоящее покрытие с белой текстурой; при штамповке не переписывает родителя.
25. Штамповка перебирает узлы с поправкой «центра клетки» ±0,5 → повёрнутый штамп сдвинут на `R(φ)(½,½) − (½,½)` тайла относительно зданий, объектов и дыр того же варианта (90°: на −1 по X).
26. Билинейная выборка зажата до «размер − 1,01» и отбрасывает дробь промежуточных значений: точка почти на узле может прочитать значение на 1 меньше.
27. Add/Subtract заворачиваются по модулю 65536 (без насыщения).
28. Альфа 0 делает высоты варианта невидимыми в любом режиме; альфа 0xFEFE вместо 0xFFFF занижает рельеф на 0,39%.
29. Цветовые карты вложенных шаблонов не штампуются (код закомментирован) — цвет только из корня.
30. Плотность травы ребёнка заменяет (не складывает) плотность слоя с тем же ID в прямоугольнике ребёнка.
31. Ребёнок, больший корня и по ширине, и по высоте, не штампуется вовсе (ни высот, ни дыр, ни пятен).
32. Пятна, сохранённые в файле рельефа, игнорируются: используются записи `TerrainSpots`.
33. Каждый штамп перебирает весь массив корня, даже для куста 2×2.
34. Подвал превращается в дыры, только если размер массива подвала равен размеру рельефа варианта.
35. Глубина подвала −200 единиц (−3,125 м), дно невидимо.
36. При объединении видимость пересечения = равенство флагов: две невидимые дыры дают видимую область; глубины складываются (остров внутри подвала стал бы видимой ямой −400).
37. Стены дыр строятся и для невидимых дыр и текстурируются записью 2 — `Fonts\System.tga`.
38. Точки многоугольников привязываются к сетке 1/4096 тайла; совпадение рёбер стен — с допуском 1e-5.
39. Дыры переносятся точным поворотом (в отличие от высот).
40. «Тот же поворот» проверяется только по синусу узла: θ, 180° − θ и 90° − θ считаются совпадающими.
41. Совпадение начала проверяется со всеми предками, включая шаблоны без собственной сетки.
42. Допуск начала группы — 0,001 тайла с округлением к ближайшему; дробный центр прямоугольника («GuardHouse» обучения) порождает отдельную повёрнутую сетку и предупреждение о флаге `Grid`.
43. Этажи здания вычисляются без учёта поворотов фрагментов и перезаписываются в общем описании варианта.
44. Фоновый свет объектов теряется, если узел — не здание.
45. Лестницы: поправка +1 тайл, этаж округляется к чётному (z = −0,5 → 0), регистрация — после создания всех групп.
46. `DC = Float2Int(Power)`; граната элемента → `DC = 7L + 16`; сундук → прочность замка `7L + 16` вместо значения из базы; случайная прочность `3(Get(20) + 2L) − 3` может быть отрицательной.
47. Предметы сундука: двойное вычитание центра по Z, отдельный статический генератор моделей, розыгрыш клетки 3×3 впустую.
48. Радиус воздействия авторского взрыва на объекты сравнивается в тайлах с расстоянием в метрах → фактически 1,6·`ObjRadius`, сфера с учётом Z.
49. Взрывы старой таблицы `Explosions` имеют неинициализированную точку привязки и радиус 10.
50. Каждый взрыв передаётся каждому зданию карты.
51. `LightParam` по умолчанию «Night»: у 42 тыс. элементов свет только ночью.
52. Юнит-место улики-персонажа без назначенной улики не создаётся вовсе.
53. `Units.Diplomacy` игнорируется; дипломатия — из таблицы варианта корня.
54. Из ресурса маршрутов берётся только первый маршрут.
55. Таблица имён сборщика хранит последнюю точку имени, реестр мира — первую; маршрут переводится по имени, поэтому действует первая.
56. Неразрешённые имена маршрута выбрасываются с сообщением в лог.
57. Номер точки-объекта в списке = номер партии игрока.
58. Режим «по точке на бойца» ищет номера, которых не бывает, и ставит всех на запасную клетку (1, 8).
59. Схема «UnitHero/Unit1…9» важнее точек-объектов; лишние бойцы встают в «UnitHero».
60. Поиск места у точки: 0,63 → 1,26 → 2,52 м; берётся место с наименьшим этажом.
61. Отряд строится 3×3 вокруг точки (`(d+4) div 3 − 1`, `(d+4) mod 3 − 1`), лицом к центру карты.
62. Зона «ETStore», шаблон 2291: высадка из перехода в точки `Unit<i>_l` / `Unit<i>_g`, пригнувшись.
63. Пограничные пятна добавляются после звуковой карты и при `Border` = 0 лежат вне рельефа — невидимы.
64. Блоки «AIblock» 5×5 м стоят на Z = 0, этаж 100, угловые — дважды.
65. Безопасная зона отсчитывается от начала группы (на тайл раньше карты): полоса выхода = `ExitBorder − 1` тайлов.
66. Пятно переписывает звук шагов в своём прямоугольнике даже пустым значением (сброс на материал по умолчанию); запрос — по ближайшему узлу.
67. Отбор травинки: после 63 неудач используется последняя точка.
68. Зерно сектора травы зависит от индекса слоя в списке рельефа.
69. Трава ставится на геометрию рельефа: над невидимым дном подвала её нет.
70. Корень с `ShowTerrain` = 0 не создаёт рельеф вовсе (подземные зоны).
71. `NoAttack`, `Weather`, `ShowTerrain`, освещение, диапазон этажей среза — только от варианта корня.
72. `PlaceTemplate` строит шаблон в начале координат (лишняя навигационная группа), высоты берёт из собственного рельефа шаблона, зданий и точек высадки не создаёт.
73. Зерно шаблона зоны — время системы в момент создания зоны: шаблоны одной зоны (и зоны, созданные в один квант таймера) получают одинаковое зерно.
74. Цветовая карта умножает текстуру как `(c + 1)/256`, через инвертированную маску поверх чёрного.
75. Подложка травы и колыхание — чисто визуальные, но сам готовый рельеф (с плотностью травы) передаётся при создании мира трекеру видимости, который строит по нему карту заслонения травой (потребитель вне этого среза — «Мир 1»).

## Примеры

### Пример 1. Штамп «HeightMapPost Office» (режим Add) в склон зоны GCom

Цепочка из базы: зона 67 «GCom» (TimeOfDay «Day») → шаблон 2900 «GCom» 128×72, вариант 5004 (корень; рельеф 1×1 → после приведения размеров все высоты 0, типы 11) → прямоугольник 23783: шаблон 2304 «CompleteGCom» 128×72, центр (64; 35,999996), 0°, вариант 3858 (Normal; высоты 238…477, альфа 65278 = 0xFEFE почти везде) → прямоугольник 18497: шаблон 2177 «Post Office» 50×30, центр (16,999998; 45), поворот 90°, `DeltaZ` 1,25, вариант 3706 (**Add**, высоты 0…159, но альфа вся 0) → прямоугольник 19339: шаблон 2427 «HeightMapPost Office» 4×2, центр (22; 7), 0°, вариант 4077 (**Add**).

Позиции:
1. «CompleteGCom»: угол = (40; 22,4999975) − (40; 22,5) = (0; −2,5·10⁻⁶), 0°. Штамп Normal: каждый узел = `Float2Int((1 − 65278/65535)·0 + 0,99608·h)`; авторские 399 → **397**, 477 → 475. (Альфа 0xFEFE вместо 0xFFFF занижает весь рельеф на 0,39%.)
2. «Post Office»: угол = (10,625; 28,125) + R(90°)(−15,625; −9,375) = (10,625 + 9,375; 28,125 − 15,625) = (20; 12,5), Z = 1,25, поворот 90°. Режим Add с альфой 0 — высоты не меняются; дыра подвала (700 клеток, контур 128 вершин) переносится.
3. «HeightMapPost Office»: локальный угол = (13,75 − 1,25; 4,375 − 0,625) = (12,5; 3,75); повёрнут на 90° → (−3,75; 12,5); мировой угол = (16,25; 24,9999975), Z = 1,25, поворот 90° (0 + 90 + 0). В тайлах `X0 = 26`, `Y0 = 39,999996`.

Источник (вариант 4077), строки — y, столбцы — x:

| y \ x | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| высоты y=0 | 79 | 79 | 79 | 79 | 78 |
| высоты y=1 | 79 | 79 | 79 | 79 | 78 |
| высоты y=2 | 79 | 79 | 78 | 78 | 78 |
| альфа y=0 | 65278 | 65278 | 65278 | 65278 | 65278 |
| альфа y=1 | 65535 | 65535 | 65278 | 65278 | 65278 |
| альфа y=2 | 65535 | 65535 | 65278 | 65278 | 65278 |

Перебор: `x = nY − 39,999996`, `y = 25 − nX` → обрабатываются узлы nX = 23…25, nY = 40…44 (точный поворот узлов дал бы nX = 24…26 — сдвиг на один узел из-за поправки ±0,5).

Высоты (единицы 1/64 м) до → после; столбец 26 — собственный «гребень» в данных «CompleteGCom» (477/476 → 475/474 после Normal), штамп его не трогает:

Разбор двух узлов:

### Пример 2. Выбор вариантов: веса, флаг, закрепление, шаги генератора

Пусть случайная встреча стартует на шаблоне 2497 «EnglandClearing» (варианты в порядке импорта: 4180 вес 60, 4181 — 30, 4182 — 10, 5937 — 5, 5938 — 30) и `GetTickCount()` вернул 1000.

Шаги ЛКГ с зерном 1000:

| № | состояние до | состояние после | r = (s >> 16) & 0x7FFF | `Get(65535)` = 2r − 1 |
|---|---|---|---|---|
| 1 | 1000 | 216544011 | 3304 | 6607 |
| 2 | 216544011 | 538833314 | 8221 | 16441 |
| 3 | 538833314 | 1759629789 | 26849 | 53697 |
| 4 | 1759629789 | 920050988 | 14038 | 28075 |
| 5 | 920050988 | 98940735 | 1509 | 3017 |

1. **Предварительный розыгрыш корня** (миссия, отдельный генератор с зерном 1000, флаги пусты): рулетка m = [0; 60; 90; 100; 105; 135]; шаг 1: f = 135·6607/65535 = 13,610; поиск: c = 2 (90) → 13,61 < 90 → e = 2; c = 1 (60) → e = 1; ответ 0 → **вариант 4180**.
2. **Сборка** (новый генератор, снова зерно 1000). Корень закреплён (ID 4180 > 0) — шаг не тратится. У 4180 нет пятен — шагов нет.
3. Первый прямоугольник 4180 → шаблон 1250 «completeRandom3» (один вариант 2251, вес 1). Пусть параметры миссии {«Day»} → флаги {6}; они непусты → подходящие: 2251 (флаги пусты) → рулетка [0; 1]; шаг 1 (тот же r = 3304, что выбрал корень): f = 0,1008 → вариант 2251. У 2251 пятен нет.
4. Его прямоугольник → шаблон 676 «baseRandom3» (вариант 1452, вес 1): шаг 2, f = 16441/65535 = 0,2509 → 1452. Штамповка 1452: 11 пятен → по шагу на каждое пятно, у шаблона материала которого есть подходящие варианты с ненулевым весом (шаги 3…13, если таковы все). Затем два прямоугольника 1452, затем элементы 1452, затем элементы 2251…
5. Шаблоны солдат «AlliedSoldier» 2349 (вариант 3930 — вес 1, ещё 11 вариантов с весом 0): рулетка [0; 1; 1; …; 1]; любое f ∈ [0; 1) даёт индекс 0 → 3930, но шаг тратится.

Фильтр по флагу (шаблон 344 «16x16» из базы: 810, 811 «5» Ночь, 813 «6» День, 887, 7765, 7913, 7966, все с весом 1), если бы ему достался шаг 2 (g = 16441):
- флаги {6}: подходят 810, 813, 887, 7765, 7913, 7966 → f = 6·16441/65535 = 1,505 → индекс 1 → **813**;
- флаги {5}: подходят 810, 811, 887, 7765, 7913, 7966 → индекс 1 → **811**;
- флаги пусты: все 7 → f = 7·16441/65535 = 1,756 → индекс 1 → **811** (дневной вариант тоже участвует и мог бы выпасть).

Настоящий шаблон с флагом в боевых картах — 2229 «Base_GTVip» (один вариант 3775 с флагом «6») в зонах GTVip (TimeOfDay «Day»): при {6} — рулетка из одного сектора, один шаг; при {5} подходящих нет — поддерево базы не строится и шаг не тратится.

Закрепление в редакторе: при построении превью рельефа прямоугольник, у которого `nPinID` < 0, разыгрывает вариант тем же генератором и запоминает его ID; следующие построения используют этот ID без розыгрыша, пока закрепления не сброшены.

## Отклонения реконструкции от оригинала

Пометок `[FORK]` в файлах среза нет. Изменения, которые автор реконструкции описывает как свои исправления или как отличие от оригинала:

1. Предмет добычи сундука без модели: оригинал разыменовывает модель предмета без проверки (падение игры); реконструкция пропускает геометрию, сохраняя поток случайных чисел (`MapBuild.cpp`, раскладка сундука).
2. Оружие в руках юнита: оригинал выбирает `Get(размер)` из списка даже после того, как все записи (только магазины или пустые) удалены, — чтение за границей массива; реконструкция в этом случае предмет в руки не выдаёт (`MapBuild.cpp`, `AddSimpleElements`).
3. Свет элементов: в релизе элемент несёт целое окно активности (`eTimeOfDay`, 0/5/6) и свет переключает мир. Реконструкция дополнительно читает строковый столбец редактора `LightParam` (поле разработки, которого в релизе нет) и, если строка непуста, гасит точечный свет ещё при сборке, когда флаги карты не содержат атрибута света. С релизным `game.db` строка пуста и ветка не работает; с базой редактора (`A5GAME.sqlite`) работает ветка гашения — это поведение версии разработки, а не релиза.
4. Реестр путевых точек: в релизе он вынесен в отдельный класс-основу мира (клонирует точку, сдвигает на смещение мира, приводит имя к нижнему регистру, первая побеждает). В реконструкции этот класс добавлен, но не подключён; работает встроенный в мир реестр с той же логикой «нижний регистр, первая побеждает», без клонирования и сдвига.
5. Восстановленные по релизу места, где версия разработки отличалась (в реконструкции уже как в релизе; на новом движке делать как здесь описано): проверка «кратно тайлу» с округлением к ближайшему и допуском 0,001 (в разработке — отбрасывание и 1e-4); регистрация лестниц в мировых координатах в конце сборки (в разработке — по номеру группы во время обхода); шаблон освещения хранится как шаблон (розыгрыш при каждом обращении мира); поля `NoAttack`/`MinCutFloor`/`MaxCutFloor`/`Weather`/`ExitBorder` варианта; ссылки на музыку как пулы `MusicTemplates`; нулевой сдвиг «опоры» для стен и неповёрнутых солидов; зажим построения отряда в пределах слоя (`GetDeployPlace`).
