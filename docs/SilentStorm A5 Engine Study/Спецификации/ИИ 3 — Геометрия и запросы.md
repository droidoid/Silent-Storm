# ИИ 3 — Геометрия столкновений и пространственные запросы

## Суть

У каждого объекта мира, кроме видимой модели, есть упрощённая «ИИ-геометрия»: набор замкнутых треугольных тел («кусков»). Все такие тела лежат в одном общем хранилище — «ИИ-карте» (рыхлое октодерево). К карте задают вопросы: «что пересекает этот луч и на каких отрезках» (пули, выбор мышью), «что пересекает пучок из сотен лучей» (укрытия, карта высот, проходимость), «какие вокселы куба заняты» (взрывы, видимость), «поместится ли здесь шар радиусом с человека» (проходимость, полёт гранаты), «куда скатится шар» (обломки, трупы). Вокруг карты построены подписки («трекеры»): кто-то заявляет «мне интересна эта область и эти типы тел», и карта сообщает, когда там что-то изменилось; так лениво пересчитываются кубы видимости, кубы взрывов, навигационная сетка и «сторож устойчивости», роняющий трупы, обломки и мины, из-под которых исчезла опора.

Главные идеи: (1) луч не пересекают с треугольниками в 3D, а проецируют геометрию на плоскость, перпендикулярную лучу, и смотрят знаки рёбер; (2) результат — не «первая точка попадания», а список интервалов «вошёл/вышел» с указанием брони, что даёт толщину материала; (3) пучки лучей считаются программным растеризатором треугольников; (4) тест «шар помещается» заранее запечён в битовые сетки с шагом 10 см; (5) видимость считается по воксельным кубам с двумя битами на воксел — «непрозрачно» и «полупрозрачно» — с бюджетом полупрозрачности, зависящим от дальности.

## Термины и единицы

| Термин | Значение |
|---|---|
| Метр | Единица мировых координат. Шаг тайловой сетки `FP_GRID_STEP` = 0,625 м. Высота ландшафта хранится в 1/64 м (`FP_TERRAIN_H_SCALE`). |
| ИИ-геометрия | Запись таблицы `AIGeometries` + ресурсный файл с тем же ID: куски, шары масс, запечённые сетки. |
| Кусок (piece) | Замкнутое треугольное тело с собственным номером (ID куска); у юнита — часть тела, у здания — фрагмент стены. |
| Корпус (hull) | Экземпляр геометрии на ИИ-карте: геометрия + матрица положения + «источник» (объект-владелец, броня, этаж, флаги). |
| Источник (SSourceInfo) | Четвёрка: указатель на объект-владельца (пусто = ландшафт), броня (`RPGArmors`), номер этажа, битовая маска флагов TS_*. |
| UserID | Номер, который возвращается в результате запроса вместе с источником: обычно ID куска, но может быть переназначен (ID фрагмента стены, часть тела). |
| Интервал | Пара «вход/выход» луча в одно тело: параметры t и нормали. |
| Трекер | Подписчик на изменения ИИ-карты в заданном объёме по маске флагов. |
| Float2Int | Округление к ближайшему целому (режим FPU по умолчанию, «банковское» на половинках). Все формулы вида `Float2Int(x − 0.5)` означают «номер ячейки, в которую попал x». |
| F_INF | 1e30 — «значение не заполнено» в растеризаторе; ±1e10 — «бесконечность» для открытых поверхностей. |

## 1. Объект ИИ-геометрии и его файл

### Назначение
Хранить упрощённую форму объекта в виде, удобном сразу для трёх потребителей: трассировки лучей (нужны рёбра), растеризации (нужны треугольники) и теста шара (нужна запечённая сетка).

### Данные
Геометрия (`CGeometryInfo`):
- `pieces` — словарь «ID куска → кусок»;
- `bound` — общий ограничивающий объём (центр, радиус сферы, полуразмеры коробки) по всем точкам;
- `spheres` — «шары масс»: центр, радиус, масса;
- `massCenter` — центр масс = взвешенное по массе среднее центров шаров; масса ≤ 0 при загрузке заменяется на 1.

Кусок:
- `points` — вершины в локальных координатах;
- `edges` — список уникальных рёбер (пара 16-битных индексов вершин) и список треугольников, где каждый треугольник — три ссылки на рёбра; старший бит (0x8000) ссылки означает «ребро проходится в обратном направлении»;
- флаг «замкнут» (для ландшафта — «не замкнут»);
- `fVolume` — объём (число из файла; в срезе только хранится);
- `juncs` — «стыки»: точка + признак «стык с землёй» (в срезе только хранятся; используются разрушаемостью);
- `precalc` — список запечённых сеток шара (раздел 2).

Построение списка рёбер из обычных треугольников (индексы вершин):
1. Вырожденный треугольник (два одинаковых индекса) пропускается.
2. Для каждой стороны ищется уже существующее ребро с теми же концами; найдено в том же направлении — ссылка без бита, в обратном — с битом 0x8000.
3. Новое ребро хранится в каноническом направлении: начало — вершина с меньшим x; при равенстве — с меньшим y; затем с меньшим z. Если исходное направление пришлось перевернуть, ссылка получает бит 0x8000.
4. Восстановление вершин треугольника из рёбер: первые две вершины — концы первого ребра (с учётом бита), третья — «дальний» конец второго ребра.

Тело замкнуто, если каждое ребро использовано одинаковое число раз в обе стороны (счётчик +1/−1 по каждой ссылке равен нулю). Есть служебная разбивка тела на связные замкнутые оболочки (обход по незакрытым рёбрам).

### Формат файла (насколько виден загрузчику)
Ресурс `AIGeometries`, ключ — ID записи. Чанковый формат «номер → значение»:

| Чанк | Содержимое |
|---|---|
| 1 | вершины (если кусков нет) |
| 2 | треугольники (если кусков нет) |
| 4 | словарь «ID куска → запись куска» |
| 6 | шары масс |
| 9 | запечённые сетки для бескускового случая |

Запись куска: 1 — вершины, 2 — треугольники, 3 — веса костей (читаются, обычным загрузчиком не используются), 10 — объём, 11 — стыки, 13 — список запечённых сеток. Если словарь кусков пуст, создаётся один кусок с ID 0. Ошибка чтения молча даёт пустую геометрию.

Скелетные модели читают тот же файл иначе (`CFileSkinPoints`): из чанка 4 берутся части тела «ID → вершины, треугольники, веса», из чанка 6 — шары масс. Веса приводятся к виду «до 4 костей на вершину».

Ещё два источника геометрии: «объект из памяти» (редакторные меши: вершины склеиваются по точному равенству координат, один кусок с ID −1; ломаные линии на карту не попадают) и кусок ландшафта (вершины: x,y × 0,625, z × 1/64; один незамкнутый кусок с ID −1, запечённой сетки нет).

### Скиннинг (подвижные тела)
`CSkinner` — ленивый вычислитель: пересчитывается только если изменилась поза или исходные точки. Для каждой вершины: результат = Σ весⱼ · (матрица_костиⱼ · точка), перебор весов останавливается на первом нулевом весе или после четырёх. Затем пересчитывается общий объём. После этого либо запекаются сетки шара заново (режим «создать»), либо подставляется заранее заданный набор сеток по кускам (режим дверей), либо ничего (юниты).

### Константы
| Имя | Значение | Смысл |
|---|---|---|
| бит 0x8000 | — | ребро в обратном направлении; отсюда предел 32767 рёбер на кусок |
| ID 110 / 111 / 118 / 150 | — | номера кешей ресурсов: геометрии, скин-точки, привязки костей, дверные сетки |
| порог 6 кусков | 6 | служебная функция выдачи геометрии по ID для геометрий с более чем 6 кусками отдаёт только кусок 0 (прихват) |

### Особые случаи
- Кусок без треугольников не создаётся.
- После загрузки у каждой запечённой сетки объём пересчитывается из её `ptMin/ptMax`.
- Шары масс без модели/геометрии — пустой список; потребители трактуют это как «устойчив».

### Что нужно от движка-носителя
Чанковое чтение ресурсов, кеш «ID → лениво загружаемый объект» с отметкой «изменился», матрицы костей от анимационной системы.

## 2. Запечённые сетки «шар помещается» (CPrecalcSpheres)

### Назначение
Мгновенно отвечать «коснётся ли шар радиуса 0,31 м (условный человек) этого тела, если центр шара в точке P», а также то же для движущегося шара. Используется при построении проходимости и проверке траектории гранаты.

### Данные
Один блок: двумерный массив 32-битных слов `isCollided[y][x]` (бит z = слой по высоте), точки `ptMin`, `ptMax` и ограничивающий объём. Блок покрывает не более 32 слоёв по Z (3,2 м); высокое тело представлено стопкой блоков.

### Алгоритм запекания
1. Коробка по всем вершинам куска (в локальных координатах) расширяется на 0,31 по каждой оси.
2. Размер сетки: `nX = Float2Int(полуразмерX · 20 + 1)`, `nY` аналогично (ячейка 0,1 м).
3. `ptMin.xy` = минимум коробки; `ptMin.z` = низ коробки + номер_блока · 3,2.
4. `nZ = Float2Int((верх − ptMin.z) · 10 + 1)`; если больше 32 — обрезается до 32 и запрашивается следующий блок.
5. Для каждой ячейки (x,y,z) берётся её центр `ptMin + (i + 0,5) · 0,1`; бит ставится, если шар радиуса 0,31 с этим центром пересекает хотя бы один треугольник куска (тест «треугольник–шар», раздел 9).
6. `ptMax.xy` = максимум коробки, `ptMax.z = ptMin.z + nZ · 0,1`; объём блока пересчитывается из min/max.

### Запросы
Статический: индекс по каждой оси `Float2Int((p − ptMin) · 10 − 0,5)`; вне сетки (беззнаковое сравнение, для Z — предел 32) → «нет»; иначе значение бита.

Движущийся (из p1 в p2):
1. Вектор сдвига переводится в ячейки (×10), длина L.
2. Если L < 1 — выполняется статический тест в p1.
3. Иначе `nSteps = Float2Int(L + 1)`, шаг = 1/nSteps; проверяются точки p1 + i·шаг·сдвиг для i = 0…nSteps−1. Конечная точка p2 не проверяется.

### Коллайдер на сетках (CCollider)
Подготовка: задаётся объём интереса и «размер элемента»; ИИ-карта отбирает корпуса по маске и сфере объёма и передаёт их коллайдеру. Для каждого корпуса:
1. Корпуса ландшафта (без объекта-владельца) отбрасываются; объекты из списка игнорируемых отбрасываются.
2. Считается мировая коробка по преобразованным вершинам.
3. Если запечённых блоков нет — они запекаются на лету (дорого).
4. Каждый блок становится отдельной «сущностью» с обратной матрицей и общей коробкой корпуса, расширенной на 0,31; сущность кладётся в иерархическую сетку (раздел 9, «контейнер объёмов»).

Запрос «движущийся шар» (центр, радиус, сдвиг): коробка движения (центр = середина пути, полуразмеры = |сдвиг|/2); выборка из контейнера по этой коробке, расширенной на радиус; для каждой сущности — пересечение коробки движения (нерасширенной) с её коробкой; центр и сдвиг переводятся в локальные координаты; движущийся тест по сетке. Запрос «шар в точке»: выборка, проверка «центр внутри объёма сущности», статический тест.

Результат отдаётся «анализатору»: функция, получающая источник и UserID и возвращающая «хватит». Простейший анализатор — «было ли столкновение». Дверной анализатор (соседний файл) копит по каждой двери, задет ли её «открытый» и «закрытый» корпус, и блокирует, только если задеты оба.

### Двери: наборы по стадиям разрушения
Ресурс `AIBSPTrees` (историческое имя), ключ — ID двери из таблицы `Doors` (194 записи). Чанк 3 и чанк 4 — два массива по стадиям разрушения; элемент массива — словарь «ID куска → один блок сетки». При регистрации двери на карту создаются два статических корпуса со скиннером, замороженным на нулевом кадре анимации: первый — кадр анимации «активация» (дверь закрыта), флаг `TS_STATE_CLOSED`, набор сеток из чанка 3; второй — кадр «деактивация» (открыта), флаг `TS_STATE_OPEN`, набор из чанка 4. Стадия разрушения, превышающая размер массивов, заменяется последней доступной (с отладочным сообщением). Если набора нет — сетки запекаются на лету.

### Константы
| Имя | Значение | Смысл |
|---|---|---|
| F_PRECALC_STEP | 0,1 м | ячейка сетки |
| F_INV_PRECALC_STEP | 10,0 | обратная величина, отдельный литерал |
| F_TEST_SPHERE_RADIUS | 0,31 м | радиус запечённого шара и расширение коробок |
| 20,0 и +1 | — | число ячеек = полуразмер·20 + 1 |
| 32 | — | слоёв по Z в блоке (3,2 м) |
| F_GRENADE_SPHERE_RADIUS | 0,25 м | радиус шара гранаты у вызывающего кода (см. прихваты) |

### Особые случаи и прихваты
- Радиус шара в запросе влияет только на предварительную выборку; сам тест всегда отвечает за радиус 0,31. Граната с радиусом 0,25 фактически проверяется как 0,31.
- Сетка отмечает только слой около поверхности: точка глубоко внутри толстого тела (дальше 0,31 от любого треугольника) считается свободной.
- Масштаб корпуса не учитывается в радиусе (центр просто переводится обратной матрицей).
- У юнитов запечённых сеток нет; их корпуса не имеют флага проходимости и в такие коллайдеры не попадают.
- В скиннере при подстановке готового набора у куска остаётся ровно один блок (стопка не поддерживается) — двери выше 3,2 м по локальной Z обрежутся.
- Соответствие «чанк 3 = открыто / чанк 4 = закрыто» в именах реконструкции противоречит флагам, с которыми эти наборы регистрируются (см. «Не установлено»).

### Что нужно от движка-носителя
Офлайн-инструмент запекания (или запекание при загрузке), хранение битовых сеток, обратные матрицы объектов.

## 3. ИИ-карта: октодерево корпусов

### Назначение
Единое хранилище всех корпусов с быстрым отбором по объёму, маске флагов, этажам и состоянию дверей.

### Данные
Узел октодерева: сфера-граница, размер ребра, 8 дочерних ссылок, ссылка на родителя; массив слотов корпусов (корпус, копия флагов, этаж), параллельный массив их объёмов, голова списка свободных слотов (свободные слоты связаны через поле флагов; −1 = конец), список трекеров, накопленный «объём изменений» и «маска изменений».

Корпус: узел и индекс слота, геометрия (ленивый вычислитель), матрицы прямая/обратная, список соответствий «ID куска → UserID» (пусто = все куски, UserID = ID куска), источник. Динамический корпус дополнительно имеет вычислитель объёма и «датчик изменения позы».

Карта: корень, список динамических корпусов, объединённая маска всех трекеров, максимальный номер этажа, сторож устойчивости, реестр «объект → его корпуса».

### Алгоритм размещения
1. Корень: куб с углом (−128, −128, −128) и ребром 1024 м; создаётся при первом обращении.
2. Сфера узла: центр = центр куба, радиус = ребро · 1,299038 (= 1,5 · √3 / 2 — «рыхлость» 1,5).
3. Спуск для объекта (центр C, радиус R): остановиться, если ребро ≤ 4 м или R ≥ ребро · 0,21650635 (= √3/8); иначе выбрать дочерний октант сравнением C с центром узла (≥ по каждой оси → старшая половина), создать его при необходимости (ребро вдвое меньше) и повторить.
4. Оценка объёма статического корпуса: центр = преобразованный центр объёма геометрии, радиус = радиус геометрии с учётом масштаба матрицы; коробка = куб с полуразмером R.
5. Корпус занимает слот узла; узел запоминает флаги и этаж корпуса у себя (отбор не трогает сам корпус).

Смысл констант: объект с радиусом меньше 0,433 ребра родителя спускается в дочерний узел; расстояние от центра дочернего куба до центра объекта ≤ 0,866 ребра, плюс радиус < 0,433 ребра → всегда внутри рыхлой сферы 1,299 ребра. Поэтому при отборе достаточно проверять сферу узла.

### Добавление корпусов (интерфейс посетителя)
| Вызов | Что создаёт |
|---|---|
| статический корпус по записи геометрии | один корпус, все куски; пропускается, если файла геометрии нет |
| корпус из «объекта в памяти» | один корпус, всем кускам назначается заданный UserID |
| набор кусков | один корпус с явной таблицей «кусок → UserID»; отсутствующие куски пропускаются; пусто — корпус не создаётся |
| кусок ландшафта | корпус без владельца, единичная матрица |
| анимированный корпус (юнит) | динамический корпус: скиннер, единичная матрица, объём от скелета; в дерево попадает при первой синхронизации |
| «перекидной» корпус (дверь/окно) | два статических корпуса (см. раздел 2); если «прозрачен в открытом виде», у открытого снимается `TS_VISION` |

Каждое добавление повышает «максимальный этаж» и расширяет мировой ящик сторожа устойчивости.

### Отбор корпусов
Рекурсивно от корня: узел отбрасывается, если тест объёма не проходит для его сферы. Для каждого занятого слота: (флаги & маска) ≠ 0; этаж подходит; фильтр дверей: корпус берётся, если запрошены оба состояния, либо у него нет битов состояния, либо есть бит «действующий». Затем тест объёма для сферы самого корпуса; геометрия обновляется (здесь срабатывает ленивый скиннинг); каждый кусок превращается в описание «точки, рёбра, матрицы, источник, UserID, сетки» и попадает в список «объекты» или «ландшафт» (по наличию владельца).

Фильтр этажей: минимальный этаж −3. Пустой набор этажей = все. Иначе строится таблица «этаж → брать»; запрошенные этажи выше максимального игнорируются; если ни одного действительного — результат пуст. Этаж вне таблицы считается подходящим.

Прочие запросы:
- «все сущности по маске» — список преобразованных в мир вершин и треугольников с ID куска, ID брони, флагами;
- «пересекает ли шар что-нибудь» — отбор по сфере, затем честный перебор всех треугольников тестом «треугольник–шар» в мировых координатах; можно исключить одного владельца (в коде помечено «медленная реализация»);
- «центр части тела» — центр сферы по точкам нужного куска (или центр всей геометрии, если куска нет), переведённый в мир; ложь только при отсутствии корпуса;
- «доступные части тела» — куски, центр которых ближе заданного расстояния от точки;
- «объём объекта» — объединение объёмов всех его корпусов;
- «положение окна» — центры закрытого и открытого корпусов (нужно ровно два корпуса);
- «указатели корпусов в объёме» — с маской включения и маской исключения, с фильтром дверей, без фильтра этажей; сравнивается сохранённый объём слота.

## 5. Двери, синхронизация и трекеры

### Двери
Дверь — два корпуса с одним владельцем. Переключение: обход всего дерева; у корпусов этого владельца с битами состояния бит `DOOR_HULL_VALID` ставится тому, чьё состояние совпало с новым, и снимается у другого; копия флагов в слоте обновляется; затем немедленное оповещение трекеров по оценочному объёму корпуса с признаком «переключение двери».

### Трекеры
Трекер регистрируется объёмом, маской и признаком «сообщать о переключении дверей»; кладётся в узел, выбранный тем же правилом спуска по сфере объёма, и никогда не перемещается. Карта копит объединение масок всех трекеров.

Два пути оповещения:
1. Отложенный (добавление, удаление, смена объёма корпуса, движение анимированного корпуса). Событие «объём B, флаги F» поднимается к корню и спускается по всем узлам, сфера которых пересекает B: в узле маска изменений объединяется с F, объём изменений расширяется до объединяющей коробки. При синхронизации в обычном режиме дерево обходится от корня: узел с нулевой маской пропускается вместе с поддеревом; иначе каждому живому трекеру узла, чья маска пересекается с маской изменений и чей объём пересекает накопленный объём узла, вызывается `OnChange`; маска обнуляется; обход детей.
2. Немедленный (только двери): если флаги корпуса пересекаются с объединённой маской трекеров, обход от корня по узлам, пересекающим объём; трекер вызывается, если маски пересекаются, объёмы пересекаются и он подписан на двери.

Кто подписан (по всему коду):

| Подписчик | Маска | Объём | Двери |
|---|---|---|---|
| куб видимости | VISION \| VISION_SOLID | куб ±5 м вокруг центра (вдвое шире самого куба 5 м) | да |
| куб взрыва | FRAGMENTED | куб ±3,2 м вокруг центра (куб 3,2 м) | да |
| ячейка сторожа устойчивости | ITEM_BLOCKER | ячейка + 1 м с каждой стороны | да |
| квадраты навигационной сетки | PASS_BLOCKER | свой | нет |

### Синхронизация (Sync)
1. Базовая синхронизация с миром: посетитель обходит активные объекты и юниты, новые регистрируют корпуса, исчезнувшие — удаляют.
2. Счётчик «медленной уборки» +1; обход дерева: только когда младшие 8 бит счётчика равны нулю (каждый 256-й вызов), узел проверяет, есть ли в нём живые корпуса, и чистит мёртвые трекеры; пустые листья удаляются.
3. Для каждого динамического корпуса: мёртвые выбрасываются; если изменился объём — ищется новый узел; при смене узла корпус переезжает (оба объёма — старый и новый — попадают в изменения); если узел тот же или изменилась только поза — в изменения попадает старый объём, а при смене объёма ещё и новый, который сохраняется в слоте.
4. В быстром режиме (`ST_FAST`) на этом всё; в обычном — рассылка отложенных оповещений.

### Особые случаи и прихваты
- Изменения копятся и объединяются в одну коробку на узел: одно событие в углу и одно в другом углу узла дадут оповещение всем трекерам между ними (ложные срабатывания допустимы, пропуски — нет).
- Уборка раз в 256 синхронизаций считает узел пустым по одним лишь корпусам; лист без корпусов удаляется вместе со списком трекеров, и эти трекеры перестают получать оповещения (по коду; соответствие оригиналу не подтверждено).
- Отложенный путь не различает «подписан на двери / не подписан»; этот признак работает только в немедленном пути.
- Переключение двери не проходит через отложенный путь, поэтому навигация о нём от карты не узнаёт (она ведёт состояние дверей сама).

### Что нужно от движка-носителя
Вызов Sync раз в такт мира и дополнительно перед пересчётом видимости; механизм «объект жив/удалён» для ленивой чистки.

## 6. Трассировка одного луча с интервалами

### Назначение
Вернуть все тела на бесконечной прямой с параметрами входа и выхода: баллистика, рукопашная, выбор мышью, проверка пола под миной, камера.

### Данные
Запись результата: вход {t, нормаль}, выход {t, нормаль}, указатель на источник, UserID. Параметр t — в долях длины вектора направления (метры, если направление единичное). Нормали — нормали треугольников в мировых координатах.

### Алгоритм
Подготовка проекции:
1. Ось 1 = направление × (0,1,0), если |dx| строго больше |dy| и |dz|; иначе направление × (1,0,0). Нормировать.
2. Ось 2 = направление × ось 1. Нормировать.
3. Обе оси хранятся как плоскости (нормаль, −нормаль·начало): подстановка точки даёт её координату на плоскости, перпендикулярной лучу, с началом луча в нуле.

Тест сферы (для отбора узлов и корпусов): |(центр − начало) × единичное_направление| ≤ радиус. Это тест бесконечной прямой: тела позади начала тоже отбираются.

Одно тело:
1. Плоскости осей переводятся в локальные координаты тела (умножение на транспонированную прямую матрицу) — вершины не преобразуются.
2. Каждая вершина проецируется в 2D; если квадрат длины проекции < 1e-6 (вершина на луче), x заменяется на −0,001.
3. Для каждого ребра считается 2D-векторное произведение проекций начала и конца (знак — с какой стороны от ребра лежит луч); ноль заменяется на 1e-6.
4. Для каждого треугольника три значения рёбер берутся со знаком направления (бит 0x8000 меняет знак). Все три > 0 — луч выходит через треугольник; все три < 0 — входит; иначе мимо.
5. Для задетого треугольника восстанавливаются три мировые вершины, нормаль n = нормированное (b−a)×(c−a), `t = ((a − начало)·n) / (направление·n)`.
6. Если знаменатель точно ноль (луч в плоскости треугольника): берётся направление, перпендикулярное нормали и лучу, находятся рёбра, пересекающие разделяющую плоскость, минимальная проекция точки пересечения на направление; `t = (мин − начало·направление) / |направление|`.

Спаривание (для тела или группы тел):
1. Входы и выходы сортируются по t раздельно.
2. Замкнутое тело: при разном количестве — отладочное сообщение, лишние отбрасываются.
3. Открытая поверхность (ландшафт): если входов меньше, чем выходов, или их поровну и первый выход раньше первого входа — в начало добавляется вход t = −1e10 с нормалью (0,0,1). Если после этого входов больше — в конец добавляется выход t = +1e10.
4. i-й вход спаривается с i-м выходом; если выход раньше входа, выход подтягивается к входу (интервал нулевой длины).

Весь запрос:
1. Отбор корпусов по маске, этажам, фильтру дверей (только действующий корпус двери) и тесту сферы.
2. Ландшафт: в режиме «объединить» (по умолчанию) входы и выходы всех кусков ландшафта собираются в общие списки и спариваются вместе, источник — от первого куска; в режиме «раздельно» каждый кусок — отдельное тело.
3. Каждое тело-объект трассируется отдельно.
4. Итоговый список сортируется по t входа.

### Как присоединяется броня и плотность
В результате лежит указатель на источник корпуса: владелец (кого повредить), броня (запись `RPGArmors` → материал `RPGMaterials`), этаж, флаги; UserID говорит, в какую часть тела или фрагмент стены попали. Потребитель считает «съеденную» пробивную способность как `(max(выход,0) − max(вход,0)) · плотность_материала`; при отсутствии брони берёт броню по умолчанию. Потребители отбрасывают интервалы с входом t ≤ 0 («это прямая, а не луч»).

### Константы
| Значение | Смысл |
|---|---|
| 1e-6 | порог «вершина на луче» и подмена нулевого знака ребра |
| −0,001 | сдвиг вырожденной вершины |
| ±1e10 | бесконечные вход/выход ландшафта |
| (0,0,1) | нормаль искусственного входа/выхода |

### Особые случаи и прихваты
- Вырожденные случаи не обрабатываются точно, а превращаются в невырожденные сдвигом («кто-то должен победить»).
- В ветке «луч в плоскости треугольника» деление на длину направления вместо квадрата длины — при неединичном направлении t в других единицах; если ни одно ребро не пересечено, берётся проекция первой вершины.
- В объединённом режиме ландшафта этаж и броня берутся от первого куска, даже если луч попал в другой.
- Тело, у которого луч начался внутри, даёт интервал с отрицательным входом.

### Что нужно от движка-носителя
Матрицы объектов с возможностью умножения плоскости на транспонированную матрицу; сортировка.

## 7. Пакетный растеризатор лучей и воксельные кубы

### 7.1 Сетка лучей (CFastRenderer)

**Назначение.** Одним проходом получить интервалы сразу для прямоугольной сетки лучей — параллельных (карта высот, проходимость, трава) или расходящихся из точки (укрытия при стрельбе).

**Данные.** Двумерная сетка указателей на односвязные списки записей {вход, выход, источник, следующая}. Записи берутся из пула блоками по 4096. Список источников (источник корпуса + UserID). Матрица «мир → пиксель/глубина», обратная матрица, таблица множителей расстояния на пиксель.

**Режимы.**
1. Параллельные вертикальные лучи: начало (x,y), угол поворота сетки, шаг ячейки, прямоугольник в ячейках (включительно). Глубина = мировая высота z; интервалы — «низ/верх» тела.
2. Параллельные лучи по произвольной камере: полуразмер в метрах, полуразмер в пикселях n (сетка 2n×2n), глубина от −5000 до +5000 м.
3. Перспектива: матрица камеры, дальность, угол обзора в градусах, n, соотношение сторон. Ближняя плоскость 0,1. Шаг тангенса на пиксель = tan(угол/2)/n (по Y — умножить на соотношение).
4. Перспектива «из точки в точку»: дальность = |цель − источник| + 0,1; угол = 2·atan2(полуразмер_окна, дальность); для прямоугольного окна соотношение = y/x.

**Алгоритм.**
1. Отбор корпусов тестом «сфера в усечённой пирамиде/коробке камеры».
2. Для каждого тела (ландшафт — одной группой или по кускам) заводится новый источник и запоминается позиция в пуле.
3. Вершины тела проецируются общей матрицей; в перспективе треугольники отсекаются ближней плоскостью (z ≥ 0,01) и четырьмя охранными плоскостями (|x|,|y| ≤ 1000·z).
4. Каждый треугольник (обе стороны) растеризуется построчно в фиксированной точке 16.16 по правилу «пиксель закрашен, если его центр внутри». Вдоль строки линейно интерполируется глубина (в перспективе — 1/z). Сторона (лицевая/обратная) определяется тем, поменялись ли местами левое и правое рёбра.
5. Для каждого пикселя: расстояние = глубина (параллельный режим) или `множитель_пикселя / (1/z)`, где множитель = √(1 + (px·шагX)² + (py·шагY)²), px,py — координаты центра пикселя; получается евклидово расстояние вдоль луча.
6. Вставка: лицевая сторона пишет в поле «вход», обратная — в «выход». Если в голове списка пикселя нет незаполненной записи текущего тела для этого поля — создаётся новая запись в голове. Затем значение вставляется сортировкой внутри записей текущего тела (большие — ближе к голове, незаполненные 1e30 — в самой голове). В итоге i-й по величине вход оказывается в одной записи с i-м по величине выходом — то же спаривание, что у одиночного луча.
7. Завершение тела-объекта: в перспективе, пока в голове вход не заполнен (камера внутри тела), входы сдвигаются и в хвост ставится вход 0; затем в каждой записи выход = max(вход, выход) и проставляется источник.
8. Завершение ландшафта: у ближайшей записи незаполненный вход → −1e10; если ближайший вход больше ближайшего выхода (начали под поверхностью) — добавляется запись с входом 0 (перспектива) или −1e10 (параллельно), все выходы сдвигаются на одну запись, самая дальняя получает выход +1e10; незаполненный выход у головы → +1e10 (если у головы не заполнено ничего, она заменяется следующей записью); проставляется источник.
9. По запросу: «свести ландшафт» — у записей без владельца вход = выход − 0,01 (ландшафт превращается в сантиметровую корку на своей поверхности); «сортировать» — пузырьковая сортировка списка каждого пикселя по входу. Сведение выполняется до сортировки.

Вспомогательное: получение мировых точек входа/выхода пикселя, направления луча пикселя, координат пикселя для мировой точки (с зажимом в `[x1, x2 − 2,001]`).

**Параметры у потребителей (для ориентира).** Укрытия при выстреле игрока: n = 20 (сетка 40×40) плюс грубая n = 5; у ИИ n = 8; окно обзора 2 м в поперечнике. Проходимость: шаг 0,625/3. Трава: кусок ландшафта.

**Константы.**
| Значение | Смысл |
|---|---|
| 1e30 (биты 0x7149f2ca) | «не заполнено»; сравнивается побитово |
| 0,499 | сдвиг на полпикселя в вертикальном режиме (должно быть 0,5; оставлено «пока куски ландшафта не сдвинуты») |
| +0,01 | добавка к размерам области в коробке отбора |
| ±5000 | диапазон глубины ортокамеры |
| 0,1 | ближняя плоскость перспективы и добавка к дальности |
| 0,01 | ближняя плоскость отсечения растеризатора; толщина корки ландшафта |
| 0,001 | наклон охранных плоскостей (x,y в пределах ±1000) |
| 4096 | размер блока пула |
| 0x8000 | полпикселя в 16.16 при старте ребра |

**Прихваты.** Временные массивы проекций статические и только растут. Порядок обхода вершин треугольника зависит от режима (в вертикальном он обратный), чтобы «вход» всегда был ближней стороной.

### 7.2 Воксельный куб: общий механизм

Куб с центром, ребром и разрешением N (N³ вокселов). Заполнение: тела рисуются тем же растеризатором три раза — ортокамерами вдоль осей X, Y, Z (плоскость N×N, глубина ±половина ребра); глубина пикселя превращается в номер слоя `Float2Int(z·N − 0,5)`. Отмечаются только вокселы поверхности; три направления нужны, чтобы грани, почти параллельные лучу, не давали дыр. Отбор корпусов делается один раз (для оси X) и переиспользуется; ландшафт всегда по кускам.

### 7.3 Куб взрыва

- Воксел 0,2 м, куб 16³ (3,2 м). Пространство взрыва — сетка 64×64×8 кубов (1024×1024×128 вокселов ≈ 204,8 × 204,8 × 25,6 м), кубы создаются по требованию.
- Значение воксела — 16-битный номер объекта: 0 — пусто, 1 — ландшафт, далее — объекты в порядке первой встречи. Реестр объектов общий на пространство: ключ (владелец, UserID) → {ландшафт?, UserID, владелец, броня, номер}. Номера 0 и 1 зарезервированы при первой инициализации.
- Маска отбора `TS_FRAGMENTED`. Слой вне куба по глубине отбрасывается. Позже нарисованное тело затирает номер.
- После растеризации куб копируется в плоский массив с перестановкой осей X↔Z; вокселы на гранях мира (глобальные X или Y = 0 или 1023, Z = 0 или 127) принудительно становятся ландшафтом.
- Лень: куб подписан на изменения; `OnChange` ставит «нужен пересчёт». Признак «посчитан» не сохраняется: после загрузки куб пересчитывается при первом обращении.
- Распространение взрывной волны по вокселам — вне этого среза.

### 7.4 Куб видимости

- Воксел `F_STEP` = 0,625/4 = 0,15625 м; куб 32³ (5 м); сетка кубов 32×32×4 (160×160×20 м), центры (i + 0,5)·5; все 4096 объектов-кубов создаются сразу, считаются лениво.
- Расчёт ведётся в кубе 34³ (поле в один воксел с каждой стороны, ребро 5,3125 м), используются внутренние 32³. Слой вне куба по глубине не отбрасывается, а прижимается к крайнему слою — поле впитывает этот мусор.
- Байт воксела при расчёте: 0x80 — «непрозрачно», 0x40 — «полупрозрачно», младшие 6 бит — счётчик со смещением 0x20.
- Тело рисуется как непрозрачное (0x80), если это ландшафт или у корпуса нет флага `TS_VISION_SOLID`; иначе как полупрозрачное (0x40), и при проходе вдоль оси Z каждая грань одной ориентации добавляет к счётчику +1, противоположной −1.
- Заливка: для каждого столбца внутренних вокселов вдоль оси счётчика идёт накопление суммы (счётчик − 0x20); младшие биты стираются; пока сумма > 0 (луч внутри замкнутого полупрозрачного тела), вокселу ставится 0x40. Так листва, стекло и трава-объекты заполняются полупрозрачными вокселами по всему объёму, а непрозрачные тела остаются тонкой оболочкой.
- Хранение: два массива 32×32 из 32-битных слов — `solid[y][x]` и `transp[y][x]`, бит = номер слоя z. Если куб пуст, массивы освобождаются.
- Трава ландшафта: при создании трекера видимости все слои травы сводятся в битовую карту по тайлам: к тайлу прибавляется `Float2Int(плотность_в_тайле · макс_плотность_слоя · 10/255)` по каждому слою, плюс 10 за каждую отдельную травинку в тайле; тайл «травяной», если сумма ≥ 7. При расчёте куба для каждого из 32×32 столбцов определяется тайл (фиксированная точка 24.8: старт = `Float2Int((край_куба) · 256/0,625)`, шаг 64, тайл = значение >> 8); если в кубе есть трава, вертикальным пучком с шагом 0,15625 м по маске `TS_TERRAINS` берётся высота ландшафта (поле «выход» первой записи пикселя), `tz = Float2Int((высота − низ_куба)/0,15625)`, и биты слоёв от max(tz,0) до min(tz+6, 32) (не включая) ставятся в `transp`: шесть вокселов = 0,9375 м травы.
- Стекло: материал Glass имеет прозрачность 3,0 (не 1 и больше 0) — значит, оконное стекло участвует в видимости как полупрозрачное заполненное тело; «стекло» с бронёй Glass_ud (материал Unbreakable, прозрачность 0) — непрозрачное.
- Лень и бюджет: `OnChange` сбрасывает «посчитан», ставит «нужен пересчёт» (если куб уже считался) и очищает оба кеша запросов видимости. Мир по окончании действия вызывает «обнови видимость» с бюджетом 0,02 с: обходятся все кубы, помеченные пересчитываются, после каждого куба проверяется таймер; при превышении возвращается «не успел», и окончание действия откладывается на следующий такт (не более 21 попытки).
- Чтение воксела: координаты >> 5 — куб, & 31 — ячейка; запоминается последний использованный куб (сбрасывается в начале каждой линии). Вне сетки кубов — «пусто». Приоритет: бит solid → «непрозрачно», иначе бит transp → «полупрозрачно».

### Что нужно от движка-носителя
Программный растеризатор треугольников с доступом к каждому пикселю и признаку стороны (GPU-буфер глубины не подходит: нужны все слои, а не ближайший); данные слоёв травы; таймер высокого разрешения.

## 8. Проверка линии видимости

### Назначение
Ответить «видит ли глаз в точке A точку B» с учётом дальности, сектора обзора, непрозрачных и полупрозрачных преград.

### Данные
Кеш кубовых запросов и кеш точечных запросов: ключ {откуда, куда, эффективная дальность, косинус половины сектора} → да/нет. Множитель видимости (≤ 1).

### Алгоритм «точка-куб видима» (основной)
1. Сектор (только в плоскости XY): d — вектор на цель, f — направление взгляда. Отказ, если `(cosH − 1e-5) · |f₂|² · |d₂|² · |cosH| > |f₂·d₂| · (f₂·d₂)`. При cosH = −1 (круговой обзор) проходит всегда.
2. Эффективная дальность: h = |dz|; `eff = min(k · √(h² + (2h + R)²), 2·k·R)`, R — дальность зрения юнита, k — множитель видимости. Взгляд вверх/вниз растягивает дальность, но не более чем вдвое.
3. Отказ, если расстояние ≥ eff.
4. Поиск в кеше; при попадании — ответ из кеша.
5. Девять линий: в саму точку и в восемь точек со смещениями (±0,2; ±0,2; ±0,2). Все девять используют одно и то же расстояние (до центральной точки). Центральная линия считает бюджет от исходной дальности R, восемь смещённых — от эффективной eff.
6. Видима, если прошли больше трёх линий (≥ 4 из 9).
7. Если в кеше больше 30000 записей — он очищается целиком; результат записывается.

«Точка видима» (один луч): те же шаги 1–3, отдельный кеш (предел 15000), одна линия с бюджетом от eff.

Быстрый предварительный отсев: `расстояние² < eff²` без сектора.

### Алгоритм одной линии
1. Обе точки переводятся в вокселы: `Float2Int(координата / 0,15625 − 0,5)`.
2. `nDist = Float2Int(расстояние / 0,15625)`; при 0 — видно.
3. Бюджет полупрозрачности: `limit = −Float2Int(185,6 · ln(nDist / (дальность / 0,15625)))`, где 185,6 = 128 · 1 · 1,45.
4. a = удвоенные модули разностей по осям; ведущая ось — с наибольшим a (при равенстве x, затем y). Если a ведущей оси = 0 — видно.
5. `limit = limit · a_ведущей / nDist` (целочисленно).
6. Целочисленный 3D-обход (Брезенхэм) от начального воксела, пока координата по ведущей оси не сравняется с конечной (конечный воксел не проверяется, начальный — проверяется). Счётчик шагов n с нуля. На каждом шаге:
   - состояние текущего воксела: «непрозрачно» → не видно; «полупрозрачно» → `limit −= (n · 128) / (n + 16)` (целочисленно), и если limit < 0 → не видно;
   - если накопитель второй оси ≥ 0 — шаг по ней; промежуточный воксел проверяется только на «непрозрачно»; то же для третьей оси;
   - шаг по ведущей оси, n += 1.
7. Дошли до конца — видно.

Смысл формул: цена полупрозрачного воксела растёт с удалением от глаза (0 вплотную, 64 на 16-м шаге = 2,5 м, стремится к 128), поэтому из куста, в котором сидишь, видно хорошо, а сквозь дальний куст — плохо. Бюджет тем больше, чем ближе цель относительно дальности зрения: на половине дальности ≈ 129, на четверти ≈ 257, на полной дальности 0, за её пределами отрицателен (первый же полупрозрачный воксел блокирует).

### Точки цели и глаза (у потребителей, для связности)
- Точки цели: основание = точка стояния + 0,5 м по высоте. Лёжа — основание и ±0,625 м вдоль направления тела; сидя — основание и +0,5; стоя — основание, +0,5, +1,0. Цель видима, если видима хотя бы одна точка.
- Глаз: лёжа — 0,625 м вперёд и 0,4 м вверх; сидя — 1,1 м; стоя — 1,56 м.
- Труп проверяется по своим точкам частей тела тем же девятилучевым тестом.
- Дальность зрения по умолчанию 20 м; сектор по умолчанию π; ночью общий множитель 0,666; перк ночного зрения ночью умножает дальность на 1,5015; радиус сбора кандидатов 40 м.

### Константы

### Особые случаи и прихваты
- Кеши сбрасываются целиком при любом изменении любого куба видимости и при смене множителя (день/ночь); множитель ограничен сверху 1.
- Старый трёхаргументный вариант (дальность 20, вместо сектора — полупространство «не позади», порог ≥ 4 из 9, ключ кеша «подсолен» значениями 20 и −2) оставлен для проб мин и предметов.
- Смещённые линии уходят на 0,2 м в стороны, но длину и бюджет берут от центральной — вблизи препятствий часть линий «заглядывает за угол».
- Модуль `aiVision` — старый подход «кубическая карта из шести перспективных сеток по 90°» (выбор грани по наибольшей компоненте направления, пиксель = n ± отношение компонент · n, сетка с сортировкой интервалов); в игре используется только отладочным просмотрщиком.

### Что нужно от движка-носителя
Положение глаз и направление взгляда юнитов, время суток, перки; вызов «обнови видимость» с бюджетом времени в конце каждого действия.

## 9. Физический коллайдер (обломки, трупы, гранаты)

### Назначение
Двигать шары сквозь мир со скольжением по поверхностям и трением; сообщать точку, плоскость и источник первого контакта.

### Данные
- «Суп треугольников» в мировых координатах: общий массив вершин, треугольники {три индекса, номер пользовательских данных, плоскость}, для каждого — три ребра в шестимерных (плюккеровых) координатах для теста отрезка.
- Контейнер объёмов — иерархическая сетка: уровень i содержит (2^i)³ ячеек со списками номеров элементов. Глубина: начиная с 1, наибольший размер объёма делится пополам, пока он больше «размера элемента» и глубина меньше 6 (самый мелкий уровень — до 32³). Масштаб по каждой оси свой.

### Алгоритм контейнера
- Координата ячейки мелкого уровня: `Float2Int((p − min) · масштаб − 0,5)`.
- Добавление: целочисленная коробка элемента; элемент целиком вне сетки — отбрасывается; коробка обрезается; уровень выбирается так, чтобы элемент занимал не более ~2 ячеек по наибольшей оси (поднимаемся на уровень, пока протяжённость > 1, деля её пополам); номер пишется во все покрытые ячейки уровня.
- Выборка по коробке: на каждом уровне перебираются покрытые ячейки; повторы отсекаются меткой «номер последней выборки» у элемента. При глубине 1 возвращается весь список без проверок.

### Подготовка
Для набора шаров со сдвигами: M = max(наибольший радиус, наибольшая длина сдвига). Объём = объединение шаров в начале и в конце пути; для режима скольжения расширяется на 2M. Размер элемента 2M. ИИ-карта отбирает корпуса по маске (все этажи) и сфере объёма; каждый кусок (и объекты, и ландшафт) добавляется треугольниками в мировых координатах; вырожденные треугольники пропускаются; можно задать игнорируемых владельцев.

### Шар против треугольника (движущийся)
1. Если нормаль·единичное_направление > −1e-6 — нет (движение вдоль плоскости или от неё).
2. Ближайшая к плоскости точка шара = центр − радиус·нормаль; её расстояние до плоскости D.
3. D больше проекции пути на нормаль — далеко, нет. D < 0 (шар уже врезан) — точка касания плоскости = проекция этой точки на плоскость; иначе — точка, в которую она придёт вдоль направления движения.
4. Если точка касания вне треугольника — заменить ближайшей точкой на трёх рёбрах.
5. Обратный луч из этой точки к шару: q = точка − центр, v = q·направление; v < 0 — нет; d = r² − |q|² + v²; d < 0 — нет; расстояние = v − √d; больше длины пути — нет. Иначе контакт на этом расстоянии, точка контакта — найденная точка треугольника.

### Скольжение одного шара
Повторять, пока квадрат оставшегося сдвига > 1e-8, не более 9 раз:
1. Найти ближайший контакт. Перед учётом каждого контакта спрашивается «бьётся ли стекло» (ниже): если да — контакт игнорируется.
2. Нет контактов — переместить шар на весь остаток, закончить.
3. Запомнить минимальный этаж среди задетых корпусов.
4. Сдвинуть шар на расстояние до контакта; вычесть пройденное из остатка.
5. Нормаль скольжения = нормированное (точка контакта − центр шара). Убрать из остатка составляющую вдоль неё (её величина s).
6. Если контакт с ландшафтом и |z нормали плоскости| > 0,5 (пол) — остаток обнуляется (шар «прилип» к земле).
7. Иначе трение: остаток укорачивается на min(0,4·|s|, длина остатка).

### Разбивание стекла
Контакт пропускается (шар пролетает), если броня корпуса помечена «предмет может разбить» (в базе это Glass и Glass curtain) и владелец — живой объект мира; при этом, если с последней смены стадии разрушения объекта прошло больше 300 тиков, стадия увеличивается на 1. Во всех остальных случаях контакт твёрдый. Проверка вызывается для каждого контакта скользящего шара.

### Прочие тесты
- Информация о контакте: ближайший контакт → {расстояние, точка, источник, UserID, плоскость}; нет контакта → расстояние −1e20.
- Отрезок–треугольник: концы по разные стороны плоскости и три плюккеровых «скалярных произведения» отрезка с рёбрами неотрицательны; точка — линейной интерполяцией; коробка выборки расширена на 1 %.
- Треугольник–шар (статический; им же запекаются сетки): любая вершина ближе радиуса → да; вырождение в отрезок/точку обрабатывается отдельно (порог квадрата длины стороны 1e-6); отсев по вороным областям вершин; расстояние до плоскости ≥ радиуса → нет; проекция центра вне треугольника → проверка расстояния до соответствующего ребра (только внутри его длины); иначе да.

### Константы
| Значение | Смысл |
|---|---|
| 6 | максимум уровней контейнера |
| 10 (9 проходов) | предел итераций скольжения |
| 1e-8 | квадрат «нулевого» остатка |
| 0,4 | коэффициент трения |
| 0,5 | порог «это пол» по z нормали |
| −1e-6 | порог «движение от плоскости» |
| 300 тиков | минимальный интервал между стадиями разбивания стекла |
| −1e20 | «нет столкновения» |
| 1,01 | расширение коробки отрезка |
| 100 | начальное значение «минимального этажа» |

### Что нужно от движка-носителя
Интегратор обломков/рэгдолла, который каждый такт отдаёт шары и желаемые сдвиги и забирает новые центры; часы «прицельного времени» мира; стадии разрушения объектов.

## 10. Сторож устойчивости

### Назначение
Когда разрушается то, на чём что-то лежало, заставить лежащее упасть: предметы обстановки ломаются, трупы снова падают, застывшие обломки оживают, мины взрываются.

### Данные
- Сетка ячеек-трекеров над всей картой. Ячейка хранит четыре списка: трупы, застывшие обломки, объекты, мины. Элемент списка: объект, его объём и список «ловцов» — указателей на корпуса, пересекавшие объём в момент регистрации.
- До «окончания строительства» карты регистрации объектов, обломков и мин копятся в очередях; мировой ящик растёт от каждого вставленного корпуса и каждого зарегистрированного объекта.

### Алгоритм
Окончание строительства:
1. Число ячеек по оси = `Float2Int(протяжённость / 2)`; ограничение: X и Y не более 16, Z не более 8; меньше 2 → 1.
2. Мир делится поровну; объём каждой ячейки расширяется на 1 м по каждой оси; ячейка подписывается на карту с маской `TS_ITEM_BLOCKER`, включая двери.
3. Очереди раздаются по ячейкам.

Регистрация:
- объект: объём = объединение его шаров масс в мире; кладётся в ячейку центра и в ячейку верхнего угла объёма, если она другая (проверка выполняется дважды, поэтому объект на границе ячеек записан в угловую ячейку два раза);
- обломок и мина: шар радиуса 0,5 м в их позиции, ячейка центра;
- труп: объём даёт вызывающий; до окончания строительства игнорируется;
- ловцы: корпуса с флагом `TS_ITEM_BLOCKER` и без `TS_LOCKED_EXTRA`, чьи сохранённые объёмы пересекают объём (с фильтром дверей).
- Номер ячейки: усечение `(v − min) · n / (max − min)` с зажимом в [0, n−1].

Срабатывание ячейки (`OnChange`): для каждого элемента — «неустойчив», если хотя бы один из запомненных ловцов отсутствует в свежем списке ловцов по тому же объёму (сравнение по тождеству указателей). Устойчивые остаются. Неустойчивые:
- объект: вызывается его собственная проверка устойчивости (ниже); устоял — остаётся в списке, нет — уничтожает себя и выбывает;
- труп: если его не несут — снова «роняется» как рэгдолл; выбывает из списка в любом случае (зарегистрируется заново, когда остановится);
- обломок: контроллер обломков оживляет его; выбывает;
- мина: луч вниз по маске `TS_ITEM_BLOCKER`; берётся ближайший вход с t ≥ 0; если поверхность не ниже 0,1 м под миной — остаётся, иначе взрывается.

Проверка устойчивости объекта:
1. Шары масс модели переводятся в мир.
2. Для каждого шара — «пересекает ли шар что-нибудь» по маске `TS_ITEM_BLOCKER`, исключая сам объект.
3. Шаров меньше 4 — устойчив, только если опираются все. Иначе неустойчив, если опирающихся ≤ n/2 (целочисленное деление): нужно больше половины.
4. Нет модели или шаров — устойчив.

### Константы
| Значение | Смысл |
|---|---|
| 2 м | желаемый размер ячейки |
| 16 × 16 × 8 | максимум ячеек |
| 1,0 м | расширение объёма ячейки |
| 0,5 м | радиус объёма обломка и мины |
| 0,1 м | допустимое проседание пола под миной |
| 4 | порог «мало шаров — нужны все» |
| FP_STABLE_HEIGHT = 0,15 | объявлена, не используется |

### Особые случаи и прихваты
- Новые опоры не учитываются; важна только пропажа старых. Элемент без ловцов никогда не станет неустойчивым.
- Запертые двери и окна исключены из ловцов, недействующий корпус двери — тоже; открытие двери, на которую что-то опиралось, роняет это.
- Срабатывает вся ячейка на любое изменение `ITEM_BLOCKER`-корпуса в её расширенном объёме; дальше фильтрует сравнение ловцов.
- Мина без единого пересечения внизу взрывается.

### Что нужно от движка-носителя
Сигнал «карта построена»; методы объекта «проверь устойчивость/умри», «урони труп», «оживи обломок», «взорви мину».

## 11. Кратко о прочих файлах среза

- BSP-деревья (`BSPTree`, `BSPCollider`): прежняя реализация теста шара — дерево разделяющих плоскостей с листьями «заполнено/пусто», со «скосами» на рёбрах и отдельным построением для ландшафта; константы точности 0,01 и 0,1, цена разбиения 3. В выпущенной игре заменены битовыми сетками и во время игры не используются; из этих файлов жив только тест «треугольник–шар» (продублирован в физическом коллайдере).
- `aiMisc`: не геометрия — вспомогательные функции стоимости пути в очках действия и поиска ИИ-командира; описываются в других спецификациях.
- `aiMapProxy.h`: обёртка навигационного слоя для раскраски областей — относится к навигации.

## Пример

### Пример 1. Луч сквозь кирпичную стену и окно
Стрелок в точке (0; 0; 1,5), направление (1; 0; 0). Кирпичная стена — коробка x от 5,0 до 5,3; за ней оконное стекло — коробка x от 8,00 до 8,02. Ландшафт — плоскость z = 0.

1. Оси проекции: |dx| строго наибольший → ось 1 = (1,0,0)×(0,1,0) = (0,0,1); ось 2 = (1,0,0)×(0,0,1) = (0,−1,0). Координаты точки на плоскости: (z − 1,5; −y).
2. Передняя грань стены, треугольник A(5;−1;0), B(5;1;0), C(5;0;3) проецируется в A′(−1,5; 1), B′(−1,5; −1), C′(1,5; 0). Знаки рёбер: A′×B′ = 3, B′×C′ = 1,5, C′×A′ = 1,5 — все одного знака, значит начало координат (луч) внутри треугольника. Какой это знак («вход» или «выход») определяет порядок обхода: для грани, обращённой к стрелку, все три отрицательны → вход.
3. t = ((A − начало)·n)/(направление·n) при n = (−1,0,0): ((5;−1;−1,5)·n)/(−1) = 5,0. Задняя грань даёт выход t = 5,3.
4. Стекло: вход 8,00, выход 8,02. Луч параллелен земле и ландшафт не задевает: списки входов и выходов пусты, искусственные интервалы не добавляются.
5. Результат после сортировки: {5,0 … 5,3; броня Brick} и {8,00 … 8,02; броня Glass}.
6. Потребитель: стена съедает 0,3 · 4000 = 1200 единиц пробивной способности, стекло 0,02 · 1 = 0,02.

Если стрелок стоит по пояс в яме и луч начинается под поверхностью земли: ландшафт даёт один выход (скажем, t = 2,4) и ни одного входа → добавляется вход −1e10; интервал {−1e10 … 2,4} потребитель обрежет нулём: 2,4 м грунта.

### Пример 2. Видимость сквозь траву
Наблюдатель лежит, цель в 10 м строго по оси X на той же высоте, дальность зрения 20 м, день (k = 1), сектор проходит.

1. h = 0 → eff = min(√(0 + 20²), 40) = 20; 10 < 20 — проходит.
2. nDist = 10 / 0,15625 = 64. Центральная линия: limit = −Float2Int(185,6 · ln(64 / 128)) = −Float2Int(−128,65) = 129.
3. Ведущая ось X: a = 2 · 64 = 128; limit = 129 · 128 / 64 = 258.
4. Случай А — наблюдатель сам в траве, трава занимает первые вокселы линии. Цены по шагам n = 0…10: 0, 7, 14, 20, 25, 30, 34, 38, 42, 46, 49. Сумма первых десяти = 256 ≤ 258 — проходит; одиннадцатый воксел (ещё 49) уводит бюджет в минус. Итог: из травы видно сквозь 10 вокселов (≈1,56 м) своей травы.
5. Случай Б — полоса травы начинается в 3,1 м от наблюдателя (n = 20). Цены: 71, 72, 74, 75… Сумма трёх = 217 ≤ 258, четвёртый воксел (сумма 292) блокирует. Итог: дальняя трава толщиной больше ≈0,47 м закрывает цель.
6. То же считается для восьми смещённых линий; цель (эта её точка) видима при четырёх и более прошедших линиях из девяти. У лежащей цели три точки; достаточно одной видимой.

### Пример 3. Индекс запечённой сетки и устойчивость
- Ящик 1×1×1 м с центром в нуле: коробка с запасом ±0,81; nX = nY = Float2Int(0,81·20 + 1) = 17; ptMin = (−0,81; −0,81; −0,81); nZ = Float2Int(1,62·10 + 1) = 17 — один блок. Точка (0,6; 0; 0): ix = Float2Int(1,41·10 − 0,5) = 14, центр ячейки x = −0,81 + 14,5·0,1 = 0,64; расстояние до грани x = 0,5 равно 0,14 < 0,31 → бит стоит, «столкновение». Точка (0; 0; 0) — до ближайшей грани 0,5 > 0,31 → бит не стоит (эффект «пустой середины»).
- Шкаф с 5 шарами масс, из-под которого выбили пол: опираются 2 шара → 2 ≤ 5/2 = 2 → неустойчив, шкаф уничтожается. При 3 опирающихся — устойчив. Табурет с 3 шарами: нужны все 3.

## Отклонения реконструкции от оригинала

Пометок `[FORK]` в файлах среза нет. Отмеченные автором реконструкции расхождения и правки:

1. Октодерево: узел хранит готовую сферу вместо угла куба (как в версии 1.2); порог спуска 0,2165 вместо более раннего 0,433; чтение старых сохранений восстанавливает сферу по углу.
2. Реестр «объект → корпуса» введён как в оригинале, но «объём объекта» и внутренний поиск корпуса по-прежнему обходят дерево; «корпус объекта» берёт первый действующий корпус из реестра.
3. «Центр части тела» принимает корпус напрямую (ранняя форма параметров), а не объект; перенесён только булев результат.
4. Коллайдер на сетках: при выборке расширяется радиусом только копия коробки, а не сама коробка движения — исправление двойного учёта радиуса (заявлено как соответствие оригиналу).
5. Коллайдер на сетках не принимает ландшафт: в комментарии ссылка на оригинал, но мотивировка — нагрузка при загрузке; считать не вполне подтверждённым.
6. Воксельные рендереры используют растеризацию в фиксированной точке 16.16 (как в версиях 1.1/1.2), ранняя версия — в плавающей.
7. Сведение ландшафта выполняется до сортировки (как в 1.2).
8. Направление луча пикселя делится на однородную координату до вычитания начала (исправление по 1.2).
9. Куб видимости: слой травы ландшафта восстановлен по оригиналу (в ранних исходниках его не было); ключ кеша видимости расширен двумя числами — кеши старых сохранений нечитаемы.
10. Старый трёхаргументный тест видимости оставлен для части потребителей; в оригинале везде пятиаргументный.
11. Сторож устойчивости: при пустой карте вместо границ навигационной сети берётся единичный ящик; ссылка на сторожа — владеющая.
12. Обход линии видимости не проверяет конечный воксел (по 1.2).
13. Номер ячейки сторожа — усечением, не округлением (по 1.2).
14. `aiMisc`: вместо оригинального калькулятора стоимости пути — локальный двойник.

## Не установлено

1. Какой из двух дверных наборов сеток (чанк 3 / чанк 4) соответствует открытой двери: имена полей реконструкции («open» у чанка 3) противоречат тому, что набор из чанка 3 получает корпус с флагом «закрыто» и кадром закрытой двери.
2. Знак ориентации граней в заливке куба видимости (какая грань даёт +1) — зависит от соглашений матрицы камеры, не прослежено; по проверке в коде сумма внутри тела положительна.
3. Теряются ли в оригинале трекеры при удалении пустого листа октодерева раз в 256 синхронизаций — по коду теряются.
4. Точное поведение завершения ландшафта в сетке лучей, когда выходов больше, чем входов, более чем на один (возможна запись с незаполненным входом) — не проверено.
5. Карта травы хранится в знаковых байтах при зажиме 0…255: суммы выше 127 могут стать отрицательными и не пройти порог 7 — ошибка реконструкции или оригинала, не подтверждено.
6. Назначение полей «объём куска» и «стыки» внутри среза не видно (только хранение).
7. Содержимое реальных файлов геометрии (сколько блоков сеток у типичных объектов, есть ли сетки в чанке 9) не проверялось — читался только код загрузчика и таблицы базы.
8. Формат ресурса привязок костей (кеш 118) и вычислителя объёма скелета — вне среза.
9. Почему у ортокамеры вертикального режима сдвиг 0,499, а не 0,5, и сохранён ли он в оригинале — только комментарий в коде.
10. Правило «более 6 кусков → только кусок 0» в служебной выдаче геометрии: назначение неясно.
